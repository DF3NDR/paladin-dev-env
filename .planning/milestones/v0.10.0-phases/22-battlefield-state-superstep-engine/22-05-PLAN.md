permits cycles, a superstep loop with snapshot isolation and bounded concurrency, one automatic
Waypoint per superstep, and typed limit errors.

runs inside the loop this plan builds, so the isolation guarantee (ENG-FR-05), the one-Waypoint-per-
superstep guarantee (ENG-FR-11) and the bounded-iteration guarantee (ENG-FR-03) must be nailed down
and unit-tested here with `Function` nodes only, no LLM in the picture.

Output: `WarGraph::validate`, the superstep loop, `EngineLimits` enforcement, and engine test doubles.
</objective>

  <action>
    Write the failing tests first, then implement.

    Create `engine/superstep.rs` holding the loop body, and reduce `WarEngine::start` in
    `engine/mod.rs` to setup plus a call into it. Implement ENG-FR-01's seven steps in order:
    take the current vanguard; take ONE `Arc<Battlefield>` read snapshot for the whole superstep;
    execute the vanguard's nodes concurrently; collect one `(NodeId, StateDelta)` per node; merge
    them through `Battlefield::merge` with the superstep number; compute the next vanguard; persist
    exactly one Waypoint; then decide whether to continue.

    Concurrency follows the in-tree shape from `phalanx_service.rs::execute_collect_all`: spawn one
    task per node with cloned handles, collect the `JoinHandle`s in one loop, then await them in a
    second loop — never await inside the spawn loop. Bound in-flight work with a
    `tokio::sync::Semaphore` whose permit count defaults to the vanguard's size (D-12) and is
    configurable on the engine. Every spawned task receives `Arc::clone` of the same snapshot, so
    the Battlefield is cloned once per superstep and not once per node (ENG-NFR-02). Nothing inside
    a spawned task may touch the mutable Battlefield — collect, then merge after the join. This is
    what makes ENG-FR-05 isolation true by construction rather than by discipline.

    Diverge from the Phalanx analog in one place: that service collects per-node errors into a
    `Vec<String>` and returns partial results. The engine keeps that collect-then-report shape for
    individual node failures within a superstep, but a Waypoint write error is propagated
    immediately — under `Strict` it becomes `EngineError::WaypointWrite` and stops the run before
    the next superstep begins.

    Persist exactly one Waypoint per superstep, after the merge and before the continue decision,
    using the child-lineage constructor so `parent_waypoint_id` chains correctly. Populate
    `completed` with a `NodeExecutionRecord` per node that ran (duration, outcome, `attempt: 1` —
    Doc 04 populates attempt meaningfully) and `vanguard` with the nodes ready for the next
    superstep. When the vanguard is empty the Waypoint's status is `Completed` and the run returns
    `RunOutcome::Completed`; the empty-entry-vanguard case takes this same path on superstep zero.

    Make `WaypointDurability::Strict` the value a caller gets without choosing, and document
    `BestEffort` at its definition with the consequence stated inline: a failed checkpoint write
    becomes a logged warning and a superstep of work can be lost. Do not select `BestEffort` in any
    example, doc snippet or shared test helper — the two tests that exercise it opt in explicitly
    and locally.

    Create `engine/test_support.rs` (compiled under `#[cfg(test)]`) with a `RecordingWaypointStore`
    that implements `WaypointPort` over a `Mutex<Vec<Waypoint>>`, exposes the saved Waypoints and a
    save-call count, and can be configured to fail its next save; and a `CountingFunctionNode`
    implementing `StateNode` that records how many times it ran, what snapshot value it observed,
    and returns a configured delta. These doubles are what every later engine plan asserts against.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| graph author -> engine | A caller-supplied graph controls how many tasks are spawned and how long a run iterates |
| node code -> shared snapshot | Concurrently executing node implementations share one read snapshot |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-13 | Denial of Service | unbounded superstep iteration on a cyclic graph | high | mitigate | `max_supersteps` is required, validated non-zero, and enforced at the top of each iteration with a typed `RecursionLimitExceeded`; `max_node_visits` bounds a single node independently so a tight self-loop cannot monopolise a run |
| T-22-14 | Denial of Service | unbounded task spawn for a large vanguard | medium | mitigate | A `tokio::sync::Semaphore` bounds in-flight node executions per superstep, defaulting to the vanguard size and configurable on the engine, following the existing Phalanx concurrency-bound pattern |
| T-22-15 | Tampering | a node observing or mutating a peer's mid-superstep state | medium | mitigate | Nodes receive an `Arc<Battlefield>` read snapshot and cannot reach the mutable state; deltas are collected and merged only after the join, asserted by an `Arc::ptr_eq` test and a peer-visibility test |
| T-22-16 | Repudiation | a run that silently loses its checkpoint | high | mitigate | `WaypointDurability::Strict` is the unchosen default and turns a save failure into `EngineError::WaypointWrite`; `BestEffort` documents the loss consequence at its definition and is selected nowhere outside its own two tests, enforced by a grep acceptance check |
</threat_model>
