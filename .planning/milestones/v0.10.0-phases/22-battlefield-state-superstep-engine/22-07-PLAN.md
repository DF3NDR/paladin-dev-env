Complete ENG-02: precise join and defer semantics that never deadlock on a not-firing branch, a
deterministic frontier and merge order proven byte-identical under randomized concurrent scheduling,
and engine-level custom dispatch registration.

Purpose: the superstep loop from Plan 22-05 executes a vanguard; this plan decides what the *next*
vanguard is. Join semantics are where the current Campaign behavior is imprecise (a false branch can
strand a downstream join), and determinism under real concurrency is the guarantee everything
downstream — resume, golden equivalence, replay — silently depends on.

the X-05 multi-thread stress test.

  <behavior>
    - Diamond graph A to B, A to C, B to D, C to D: D executes exactly once, in the superstep after both B and C have completed, never once per incoming edge
    - Same diamond where the A-to-C edge condition evaluates false: C never executes, C is proven not-firing, and D still executes exactly once rather than waiting forever
    - A node whose only incoming edge comes from an unreachable node is itself never executed and does not stall its own downstream joins
    - A node marked `defer` with two sibling branches executes only after both branches have drained, in a superstep where no other node is executable
    - Two `defer` nodes in one graph resolve in stable insertion order rather than map order
    - Adding the same nodes and edges to a graph in a different insertion order still produces the identical Vanguard sequence for identical node outputs

  <action>
    Write the failing tests first, then implement.

    Implement next-Vanguard computation as an explicit readiness rule rather than a
    dependencies-satisfied heuristic. Track, per node, the resolution state of each incoming edge:
    *fired* (the source completed and the condition evaluated true), *not-firing* (the source
    completed and the condition evaluated false, or the source is unreachable given conditions
    already resolved), or *pending*. A node becomes executable when no incoming edge from a
    run-reachable source is still pending and at least one has fired. This is the precise form of
    the existing Campaign readiness check plus the not-firing case, and the not-firing case is what
    stops a false branch from stranding a downstream join.

    Add a `defer: bool` on `NodeSpec` (or its per-node metadata). A deferred node that is otherwise
    executable is held back until the computed Vanguard contains no non-deferred executable node,
    giving aggregate-after-all-branches semantics. Multiple deferred nodes released in the same
    superstep are ordered by the graph's insertion order.

    Make the frontier deterministic by construction: iterate nodes and edges through the graph's
    stable insertion-order views, never through raw map iteration. Collect and sort where a map must
    be traversed. Add the insertion-order test from the behavior list — build the same logical graph
    twice with different insertion sequences and assert the two runs produce the identical Vanguard
    sequence.

    Add the cycle tests: a self-loop that leaves the Vanguard when its condition stops holding, and
    a two-node cycle that terminates on its edge condition rather than on `max_supersteps`. These
    are what prove cycles are a first-class execution shape here and not merely un-rejected.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| graph author -> custom dispatch closure | Application-supplied executable code runs inside the merge path on every superstep |
| conditional edges -> frontier | Edge conditions decide which nodes ever run, and a mis-resolved condition can strand or over-run a branch |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-22 | Denial of Service | a downstream join stranded by a false branch | high | mitigate | The readiness rule resolves every incoming edge to fired or provably-not-firing before a join waits, with a dedicated test carrying an explicit timeout guard so a regression fails loudly instead of hanging |
| T-22-23 | Denial of Service | a panicking or non-terminating custom dispatch closure | medium | accept | The PRD requires panic and slowness isolation for the `TraceSink` (ENG-FR-21) but states no equivalent requirement for `Custom` dispatch closures or interceptors. Accepted for this epic with the asymmetry documented at the registry's definition so a consumer knows a custom rule runs on the critical path unguarded; wrapping arbitrary closures is out of scope here |
| T-22-24 | Tampering | a custom rule silently shadowing a built-in merge semantic | medium | mitigate | Registration of a name colliding with a built-in variant is rejected, so a schema author cannot believe they overrode `LastWrite`; an unregistered name fails validation rather than falling back to any built-in |
| T-22-25 | Tampering | nondeterministic merge producing divergent state across replays | high | mitigate | Merge and frontier order are fixed by explicit sorting and stable insertion-order iteration, proven by a 20-iteration seeded randomized-scheduling test asserting byte-identical serialization of both the final state and the Vanguard sequence |
</threat_model>
