<objective>
Close the storage half of gap G-22-2 (blocker): give `WaypointPort` a delete-only-unprotected
primitive.

The retention routine today implements pruning as delete-then-resave — wipe the whole thread with
`delete_thread`, then save the survivors back. A crash or backend failure between the two destroys
the thread's protected Waypoints: its latest, and any `AwaitingInput` checkpoint a human is
waiting on. That inverts the runtime's core invariant, and "retention is disabled by default"
does not contain it, because it ships as a callable routine.

The primitive is wrong, not the feature. A prune that only ever deletes rows outside the keep-set
has no crash window at all: the protected rows are never touched, so there is no interval during
which they are missing. This plan adds that primitive and proves it across all three backends.
Plan 22-14 rewrites the retention routine on top of it.

Purpose: make the keep-set intact under any interruption, by construction rather than by
sequencing.
Output: `WaypointPort::prune_thread` with a safe provided implementation, transactional SQL
overrides, and shared contract coverage on InMemory, SQLite and Postgres.
</objective>

  <name>Task 1: Add the delete-one and prune_thread surface to WaypointPort, contract-first</name>
  <files>crates/paladin-ports/src/output/waypoint_port.rs, crates/paladin-storage/src/waypoint/contract_tests.rs, crates/paladin-storage/src/waypoint/in_memory.rs</files>
  <behavior>
Write the shared contract functions before either implementation, and run them against
`InMemoryWaypointStore` to watch them fail first.

- delete-one removes exactly the named Waypoint: a thread holding three, after deleting the
  middle one, holds the other two and reports that a row was removed.
- delete-one on an id the thread does not hold reports that no row was removed, is not an error,
  and leaves the thread's contents unchanged.
- delete-one on a thread the backend does not hold reports no row removed, not an error.
- `prune_thread` with a keep-set naming two of five ids leaves exactly those two, in the same
  history order, with their payloads byte-identical to what was saved.
- `prune_thread` returns the number of Waypoints it removed.
- `prune_thread` with an empty keep-set removes every Waypoint of the thread.
- `prune_thread` on a thread the backend does not hold returns zero, not an error.
- `prune_thread` given ids that are not in the thread ignores them: they are not an error and
  cause no deletion of anything else.
- `prune_thread` run twice with the same keep-set removes nothing the second time and leaves the
  keep-set intact — idempotence.
- convergence: after a `prune_thread` that leaves a superset of the keep-set (simulate by first
  pruning to a larger keep-set, then pruning again to the target), a second run with the target
  keep-set reaches exactly the target.
- large keep-set: a thread holding 1,200 Waypoints pruned to a keep-set of 1,100 ids leaves
  exactly those 1,100. This is the parameter-limit guard — it must live in the shared suite so
  every backend proves it, not in a backend-specific test.
  </behavior>
  <action>
Extend the `WaypointPort` trait in `crates/paladin-ports/src/output/waypoint_port.rs` with two
methods, both `async` under the existing `#[async_trait]`:

1. A required delete-one primitive taking `&ThreadId` and `&WaypointId` and returning
   `Result<bool, WaypointError>` — `true` when a row was removed, `false` when the thread or the
   id is unknown. Follow the module's existing "Missing is `None`, not an error" contract in both
   the signature and the rustdoc: an unknown id is the normal case, never an error.

2. `prune_thread(&self, thread: &ThreadId, keep: &[WaypointId]) -> Result<u64, WaypointError>`
   as a **provided** method, returning how many Waypoints it removed. Implement the default body
   using only the port's own surface: page through `history` to enumerate the thread's ids, then
   call the delete-one primitive for each id absent from `keep`. Page with an explicit `limit`
   and the `before` cursor rather than requesting the whole history unbounded, so a very long
   thread does not materialise entirely in memory.

Rustdoc `prune_thread` with the contract the rest of the system will rely on, stated as
properties rather than as a description of the loop:

- Monotone. It only ever removes ids absent from `keep`. There is no point during the call at
  which an id present in `keep` is missing from the backend. This is why it replaces the previous
  delete-then-resave approach: that one had an interval during which protected Waypoints did not
  exist, and an interruption inside that interval destroyed them.
- Crash-safe by construction. An interruption part-way through leaves a superset of `keep` —
  some intended removals not yet done, and nothing else. A superset is always a safe state.
- Idempotent and convergent. Re-running with the same `keep` after any partial run reaches
  exactly `keep` and removes nothing thereafter.
- Best-effort reclamation. Leaving extra Waypoints behind is acceptable; removing one named in
  `keep` never is. Callers must treat the returned count as informational.
- Policy-free. The port does not know what "protected" means. Deciding which ids belong in
  `keep` is the application layer's job (X-01) — the port is handed the answer.
- Overridable. A backend that can express the whole operation atomically should override this
  method; the provided body exists so that a backend which cannot is still correct.

Also document on the delete-one primitive that callers wanting to prune a thread should reach for
`prune_thread` instead, so nobody rebuilds the unsafe sequence by hand.

Update the `MockWaypointStore` fixture inside that file's test module to implement the new
required method, and keep the existing object-safety test passing.

Then add the contract functions listed in `<behavior>` to
`crates/paladin-storage/src/waypoint/contract_tests.rs`, one `pub async fn` per clause taking
`&dyn WaypointPort`, named after the clause they enforce, following the file's existing style
exactly. Add every one of them to `run_all`. Finally wire `InMemoryWaypointStore` into each with
one `#[tokio::test]` per contract function in `in_memory.rs`, and override `prune_thread` there
with a single `retain` under one write-lock acquisition — the in-memory store can do the whole
operation without an intermediate observable state, and should.
  </action>

  <files>crates/paladin-storage/src/waypoint/sqlite.rs, crates/paladin-storage/src/waypoint/postgres.rs</files>
  <behavior>
Both SQL backends must pass every contract function added in Task 1, unchanged and with no
per-backend relaxation — that is what "one shared suite" means here. Wire them in first and watch
them fail against the provided default before writing the overrides.

Additional backend-specific expectations, each its own test:
- SQLite: pruning a thread of 1,200 Waypoints down to a 1,100-id keep-set succeeds. The default
  per-statement bound-parameter limit is well below 1,100, so a naive single `IN` list would fail
  here — this test is the reason the override is written the way it is.
- SQLite: a `thread_id` and a `waypoint_id` containing SQL metacharacters round-trip through
  `prune_thread` as data, matching the existing metacharacter test in this module.
- Postgres: the same 1,200-to-1,100 case and the same metacharacter case, both behind the
  module's existing reachability gate so they return early with a named reason when no server is
  up rather than hanging or panicking.
  </behavior>
  <action>
Override `prune_thread` on both SQL backends so every deletion for one call commits or rolls back
together. An interruption must leave either the pre-call state or the post-call state, never a
partially-pruned thread — and in neither of those states is any id from `keep` missing.

Postgres: express it as one statement inside the driver's implicit single-statement transaction,
binding the keep-set as a text array and matching rows whose `waypoint_id` is not equal to any
element of it. An array bind has no per-element parameter cost, so the keep-set size is
unbounded. An empty array is the natural degenerate case — every row fails the "not equal to any
element" test vacuously and the whole thread is removed, which is exactly the specified empty
keep-set behaviour. Confirm that with the shared contract function rather than reasoning about
it.

SQLite: sqlx's SQLite driver has no array binding, and a per-id `IN` list would run into the
per-statement bound-parameter limit — the reason the 1,200-Waypoint test exists. Open an explicit
transaction, select the thread's ids inside it, compute the delete-set in Rust as the ids absent
from `keep`, issue the deletions in bounded chunks of bound parameters within that same
transaction, and commit once. Atomicity comes from the single transaction, not from the single
statement, so chunking costs nothing. Choose a chunk size comfortably under the driver's limit
and name the limit in a comment beside it.

Both overrides: bind `thread_id` and every id as parameters. No query text may be assembled by
formatting a caller-supplied value into it — this is the existing T-22-17 mitigation and it
applies unchanged to the new statements. Return the number of rows removed. Route errors through
each backend's existing error wrapper so the credential-redaction path (T-22-18) covers these
statements too.

Then wire both backends into every contract function from Task 1 with one `#[tokio::test]` each,
following each module's existing style — `fresh_store()` in SQLite, the reachability gate in
Postgres — and add the backend-specific tests from `<behavior>`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied keep-set -> SQL statement | A caller-controlled list of ids becomes part of a DELETE predicate |
| interruption point -> stored thread contents | A crash, cancellation or backend failure can land between any two storage operations |
| application-layer policy -> storage adapter | The decision about which Waypoints are protected crosses from the application layer into the adapter as data |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-43 | Denial of Service | destruction of a protected Waypoint by an interrupted prune | critical | mitigate | The primitive never removes an id present in `keep`, so no interval exists during which a protected Waypoint is absent. Proven by the monotone/idempotent/convergent contract functions, and by the fault-injection acceptance test in plan 22-14 |
| T-22-44 | Tampering | SQL injection through `thread_id` or a `keep` element | high | mitigate | Every id is a bound parameter in both overrides; a structural check asserts no statement is built by interpolation, and a metacharacter round-trip test per backend proves ids are treated as data |
