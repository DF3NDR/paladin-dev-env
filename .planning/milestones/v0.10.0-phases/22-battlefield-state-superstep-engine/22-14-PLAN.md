<objective>
Close the remaining half of gap G-22-2 (blocker): rebuild retention on the safe primitive and
prove it under injected failure.

Plan 22-13 added `WaypointPort::prune_thread`, which never touches an id in the keep-set. This
plan rewrites the retention routine on top of it — removing the delete-then-resave sequence
entirely — moves the definition of "protected" into the application layer and passes it into
prune rather than recomputing it inside the adapter (X-01), and adds the fault-injection
acceptance test the gap requires: fail the backend part-way through a prune, then assert the
protected Waypoints still load, the thread still resumes on a real engine, and a re-run converges.

Purpose: the invariant this program is built on is that a crashed process resumes exactly where
it stopped. A retention routine whose crash window destroys the checkpoint resume depends on
inverts it. After this plan the window does not exist, and a test proves it rather than a comment
asserting it.
Output: a keep-set-driven prune, one application-layer definition of protected, a fault-injection
acceptance test, and the invariant written into the requirement text.
</objective>

  <name>Task 1: Rewrite prune on the keep-set primitive and move the protected-set definition up a layer</name>
  <files>crates/paladin-storage/src/waypoint/retention.rs, crates/paladin-storage/src/waypoint/mod.rs, src/application/services/waypoint_retention.rs, src/application/services/mod.rs, src/config/waypoint_retention.rs, .project/v0.10.0/01-battlefield-state-and-execution-engine.md</files>
  <behavior>
Every one of the eight tests already in `retention.rs` is a behavioral guarantee that must still
hold after the rewrite. Adapt each to the new signature first, watch the suite fail against the
not-yet-rewritten body, then implement. Do not weaken any of them:

- both bounds unset removes nothing and does not read the port at all;
- a thread holding one Waypoint is untouched under every bound combination;
- a count bound leaves exactly the newest N, including the latest;
- an age bound never removes the newest Waypoint even when it is older than the bound;
- an age bound removes an old non-latest Waypoint;
- an AwaitingInput Waypoint survives both bounds together, while something else in the same
  over-bound zone is still removed;
- running the same prune twice removes nothing the second time;
- the report carries per-thread removal counts, with an untouched thread reading zero.

Add these, which the previous shape could not express:

- the keep-set handed to the port always contains the thread's latest id and every AwaitingInput
  id, asserted by capturing the keep-set through a recording port double rather than inferred
  from the after-state;
- prune issues exactly one keep-set call per thread that has something to remove, and no call at
  all for a thread that does not;
- prune never calls the whole-thread delete, asserted through the same recording double.

And in the application-layer service:

- the protected set for a thread is exactly its latest id plus every AwaitingInput id, over a
  fixture containing both, neither, and each alone;
- the service passes the configured bounds through unchanged and returns the routine's report.
  </behavior>
  <action>
Rewrite `prune` in `crates/paladin-storage/src/waypoint/retention.rs` around two changes.

First, it is handed the protected set instead of deriving it. Give it a parameter through which
the caller supplies, for a given thread and that thread's history summaries, the set of ids that
must never be deleted — a borrowed function or a small trait object, whichever reads better
against this codebase's conventions; either keeps the adapter free of any notion of what
protected means. Everything the routine does with that set is mechanical: union it with whatever
survives the configured bounds, and that union is the keep-set.

Second, the deletions go through the port's keep-set primitive. For each thread with something to
remove, make exactly one call passing the keep-set. Delete the whole-thread-then-resave sequence
— the enumeration of survivors, the whole-thread delete, and the resave loop all go. There is no
longer any interval during which a protected Waypoint does not exist, because nothing removes it
in the first place.

Rewrite the module doc accordingly. Its current "Mechanism" section explains the composition it
used because no per-waypoint primitive existed; that is now false and actively misleading. Replace
it with the invariant: prune is monotone and idempotent, the keep-set is intact under any crash
or backend failure, a re-run converges, and retention is best-effort reclamation where extra
survivors are acceptable and a lost protected Waypoint never is. Also correct the doc's claim
that the routine enforces the latest and AwaitingInput exclusions as its own invariants — after
this change it enforces whatever it is handed, and the exclusions are guaranteed one layer up.
Point at that layer by name.

Then create `src/application/services/waypoint_retention.rs`, declared in
`src/application/services/mod.rs` alongside its siblings. It holds the one definition of
protected in the system — the thread's latest Waypoint plus every Waypoint whose status is
AwaitingInput — and a service that owns an `Arc<dyn WaypointPort>` and the existing
`WaypointRetentionConfig`, and drives the routine with that definition.

Rustdoc the definition with the two classes that do not exist in the tree yet, naming them as
seams rather than leaving them silently absent: a Waypoint referenced by an unresolved Parley,
and a Waypoint pinned by an active fork lineage in the Chronicle. Name the phase that introduces
each. Do not fabricate a field, a flag or a stub type for either — the point is that the next
author extends this one function instead of discovering the omission from a data-loss report.

Update the doc comment in `src/config/waypoint_retention.rs` so it points at the service as the
entry point rather than at the routine directly.

Finally amend `.project/v0.10.0/01-battlefield-state-and-execution-engine.md` beside ENG-FR-18,
adding the invariant as requirement text rather than leaving it only in rustdoc: pruning is
monotone and idempotent; under any crash or backend failure the keep-set is intact and a re-run
converges; retention is best-effort reclamation where extra surviving Waypoints are acceptable
and a lost protected Waypoint is not. Keep the existing ENG-FR-18 sentence intact and extend it
in the file's established voice.
  </action>

<task type="auto" tdd="true">
  <name>Task 2: Fault-injection and cancellation acceptance test</name>
  <files>tests/integration/waypoint_retention_fault_injection_test.rs, Cargo.toml</files>
  <behavior>
This is the test the gap asks for, and its assertions are the whole point of the fix.

Part A — injected backend failure on the port's provided prune path:
- Build a decorating `WaypointPort` that wraps `InMemoryWaypointStore`, delegates every method,
  and makes the delete-one primitive return a backend error after the first N successful calls.
  Deliberately do not override the keep-set prune on the decorator, so the call takes the port's
  provided implementation and the injected failure lands part-way through a real prune.
- Seed a thread with a mix of Waypoints including a completed latest and an AwaitingInput one
  that both bounds would otherwise want to remove.
- Run the retention service and expect it to surface the injected error.
- Assert the thread's latest Waypoint still loads and is the same Waypoint as before the prune.
- Assert the AwaitingInput Waypoint still loads by id, with its payload byte-identical.
- Assert what remains is a superset of the keep-set — extra survivors are acceptable, a missing
  protected Waypoint is not.
- Re-run with the fault injection disabled and assert convergence: exactly the keep-set remains,
  and a third run removes nothing.
- Sweep N across the whole range of delete counts the fixture can produce, so the failure is
  injected at every position rather than one arbitrary one.

Part B — resume after an interrupted prune:
- Run a small multi-superstep graph on a real engine against a store until it has several
  Waypoints, interrupt a prune as in Part A, then construct a fresh engine over the same backend
  and thread id and resume.
- Assert the run completes and its final Battlefield equals an uninterrupted control run's. This
  is the assertion that ties retention back to the program invariant: an interrupted prune must
  not have cost the thread its ability to resume.

Part C — cancellation against the transactional SQLite override:
- Seed a SQLite-backed thread, spawn the prune, abort the task after a varying short delay, and
  assert on every iteration that every id in the keep-set still loads. Whether the abort lands
  before or after the transaction commits is a race, and the assertion is chosen deliberately to
  hold either way — an aborted prune leaves either the pre-call state or the post-call state, and
  the keep-set is intact in both.
- Then run the prune to completion and assert convergence to exactly the keep-set.
  </behavior>
  <action>
Create `tests/integration/waypoint_retention_fault_injection_test.rs` and register it as its own
`[[test]]` target in the root `Cargo.toml`, following the `e2e_crash_resume` entry exactly.

Implement the three parts described in `<behavior>`. Keep the fault-injection decorator inside
this test file rather than in shipped code: it exists to prove a property, not to be a reusable
adapter.

For Part B, reuse the graph-construction approach from `tests/integration/e2e_crash_resume_test.rs`
rather than inventing a new fixture shape — a small graph is enough, the point is the resume, not
the graph. Read that file's fixture builder first and follow its conventions for schema, nodes
and limits.

For Part C, use the SQLite backend as that module's own tests do, so a real transaction is
exercised rather than the provided implementation. Bound the abort-delay sweep so the whole test
stays well under a second; this is an invariant check, not a soak test.

Give every assertion a message naming the invariant it protects, so a future failure reads as a
contract violation rather than a line number.
  </action>
