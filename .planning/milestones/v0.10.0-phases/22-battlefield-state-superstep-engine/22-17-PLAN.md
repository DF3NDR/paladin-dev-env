  <what-built>
Three gap fixes, delivered by plans 22-12 through 22-16:

- **G-22-1** — a `postgres-integration` job in `.github/workflows/ci.yml`. It brings up the
  `postgres-test` service, waits for an anchored healthy status, asserts the server accepts
  connections, runs the waypoint contract suite single-threaded with the connection URL set, and
  then fails the job on two independent conditions: the suite's early-return marker appearing in
  the log, or the reported passed-count falling below the number of test functions the module
  declares. The Makefile runner was aligned to the same flags.

- **G-22-2** — `WaypointPort` gained a delete-one primitive and a `prune_thread(thread, keep)`
  method with a safe provided implementation, overridden transactionally by SQLite and Postgres
  and atomically by the in-memory store, all proven against the same shared contract suite.
  The retention routine was rebuilt on it: the whole-thread delete and resave loop are gone, and
  the definition of a protected Waypoint moved into an application-layer service that passes the
  protected set into the routine. A fault-injection acceptance test fails the backend at every
  delete position and asserts the latest and AwaitingInput Waypoints still load, the thread still
  resumes on a fresh engine to the control run's final state, and a re-run converges.

- **G-22-3** — `WarGraph::validate` now computes the eligible set from entry plus explicitly
  marked dynamic targets, to a fixed point, and rejects every declared node outside it in one
  error listing all offenders. Self-loops on reachable nodes stay legal. The fix is test-first in
  git history. The fixture audit classified every strandedness-adjacent fixture in the tree.
  </what-built>
  <how-to-verify>
**1. The CI run — the item that cannot be checked locally.**

Push the branch if it is not pushed, then find the run and read the job:

- `gh run list --workflow=ci.yml --branch "$(git rev-parse --abbrev-ref HEAD)" --limit 5`
- `gh run view <run-id>` and confirm a job named for the Postgres waypoint contract suite is
  present and green.
- `gh run view <run-id> --log --job <job-id>` and confirm four things in the log, in order:
  the container reported healthy; the connectivity assertion succeeded; the cargo run reported
  `test result: ok` with a passed-count equal to the number of `#[tokio::test]` functions in
  `crates/paladin-storage/src/waypoint/postgres.rs`; and the early-return detection step reported
  that the live server was exercised.

A green job whose log shows a passed-count of zero, or shows the early-return marker, is the
original defect in a new costume — reject it. This is the single question gap G-22-1 turns on:
did the suite run against a real server, or did something merely report success.

**2. The readiness defect's disposition — the one open decision.**

Read the finding in `22-deferred-items.md` and run its reproduction:
`cargo test -p paladin-battalion --lib engine::superstep -- --ignored --nocapture`

The mechanism: readiness requires every incoming edge to be resolved, and a node's own self-edge
is unresolved until that node has executed, so a node that is both self-looping and fed by an
upstream edge can never take its first turn — and the run still reports completion. It is the
same truthful-outcome violation as BUG-02, reached differently, and reachability validation
cannot catch it because such a node is statically reachable. The crash-resume fixture's
looping-node arrangement exists because of this rule, which is why that arrangement was corrected
in its comment rather than removed.

Choose one and say which:
- register it in the program overview's defect register alongside BUG-01 and BUG-02, and assign
  it to the phase that owns routing and frontier work;
- register it and schedule it elsewhere;
- close it with a reason.

Nothing under `.project/` was edited by the executor — registering it is a developer act.

**3. The retention design's one degree of freedom.**

The gap's fix design said to rewrite the routine on the new primitive and to pass the keep-set in
rather than recompute it in the adapter. That was implemented as: the routine stays in the
storage module and takes the protected set as an argument; the application-layer service holds
the single definition of protected — the thread's latest plus every AwaitingInput Waypoint — with
the Parley-referenced and fork-lineage-pinned classes named as seams for their owning phases.

Read `src/application/services/waypoint_retention.rs` and the rewritten module doc on
`crates/paladin-storage/src/waypoint/retention.rs` and confirm that is the shape you intended,
or say what it should be instead.
