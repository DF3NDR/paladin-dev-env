# Phase 22.1 Plan 01: Cycle-bootstrap starvation fix (BUG-03 / ENG-FR-06a) Summary

**Starvation-release fallback pass in `compute_next_vanguard` fixes cycle-bootstrap starvation (BUG-03) test-first, with both reproductions landing red-then-green and the defect registered in the `.project/v0.10.0` trio.**

## Accomplishments

- Fixed BUG-03: `Frontier::is_ready` required every incoming edge resolved before scheduling a node, so a cycle's own back-edge (which can only resolve after the cycle's own first bootstrap execution) permanently starved that node — the run reported `Completed` over a node that never ran.
- Added a third fallback pass, `starved_release`, to `compute_next_vanguard`: engaged ONLY when both the normal-ready pass and the `defer`-release pass return empty, it releases a node holding at least one fresh fired incoming edge whose every remaining unresolved edge is `Pending` from a live source that has never executed.
- Factored `Frontier::node_edge_summary`, a shared per-node edge-resolution helper both `is_ready` and `starved_release` call, so the fresh-fire / pending-from-live classification is computed once, not re-derived.
- Un-ignored the existing self-loop reproduction (`self_looping_node_fed_by_upstream_edge_can_never_take_first_turn`) with zero assertion/fixture changes, and added a new general-shape reproduction (`cycle_node_fed_from_outside_the_cycle_takes_its_first_turn`, `entry -> a -> b -> a`) — both committed RED, then GREEN in a separate commit.
- Confirmed `diamond_join_executes_target_exactly_once` and `false_branch_is_proven_not_firing_and_join_still_runs_once` (ENG-FR-06 join-semantics canaries) are byte-identical and still pass — the starvation release does not relax normal join semantics.
- Registered BUG-03 and ENG-FR-06a in `00-program-overview.md` §7, `08-traceability-matrix.md`, and `01-battlefield-state-and-execution-engine.md`, mirroring BUG-02's pre-release classification (no `MIGRATION.md`/`CHANGELOG.md` entry, since the `engine` module is absent at the `v0.9.0` tag).

## Decisions Made

- Ordering of `compute_next_vanguard`'s three passes is normal-ready -> starvation-release -> defer-release (not starvation-after-defer), so a `defer`-marked aggregator still waits for a released cycle node to run first, per CONTEXT.md's recommended ordering (D-03).
- `node_edge_summary` returns `pending_from_live: Vec<usize>` (the unresolved-from-live-source edge indices) rather than a plain `any_pending: bool`, since `starved_release` needs the actual edge indices to check each one's source against `last_executed` — `is_ready` only needs `pending_from_live.is_empty()`.
- No new `Frontier` field was introduced; confirmed via `grep -c 'struct Frontier'` and a field-count check per the plan's acceptance criteria — `edge_state`, `dead`, `last_executed`, `incoming` unchanged.
