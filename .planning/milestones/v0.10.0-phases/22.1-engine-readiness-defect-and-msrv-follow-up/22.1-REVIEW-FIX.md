### CR-01: `WarGraph::fingerprint()`'s canonical byte encoding is not collision-free

**Files modified:** `crates/paladin-battalion/src/engine/graph.rs`, `crates/paladin-core/src/platform/container/waypoint.rs`, `MIGRATION.md`
**Commit:** `02eaedf179cde0fa6213e13a940a01fdfcd597cd`
**Applied fix:** Replaced the delimiter-separated (`|`, `-`, `:`) canonical byte encoding in `WarGraph::fingerprint()` with a length-prefixed encoding (new private `push_field` helper: an 8-byte little-endian length prefix before each variable-length field's bytes), eliminating the byte-split ambiguity the review demonstrated (two nodes `"a"`+`"b"` vs. one node `"a|nf|b"`; edge `"a"->"b-c"` vs. edge `"a-b"->"c"`). Bumped `GRAPH_FINGERPRINT_VERSION` from `"v1"` to `"v2"` in `paladin-core`'s `waypoint.rs` (plus its rustdoc and the `starts_with("v2:")` unit test) so every previously stored fingerprint is recognized as a stale version-tag mismatch on `resume` rather than silently reinterpreted. Re-pinned `fingerprint_golden_hex_pins_canonical_bytes` and `fingerprint_is_deterministic_across_calls`'s golden hex literals to the new encoding's actual output (determined by running the test suite and reading back the computed value, not guessed). Added two new regression tests, `fingerprint_distinguishes_length_prefix_collision_two_nodes_vs_one` and `fingerprint_distinguishes_length_prefix_collision_edge_split`, asserting the two constructed collisions from the review now produce *different* fingerprints. Searched the rest of the workspace (`paladin-storage`'s `contract_tests.rs`/backend adapters, `tests/integration/e2e_crash_resume_test.rs`) for any other pinned fingerprint bytes or "v1" version-string dependency; found none — all other call sites use `GraphFingerprint::from_canonical_bytes` with arbitrary fixture bytes, unaffected by the encoding change. Updated `MIGRATION.md` §9.4's "Persisted `GraphFingerprint` format" paragraph to describe the `v1` -> `v2` bump and why.

### WR-01: `.expect()` in spawned superstep task violates the "no unwrap/expect/panic in library code" convention

**Files modified:** `crates/paladin-battalion/src/engine/superstep.rs`
**Commit:** `38abd07fc591eb0f0b699a2193a7aa07aa8ec1f1`
**Applied fix:** Replaced `sem.acquire_owned().await.expect("semaphore is never closed")` with a `match` on the `Result`: the `Ok(_permit)` arm keeps the existing node-execution logic unchanged (same permit scope as before), and the new `Err(_)` arm reports the failure through the existing `NodeRunOutcome::Failed(NodeError(...))` plumbing instead of panicking inside the detached `tokio::spawn`ed task, consistent with how a node's own execution error is already reported. No new regression test was added: the semaphore is constructed fresh, locally, and never exposed for external `.close()`-ing anywhere in the current call graph, so the error path is provably unreachable through any public API today — there is no way to exercise it without an invasive, out-of-scope refactor to inject a closed semaphore. The fix removes the latent panic risk itself (the review's stated concern) even without a dedicated unit test for the currently-unreachable branch.
