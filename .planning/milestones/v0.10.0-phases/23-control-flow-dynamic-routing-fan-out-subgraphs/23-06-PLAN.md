<objective>
Make a Muster survive a crash: persist intra-superstep progress Waypoints carrying the completed
tasks' unmerged deltas, and make resume re-enter the muster running only the unfinished tasks —
then register the ENG-FR-11 clarification that makes this legal.

Purpose: without this, a five-task Muster interrupted after two tasks re-runs all five on resume,
which for LLM-backed workers is both expensive and non-idempotent. This is the only new
per-superstep persistence semantics in the phase, and the only place a partially merged Battlefield
could silently appear.

Output: `MusterProgress` on the `Waypoint`, a resume path that runs exactly the unfinished tasks,
three-backend contract coverage, and PRD 01's ENG-FR-11 note.
</objective>

  <decision>Freeze the mid-muster progress-Waypoint payload contract (`MusterProgress`) before it becomes a stored format</decision>
  <context>
CONTEXT.md D-14 rates this decision **one-way after v0.10.0 ships**: `muster_progress` becomes part
of a persisted Waypoint payload that SQLite and Postgres deployments will hold, so changing its
shape after release requires a data migration for every stored thread, not a refactor. It is cheap
right now only because no Waypoint carrying it exists outside this branch. CONTEXT.md was gathered
in `--auto` mode, so this door was auto-selected on the recommended default rather than chosen by a
human — this checkpoint is the first human look at it.

The choice also decides how a resumed muster stays idempotent. Storing unmerged per-task deltas is
what lets the engine merge each delta exactly once; storing a progressively merged Battlefield
instead would make a resume double-merge and would break snapshot isolation for the sibling tasks
still running in that superstep.
  </context>
  <options>
    <option id="option-a">
      <name>D-14 as written — one progress Waypoint per completed task, carrying unmerged deltas keyed by task_key, at the same superstep index with status Running</name>
      <pros>Satisfies CF-FR-12 and PRD §4 test-plan item 5 ("2/5 done, resume, exactly 3 re-run"); preserves ENG-FR-05 snapshot isolation because the stored Battlefield never changes mid-muster; reuses the proven additive `#[serde(default)]` field pattern with no SQL migration; a resumed run merges each delta exactly once.</pros>
      <cons>Up to `max_muster_tasks` extra Waypoint writes per muster superstep (100 by default); ENG-FR-11's "one Waypoint per superstep" wording needs an explicit clarification note; the payload shape is a stored contract from v0.10.0 onward.</cons>
    </option>
    <option id="option-b">
      <name>Superstep-end checkpointing only — no intra-superstep Waypoints</name>

      <cons>Violates CF-FR-12 outright and fails PRD §4 item 5: a crash mid-muster re-runs every task, including the expensive ones that already succeeded. Rejected in CONTEXT.md D-14.</cons>
    </option>
    <option id="option-c">
      <name>One task per superstep — each worker gets its own superstep and the existing per-superstep Waypoint</name>
      <pros>No new field at all; resume falls out of the existing machinery.</pros>
      <cons>Violates CF-FR-10's "all tasks of one Muster execute in the same superstep, concurrently" — it serialises the fan-out and removes the parallelism Muster exists to provide. Rejected in CONTEXT.md D-14.</cons>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| engine -> `WaypointPort` backend | A progress Waypoint's payload — including every completed worker's delta, which may contain model output placed there by the workflow — is written to durable storage on each task completion. |
| stored Waypoint -> resumed run | A persisted `muster_progress` record drives which tasks a resumed run skips; a wrong or tampered record means work silently not done. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-23-23 | Tampering (of a resumed run's completeness) | `muster_progress`-driven resume | high | mitigate | The resumed run's final Battlefield is asserted equal to the uninterrupted control run's, and the recording port is asserted to show exactly the unfinished-task count — the same control-run equality property E2E-1 uses, applied to the mid-muster path. |
| T-23-24 | Tampering (double-merged state) | incremental merge temptation | high | mitigate | Deltas are held unmerged in `muster_progress` and merged exactly once when all tasks resolve; `progress_waypoint_battlefield_equals_the_superstep_start_snapshot` asserts the stored Battlefield never changes mid-muster, so a resume cannot merge the same delta twice. |
| T-23-25 | Information Disclosure | progress Waypoints persisting worker deltas | medium | accept | A worker delta may contain model output, exactly as a superstep-complete Waypoint's Battlefield already may — `MIGRATION.md` M-B-04 already documents that Waypoint snapshots may contain raw prompts and outputs, and `WaypointRetentionConfig` is the existing control. Progress Waypoints add frequency, not a new class of stored content. Recorded, not separately mitigated. |
| T-23-26 | Denial of Service | unbounded progress-Waypoint writes | medium | mitigate | Cadence is one write per completed task, bounded by `max_muster_tasks` (default 100), which Plan 23-05 enforces before any task starts — so the write count per muster superstep is bounded by construction. |
| T-23-27 | Repudiation | ENG-FR-11's "one Waypoint per superstep" contract | low | mitigate | The clarification note records precisely which invariant still holds (one superstep-complete Waypoint) and which is additive (progress Waypoints inside a muster superstep), so a future auditor is not left reconciling the code against stale FR text. |
| T-23-SC | Tampering | npm/pip/cargo installs | high | accept | This plan installs no packages, modifies no manifest, and adds no SQL migration; `23-RESEARCH.md` §Package Legitimacy Audit records zero external package additions for the phase. |
</threat_model>
