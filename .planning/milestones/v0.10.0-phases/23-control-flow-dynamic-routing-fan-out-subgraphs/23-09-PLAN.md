<objective>
Give an embedded child run its own durable identity: a derived, injective child `ThreadId`, an
additive `checkpoint_ns` record on the Waypoint, resume-mid-child with zero re-execution, and the
`restart_on_resume` opt-out — proven end-to-end by the CF-FR-17 Formation-inside-Campaign test.

Purpose: CF-FR-15 is what makes subgraphs durable rather than merely compositional, and the
identity encoding is the one place this phase can reintroduce the exact defect class 22.1's CR-01
already found and fixed once. `NodeId` accepts any non-empty string, so a naive delimiter join is
demonstrably collidable.

Output: an injective child-thread derivation with an adversarial collision test, `checkpoint_ns`
round-tripping through all three backends, resume-mid-child proven, and PRD acceptance criterion 4
green.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>Freeze the child-thread identity encoding and the `checkpoint_ns` Waypoint field before either becomes a stored contract</decision>
  <context>
CONTEXT.md D-20 rates this decision **one-way after v0.10.0 ships**: derived child `ThreadId`s and
the `checkpoint_ns` field both become persisted contracts. Every stored child thread is addressed by
the id this encoding produces, so changing the encoding afterwards orphans every existing child
chain — a data migration across every SQLite and Postgres deployment, not a refactor. CONTEXT.md was
gathered in `--auto` mode, so this door was auto-selected on the recommended default rather than
chosen by a human; this checkpoint is the first human look at it.

The encoding is also a correctness question, not only a compatibility one. `NodeId` has NO charset
restriction (only non-emptiness) and `ThreadId::new` rejects only whitespace and over-256-byte ids,
so a `format!("{parent}/{node}")`-style join is collidable by construction: node `"a/b"` under
parent thread `"t"` produces the same id as node `"b"` under parent thread `"t/a"`. Phase 22.1's
CR-01 found exactly this defect class in the fingerprint encoding and fixed it with a
length-prefixed format; this is the same hazard in a second place.
  </context>
  <options>
    <option id="option-a">
      <name>D-20 as written — length-prefixed (or escaped) injective derivation, plus an additive `#[serde(default)] checkpoint_ns` record, with `latest(child_thread)` unchanged</name>
      <pros>Provably injective, and provable by an adversarial test rather than by inspection; reuses the `push_field` encoding CR-01 already validated; needs no `WaypointPort` method change, no SQL migration and no retention change; resume-mid-child falls out of the child having a genuinely distinct thread.</pros>
      <cons>Child thread ids are opaque rather than human-readable in a database browser (`checkpoint_ns` is the readable record that compensates); the derivation and the field are both stored contracts from v0.10.0 onward; the 256-byte `ThreadId` cap bounds nesting depth for very long node names.</cons>
    </option>
    <option id="option-b">
      <name>Bare delimiter join (`parent/node_id`)</name>
      <pros>Human-readable ids; trivial to implement and to reason about at a glance.</pros>
      <cons>Demonstrably collidable given `NodeId`'s unrestricted charset — two distinct (parent, node) pairs can map to one child thread, silently merging two subgraph runs' checkpoint histories. This is the exact defect CR-01 fixed; reintroducing it knowingly is not defensible.</cons>
    </option>
    <option id="option-c">
      <name>Keep the parent's `ThreadId` and disambiguate child Waypoints by `checkpoint_ns` alone</name>
      <pros>No new identity concept; one thread per run, which reads simply.</pros>
      <cons>`WaypointPort::latest(thread)` has no namespace parameter, so a parent's `latest` would return a child's Waypoint and resume would break; making it work requires a `WaypointPort` method change D-20 explicitly forbids (RESEARCH Pitfall 6).</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| (parent thread, node id) -> derived child `ThreadId` | An author-controlled `NodeId` with no charset restriction is combined with a thread id to address durable storage; the mapping must be injective or two runs' histories merge. |
| child Waypoints -> shared `WaypointPort` backend | Parent and child rows live in the same store, distinguished only by thread id; a collision is a silent cross-run data mix. |
| stored child chain -> resumed run | A resumed parent trusts `latest(child_thread)` to identify where the child stopped. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-23-36 | Tampering (delimiter collision in a new identity encoding) | the child-`ThreadId` derivation | high | mitigate | Length-prefixed or escaped segment encoding mirroring `push_field`, never a bare delimiter join; proven by `child_thread_derivation_is_injective_under_adversarial_names`, which constructs the exact colliding pair CR-01 identified and asserts the ids differ. `NodeId`'s unrestricted charset is what makes this a real attack surface rather than a theoretical one. |
| T-23-37 | Information Disclosure | one workflow's child checkpoints readable under another's thread | high | mitigate | Isolation comes from the distinct derived thread id, not from `checkpoint_ns`; `latest_on_the_child_thread_returns_the_childs_own_waypoint` asserts parent and child histories do not alias, and no lookup filters a parent's history by namespace (RESEARCH Pitfall 6). |
| T-23-38 | Tampering (of a resumed child's completeness) | resume-mid-child | high | mitigate | The resumed run's already-completed child node is asserted not to re-execute AND the final parent Battlefield is asserted equal to the uninterrupted control run's — the same two-sided property E2E-1 uses, applied to the nested path. |
