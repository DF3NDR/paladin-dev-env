<objective>
Put a port between the HTTP surface and the engine. `paladin-web` must be able to trigger a resume
without ever naming `paladin-battalion`, so the trigger becomes an input port, the facade implements
it, and the continuation runs in the background bounded by graceful shutdown.

Purpose: HITL-05's server-side half and the D-25/D-26 architecture that lets Phase 27 swap the
in-process background task and the code registry for a worker pool and a `WarGraphDoc` registry
behind the same port.

Output: `ParleyPort`, the facade adapter with its `GraphRegistry`, and `WaypointStoreConfig`.
</objective>

`registry.rs` holds `GraphRegistry`: a `GraphFingerprint`-keyed map of registered `WarGraph`s with a
register method and a lookup that returns `None` for an unknown fingerprint (D-26). Phase 27's
`WarGraphDoc`/assistant registry replaces this lookup behind the same port, so keep the surface
minimal and document that seam.

`adapter.rs` implements `ParleyPort` over a `WarEngine`, a `GraphRegistry` and a
`ShutdownCoordinator`. On `resume_with`: load the thread's latest Waypoint (absent means
`ThreadNotFound`), resolve its `GraphFingerprint` through the registry (absent means
`GraphNotRegistered` — never fall back to a default or nearest graph), then run
`WarEngine::resume_with`'s validation path synchronously so every typed error surfaces from this
call with nothing persisted and the thread still suspended (D-10, D-25). Only after validation
succeeds, register with the `ShutdownCoordinator` and `tokio::spawn` the continuation holding the
returned `RunGuard`, then return `ResumeAccepted` immediately.

This is the same validate-then-spawn-then-return shape `agent_controller.rs`'s `enqueue_job`
already ships; follow it rather than inventing a second pattern. Map every `EngineError` the
validation path can produce onto its `ParleyError` counterpart explicitly — a catch-all mapping that
collapses distinct validation failures into one variant would erase the 400-versus-409 distinction
plan 24-11 depends on.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP caller -> `ParleyPort::resume_with` | Untrusted request data reaches the engine through this single method |
| thread fingerprint -> `GraphRegistry` | The graph a continuation runs is selected by a value read from storage |
| accepted request -> background task | Work continues after the requesting connection is gone |
| config -> database connection string | A postgres url must not be serialised into config or logs |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-24-39 | Tampering | A continuation running against the wrong graph | high | mitigate | The graph is resolved strictly by the `GraphFingerprint` on the thread's latest Waypoint; an unregistered fingerprint is `GraphNotRegistered` with no fallback, pinned by a test |
| T-24-40 | Denial of Service | An unbounded background continuation surviving shutdown | high | mitigate | The spawned task registers with the `ShutdownCoordinator` and holds a `RunGuard`, so it is bounded by the same engine limits as any run and by the grace window |
| T-24-41 | Information Disclosure | A postgres connection string leaking through a serialised config or debug print | high | mitigate | The postgres backend variant carries the NAME of the env var holding the url, never the url; `validate()` resolves it at startup without storing it on the config |
| T-24-42 | Elevation of Privilege | A validation failure being accepted and then failing silently in the background | high | mitigate | Validation is synchronous and total before the spawn; an error returns from the call with nothing persisted and the thread still suspended |
| T-24-43 | Repudiation | Distinct validation failures collapsing into one error, hiding why a request was rejected | medium | mitigate | Every `EngineError` validation variant maps to a distinct `ParleyError` variant, with a test exercising every mapping, so plan 24-11 can render the 400-versus-409 distinction |
| T-24-SC | Tampering | package-manager installs | low | accept | No new dependency line is added to `paladin-ports` or the root crate |
</threat_model>
