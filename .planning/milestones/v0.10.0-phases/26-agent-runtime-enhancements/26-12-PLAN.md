<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model output → `extract_json` → a parsed value | Fully model-controlled text crosses into a parser whose result drives typed program flow |
| model output → the repair re-prompt | The offending output is fed straight back into the next prompt |
| caller-authored schema → `shape_check` / `render_instruction_block` | Caller data drives validation and prompt text |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-12 | Denial of Service | an unbounded repair loop | medium | mitigate | `max_repair_attempts` defaults to 1 and is enforced by the driver, so a model that never conforms costs at most `1 + max_repair_attempts` calls; `zero_repair_attempts_means_one_call` and `exhaustion_returns_the_typed_error_with_raw_preserved` pin both ends (D-26, RT-FR-18) |
| T-26-40 | Tampering | the repair re-prompt echoing model output as an instruction | medium | mitigate | The offending output is re-inserted as **quoted data** inside the repair prompt with the parse error, in the same delimited-section discipline the phase uses for recalled memory and tool errors (D-41); the wording is written once in the driver rather than at each call site |
| T-26-41 | Tampering | over-trusting a partial shape check | medium | mitigate | `shape_check`'s rustdoc enumerates the seven keywords it enforces **and** states that anything else in a schema is ignored, so a caller relying on `minLength` learns it from the docs rather than from a production surprise; the full-validator path is a recorded Deferred Idea rather than an unstated gap (D-30) |
| T-26-42 | Denial of Service | a deeply nested schema or value in `shape_check` | low | mitigate | `shape_check` recurses over `properties` and `items`; keep the recursion bounded by the schema's own depth and document that schemas are caller-authored, not attacker-authored — the caller is the same process that wrote the type |
| T-26-SC | Tampering | cargo installs (`schemars` promoted to a direct dependency) | high | mitigate | 26-RESEARCH.md's Package Legitimacy Audit records `schemars` as verdict `OK` — crates.io, published 2019, ~12.3M downloads/week, `github.com/GREsau/schemars`, already resolved at `1.2.1` in `Cargo.lock` via `rmcp 2.1.0`. It is pinned to `"1.2"` to reuse that exact resolution, and the `cargo tree -i schemars` count of exactly 2 is an acceptance criterion, so no third version can slip in. No `[ASSUMED]` or `[SUS]` package exists in the audit, so no legitimacy checkpoint is required. |
</threat_model>
