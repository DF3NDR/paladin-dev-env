<objective>
Close verification gap 1: the Redis run-queue attempt counter is off by one. `RUN_QUEUE_CLAIM_LUA`
increments `attempt` unconditionally on every claim, so the very first dequeue of a freshly-enqueued
message reports `attempt = 2` where `InMemoryRunQueue` reports `1`; the nack script double-counts for
the same reason. Three live-CI tests fail on this in the `redis-queue` job, and the same three
assertions abort the `coverage` job with exit 101 before any line-coverage percentage is computed —
one fix closes both.

Purpose: PLAT-02 / PLAT-FR-03. At-least-once redelivery is only meaningful if `attempt` counts
deliveries the way both adapters agree it does; a worker reading `attempt = 2` on a first delivery
mis-reports every run's retry history.

Output: a corrected claim script and nack script in `crates/paladin-storage/src/run_queue/redis.rs`,
an adapter-internal claim marker on the ZSET member, and three Tier-1 guard tests that pin the
semantics without a live server.
</objective>

`QueuedRun { run_id: RunId, thread_id: ThreadId, attempt: u32, enqueued_at: DateTime<Utc> }`
(`crates/paladin-ports/src/output/run_queue_port.rs:55`) — plain `#[derive(Serialize, Deserialize)]`
with **no** `deny_unknown_fields`, so an extra JSON key on the serialised member is ignored on read.
`InMemoryRunQueue` (the semantics of record) increments `attempt` at exactly two sites:
`Inner::reclaim_expired_leases` (lease-expiry redelivery) and `nack`. Its `dequeue` never increments.
Redis key layout (unchanged by this plan): `{prefix}:ready` ZSET member = the serialised `QueuedRun`
JSON, score = microsecond visibility timestamp; `{prefix}:leases` HASH token → the exact member
string; `{prefix}:lease_expiry` ZSET token → expiry.
`redis::Script::invoke_async` already handles `NOSCRIPT` reload — do not hand-roll it.
