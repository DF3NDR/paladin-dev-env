<objective>
Close verification gap 3: the `sdk-clients` CI job. It fails for two independent reasons and would
report a false pass for a third. (1) The TypeScript half never runs — `npm ci` needs a
`package-lock.json` that `scripts/sdk-smoke/` does not ship. (2) The smoke agent is wired to a real,
unauthenticated third-party LLM endpoint, so the submitted run legitimately ends `failed`. (3)
`smoke.py` treats every terminal status as success, so it printed "all checks passed" for that failed
run — the Python half's pass/fail logic does not currently prove a working client round trip at all.

Purpose: PLAT-06 / PLAT-FR-17, D-49. The job's whole point is proving the published spec is complete
enough to generate a client that can drive a run to success; a job that goes green on a failed run
proves nothing.

Output: a hermetic loopback LLM stub and a single shared boot definition, a generator-free HTTP round
trip that proves `completed` locally, a committed lockfile with the generated client installed as a
separate step, and both smoke scripts asserting the exact success status.
</objective>

Provider construction reads the ENVIRONMENT, not the YAML `llm:` section:
`LlmProviderFactory::create("openai")` calls `OpenAIConfig::from_env()`
(`crates/paladin-llm/src/openai/adapter.rs:56-77`), which reads `OPENAI_API_KEY` (must be present and
non-empty) and `OPENAI_BASE_URL` (defaults to the vendor endpoint). Request paths are
`{base_url}/chat/completions` (adapter.rs:441, 481) and `{base_url}/models` (adapter.rs:676).
Response shape the adapter deserialises (adapter.rs:183-205): `{ id: String, model: String,
choices: [ { index: u32, message: { role: String, content: String }, finish_reason: Option<String> } ],
usage: { prompt_tokens: u32, completion_tokens: u32, total_tokens: u32 } }`.
`smoke-config.yml` is read whole by `Settings::load_from_file` (no merge), so every currently-present
top-level key must stay present.
HTTP surface used by the smoke: `GET /v1/assistants` → `{ items: [...] }`; `POST /v1/runs` → 202 with
`run_id`; `GET /v1/runs/{run_id}` → `{ status, error, ... }` with lower-case wire statuses
(`completed`, `failed`, `halted`, `cancelled`).
The CI job already provides Python 3.12 (`actions/setup-python`) and Node 20 (`actions/setup-node`),
and builds `target/debug/paladin-server` with `--features web-server` before calling `run.sh`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI runner → external network | The smoke previously reached a third-party API endpoint from a job that runs on every PR, including forks. |
| npm registry → CI runner | Toolchain packages are fetched and executed during the job. |
| Smoke config → server process | A config file in the repo supplies the credentials and endpoints a booted server uses. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-27-21-01 | Spoofing / Information disclosure | outbound LLM call from CI with a caller-visible config | high | mitigate | The provider base URL is a loopback stub started by the job itself; no request leaves the runner and no real credential is needed or accepted. |
| T-27-21-SC | Tampering | npm/pip installs in the job | high | mitigate | A committed `package-lock.json` makes `npm ci` an integrity-pinned install (an improvement on the current unpinned state); no new package is introduced — `typescript` and `@types/node` are the already-present devDependencies from 27-18, and the only other install is the locally generated client from `target/`, never a registry package. `python3 -m pip install target/sdk/python` likewise installs a locally built tree. Any future NEW package here requires the RESEARCH.md Package Legitimacy Gate first. |
| T-27-21-02 | Repudiation | a green job that proved nothing | high | mitigate | Success requires the exact `completed` status; the failure path prints the status and the run error; a self-test proves the decision function itself. |
| T-27-21-03 | Information disclosure | a real credential leaking through the committed config | medium | mitigate | The config's key is a fixed placeholder and the endpoint is loopback, so a copied config cannot carry or exercise a real secret. |
| T-27-21-04 | Denial of service | stub or server left running after a failure | low | mitigate | Both processes are started and stopped by one library with an `EXIT` trap in every caller. |
</threat_model>
