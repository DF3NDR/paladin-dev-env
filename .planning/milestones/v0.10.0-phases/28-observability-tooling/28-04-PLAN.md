full-fidelity replay (28-11) and what give the execution overlay exact fired/evaluated edge sets
(28-10).

Target trait (D-17, verbatim):
`#[async_trait] pub trait RunTracePort: Send + Sync {
  async fn append(&self, records: &[TraceRecord]) -> Result<(), RunTraceError>;
  async fn read(&self, thread: &ThreadId, after_seq: u64, limit: u32) -> Result<Vec<TraceRecord>, RunTraceError>;
  async fn prune_thread(&self, thread: &ThreadId, before_superstep: u64) -> Result<u64, RunTraceError>;
}`

Migration numbering (28-RESEARCH.md Q3, verified): both `migrations/sqlite/` and
`migrations/postgres/` currently end at `005_create_webhook_deliveries_table.sql`; the next free
number is `006` for both. Mechanism, identical across all five existing adapters
(`waypoint/sqlite.rs:95`, `run/sqlite.rs:91`, `assistant/sqlite.rs:74`, `webhook/sqlite.rs:58`,
`run_schedule/sqlite.rs:61`):
`static MIGRATOR: sqlx::migrate::Migrator = sqlx::migrate!("migrations/sqlite");` then
`MIGRATOR.run(&pool).await?` on adapter construction.

Retention pitfall (28-RESEARCH.md Q14 / Pitfall 3, load-bearing):
`WaypointRetentionService { port: Arc<dyn WaypointPort>, config: WaypointRetentionConfig }`
(`src/application/services/waypoint_retention.rs:67-98`) is hard-typed to one port, and the free
function `paladin_storage::waypoint::retention::prune(port: &dyn WaypointPort, max_age_days,
max_waypoints_per_thread, protected)` takes `&dyn WaypointPort` directly. Neither can be made generic
over both traits. The sanctioned shape is an additive optional second field plus a small sibling
function — do not reach for a shared supertrait.

Feature gating: no new cargo feature. The SQLite adapter compiles under the always-on `sqlite`
feature; the Postgres adapter under the existing `postgres` feature (D-17).
Docker is unavailable locally (24-CONTEXT D-28) — the Postgres leg is Tier 2, proven only by CI's
`postgres-integration` job.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `TraceRecord` payload → persisted database row | Observability data becomes durable, readable state with its own lifetime. |
| Caller-supplied `ThreadId` → SQL query | An identifier from an untrusted caller reaches the storage layer. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-28-04-01 | Tampering | SQL injection through `thread_id` or `after_seq` | high | mitigate | Every statement uses bound parameters in named `const` SQL blocks; no query string is built by formatting a caller value, asserted by a zero-`format!` check on the adapters. |
| T-28-04-02 | Information disclosure | Long-lived trace rows outliving their run's retention window | medium | mitigate | `prune_thread` joined to the existing Waypoint retention routine with the same bounds; no `run_traces`-specific tunable that could be set to never expire (D-17). |
| T-28-04-03 | Tampering | Reading a row written by a newer, unknown schema | medium | mitigate | Per-row `schema_version` and a typed `UnsupportedSchemaVersion { found }` on read (X-04). |
| T-28-04-04 | Denial of service | Unbounded `read` returning a whole run in one response | medium | mitigate | `limit` is a required parameter; the replay consumer (28-11) paginates by `after_seq`. |
| T-28-04-05 | Information disclosure | `ThreadId` treated as an authorization boundary by a caller | low | accept | Documented in the module docs exactly as `waypoint_port.rs` documents it; authorization is the web layer's job. |
</threat_model>
