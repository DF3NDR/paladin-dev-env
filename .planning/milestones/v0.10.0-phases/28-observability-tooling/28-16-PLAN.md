<interfaces>
The three integration tests and their acceptance bars (program overview §6):
- `tests/integration/e2e_crash_resume_test.rs` — a six-node cyclic workflow with a bounded loop over a
  durable Waypoint backend; the engine is dropped after superstep 3, a fresh engine is built from the
  same backend and thread and resumed, and the test asserts completed nodes are not re-executed, the
  final Battlefield equals an uninterrupted control run's, and exactly one Waypoint exists per
  completed superstep.
- `tests/integration/e2e_approval_gate_test.rs` — a Parley node awaiting approval; the run returns an
  awaiting-input outcome rather than an error, the process can be dropped and re-created, and
  resuming with a denial routes to the cancellation node while an approval routes to the action node.
  Both branches asserted.
- `tests/integration/e2e_compensation_chain_test.rs` — the map-reduce fault-tolerance scenario: a
  planner node musters five workers, one fails transiently twice before succeeding, its retry policy
  recovers it, a deferred aggregation node runs exactly once after all five complete, and the
  list-dispatch field holds exactly five results in deterministic order.

`tests/helpers/` currently holds `mock_arsenal_adapter.rs`, `mock_llm_adapter.rs`,
`mock_paladin_port.rs` and `mod.rs` — the extraction target joins them.

From 28-12: `ScenarioRunner::register_graph(name, ctor)` receiving the per-node scripted ports,
`register_registries(name, factory)`, `eval_scenarios!`, `interrupt_after_superstep` and
`parley_responses`, and the CLI's constraint that it can only run registered targets whose
constructors ship in the facade's eval registry.

From 28-05: the scenario format's `target`, `store`, `llm`, `cases`, `assertions` keys and the
assertion names.

X-03 and SHIP-03: the three integration tests must keep passing AS integration tests; the extraction
is behaviour-preserving, and a discovered behavioural difference is a stop-and-flag event.
</interfaces>
