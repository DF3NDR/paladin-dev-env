Run the `lint` job's documentation command exactly as `ci.yml` writes it —
`cargo doc --workspace --no-deps` with its output teed to a capture file and the subsequent
`grep -q "warning:"` negation — but tee to

ratification.

Then write `34-rustdoc-rows.sh`, a bash parser taking a capture file path and a run label. It walks
the capture and, for each diagnostic block beginning with a line matching `^warning:` (or `^error:`
when the caller passes an all-features capture), emits one pipe-table row. It must handle the two
diagnostic shapes:
— A block carrying a `-->` line: take `file:line` from that span directly and set the Location
source cell to the rustdoc span.
— A block carrying no `-->` line, only a note whose text states that the link appears in a given
line: take that quoted snippet and recover the location by `grep -rn` for the snippet, restricted
to the `src/` tree of the crate the diagnostic names (fall back to the workspace `src/` and
`crates/` when the crate is ambiguous), and set the Location source cell to the grep recovery. Emit
the recovered `file:line`; a row that ends with an empty or placeholder location is a parser bug,
not an acceptable output.
Classify Kind into one of: private intra-doc link, unresolved link, redundant explicit link,
unclosed HTML tag, missing docs, other — deriving it from the diagnostic's own first line, and
emitting `other` with the verbatim first line preserved rather than guessing. Skip the per-crate
summary lines that report how many warnings a crate generated — those are totals, not findings, and
counting them as rows would double-count. The script prints rows to stdout and prints a reconciliation
line at the end giving the number of content diagnostics found and the number of rows emitted; the
two must be equal or the script exits non-zero.

Run the parser against the default-feature capture and paste its rows into `34-AUDIT.md` §3 under a
subheading naming the run (`cargo doc --workspace --no-deps`, default features) and the HEAD SHA.
Assign `RD-nn` IDs in table order, continuing from the highest already present. Give every row a
size from the D-04 rubric — a single link repair is `S`, a rustdoc block on an undocumented item
family is `M` — and an evidence anchor pointing at the capture file.

Then verify the enumeration against its own known answers, as CONTEXT.md's Specific Ideas require:
confirm at least one row exists whose location was recovered by grep rather than read from a span,
and confirm the row count reconciles with the capture. Record the total count alongside the rows
with the HEAD SHA and an explicit drift note comparing it against the two figures earlier phases
recorded (72 at the Phase 29 acceptance audit, 73 at Phase 33 close) — say whether the number moved
and, if it did, that this phase does not attribute the movement to a commit, only records it.

Finally cross-check `.planning/WINDOWS.md` rows 36 and 37 against the enumeration: state in §3
whether each row's subject appears among the enumerated findings and confirm both remain `open`
through this phase, with Phase 36 closing them. Do not edit `WINDOWS.md` — rows are added or moved
only through the project's own tooling, and this phase adds none.

Append the commands to `34-EVIDENCE.md` as numbered rows in the command/result/verdict shape, each
verdict cell marking the result as a baseline this phase carries rather than a gate it enforces,
plus the SC5 `git status`.
