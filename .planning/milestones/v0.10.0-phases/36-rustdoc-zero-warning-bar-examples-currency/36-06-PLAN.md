Create `examples/war_engine_configuration.rs` as a single default-feature example binary — no
required-features, so the bulk `cargo build --examples` selector picks it up and no manifest edit is
needed.

Structure it as one runnable story that prints each step, in this order, so a reader sees the
capability without reading the source:

  1. **Inject a waypoint backend (EX-62).** Build the engine against an explicitly constructed
     in-memory waypoint-port implementor — the same store the doc-examples superstep-engine module
     imports — and print which backend was injected and that the same trait is what a SQLite or
     Postgres backend would satisfy. Do not implement a second production backend; the capability is
     the injection point.
  2. **Configure the engine (EX-64).** Construct an engine config naming every field the audit row
     lists — max supersteps, max node visits, run timeout, waypoint durability and max muster tasks
     — and print the resolved values.
  3. **Override the superstep cap from the environment (EX-65).** Set `APP_ENGINE_MAX_SUPERSTEPS`
     in-process before the config is loaded, reload, and print the before and after values so the
     override is visibly the thing that changed it. Restore the variable afterwards so the rest of
     the program runs under the declared config.
  4. **Run a small graph and inspect the checkpoints (EX-63).** Run the seeded cyclic graph to
     completion, then read the persisted checkpoint rows back through the port and print the
     superstep number and node key of each, so the reader sees the table's shape.
  5. **Prune with the retention service (EX-66).** Construct a retention config, run the retention
     service against the same store, and print how many rows it pruned and how many remain.
  6. **Print and explain the fingerprint version (EX-80).** Print the graph fingerprint version
     constant and one sentence stating what a bump invalidates — resumed runs whose stored
     fingerprint no longer matches — matching the specifics note in `36-CONTEXT.md`.

Header comment follows the house shape: what it demonstrates, naming each capability the README
section will name; the exact `cargo run --example war_engine_configuration` command; and an explicit
statement that it needs no provider key and no external service (D-16, D-29). Use question-mark
propagation through a boxed-error main; no unwrap or expect in the body. Use the Medieval-military
terms the tree uses — Waypoint, WarEngine, WarGraph, Muster, Battalion — and never Quartermaster
(D-00i).

Run it once, and record the exit code and the first lines of stdout in
`36-evidence/36-06-examples.txt` (D-16).
