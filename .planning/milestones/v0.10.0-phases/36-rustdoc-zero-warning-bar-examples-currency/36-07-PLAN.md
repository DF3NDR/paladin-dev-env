human-in-the-loop gating and resume (EX-71, EX-72, EX-73) and graceful shutdown (EX-74, EX-75,
EX-76).

Create `examples/human_in_the_loop_gate.rs` as a single default-feature example binary — no
required-features.

Structure it as one runnable story that prints each step:

  1. **Pause at a Gate (EX-71).** Build a small graph containing a Gate node, run it against an
     in-memory waypoint store, and print the outcome the engine returns when it reaches the gate —
     the thread id and what the gate is awaiting. Do not simulate the pause; let the engine produce
     it.
  2. **Resume with typed responses (EX-72).** Call the engine's typed resume entry point with the
     graph, the same thread the pause produced, and the responses the gate awaited, then print the
     completed result. Show what total validation means by also attempting a resume that omits one
     awaited response and printing the typed error it returns — that rejection is the capability, so
     it must be printed, not swallowed.
  3. **Replay or fork the thread (EX-73).** Construct a chronicle service over the same store, read
     the thread's history back, print the superstep-by-superstep record, then replay or fork the
     thread from an earlier point and print the divergent result.

Every LLM call inside the graph goes through the facade's mock adapter with canned responses
(D-16). Header comment follows the house shape: what it demonstrates naming each capability, the
exact `cargo run --example human_in_the_loop_gate` command, and an explicit statement that it needs
no provider key and no external service (D-29). Use question-mark propagation through a
boxed-error main; no unwrap or expect in the body. Use the tree's Medieval-military vocabulary and
never Quartermaster (D-00i).

Run it once and record the exit code and the first lines of stdout in
`36-evidence/36-07-examples.txt`.

Commit per D-26: `docs(36): add human_in_the_loop_gate example (EX-71, EX-72, EX-73)`. Run

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer shell → example process | the example executes in the developer's environment and may read process environment variables |
| human responses → engine resume | the typed resume accepts caller-supplied responses for the awaited gate, which is the trust boundary the total-validation rule guards |
| example process → engine configuration | the program mutates the shutdown grace-period and graceful-shutdown variables in-process |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-36-20 | Spoofing | the engine's typed resume total validation | high | mitigate | EX-72's capability is precisely that an incomplete or mismatched resume is rejected with a typed error rather than silently accepted. The program must print the rejection path, so an example reader learns to rely on it rather than pre-validating by hand. |
| T-36-21 | Information Disclosure | both new example programs | medium | mitigate | Neither program reads or prints a provider key; both use the mock LLM adapter and in-memory ports and say so in their header comments (D-16, D-29). | T-36-23 | Tampering | process environment | low | mitigate | Both environment demonstrations set the variable in-process and restore it afterwards. |
