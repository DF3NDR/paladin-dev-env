Task 2: examples/platform_api_client.rs (EX-77, EX-78, EX-79, EX-91, EX-92, EX-93, EX-94,
EX-95, EX-98, EX-99, EX-104, EX-110)
------------------------------------------------------------------------------------------------

Design note: `paladin_port_from_settings` (`src/infrastructure/web/facade_provisioner.rs`)
resolves a REAL provider credential via `LlmProviderFactory` -- there is no "mock" entry in
its provider registry -- so this example cannot go through `build_run_api` and stay offline.
Instead it wires the same collaborators `build_run_api` wires (run/assistant/run-schedule/
webhook-delivery repositories, run queue, waypoint store, resolvers, worker pool, schedule
service, webhook delivery drain loop, run event bus), but every store is the
`paladin_storage::*::in_memory` adapter for its port (never sqlite/postgres/redis), and the
run engine's `PaladinPort` is a local `MockEnginePort` wrapping the SAME
`PaladinExecutionService` + `MockLlmAdapter` pair `http_service_host.rs` uses -- fully
in-process, offline, no provider key, per D-16.

Task 3: examples/webhook_receiver.rs (EX-96, EX-97)
------------------------------------------------------------------------------------------------

Reuses the SAME `sign_webhook_body` function and the SAME `hmac`/`sha2` crates the shipped
`WebhookDeliveryService` signs with (never a hand-rolled construction); the receiver handler
captures the raw request body via axum's `Bytes` extractor (before any deserialization) and
verifies in constant time via `hmac::Mac::verify_slice` (never a plain `==` on digest bytes).
The signing secret is generated in-process from 32 random bytes and is never printed --
only "valid"/"invalid" and the constant-time-verified/rejected narration are printed.
