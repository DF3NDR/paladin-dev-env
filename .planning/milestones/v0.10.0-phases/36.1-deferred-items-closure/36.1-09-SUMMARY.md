# Phase 36.1 Plan 09: RunSubmissionService and RunInspectorService `# Examples` Summary

**Added compiling, passing `# Examples` doctests to `RunSubmissionService` and `RunInspectorService`, settling the shared unverified `AssistantResolver` collaborator by reusing the shipped `CodeWorkflowResolver` rather than writing an inline implementation, dropping the facade `*Service` examples-gate MISSING count from 5 to 3.**

## Performance

- **Duration:** ~35min
- **Completed:** 2026-09-18
- **Tasks:** 2
- **Files modified:** 2 (plus 1 evidence file created)

## Accomplishments

- `RunSubmissionService`'s doc comment now carries a `# Examples` section that constructs the service from `paladin_storage::run::in_memory::InMemoryRunRepository`, `paladin_storage::run_queue::in_memory::InMemoryRunQueue`, and `paladin::application::services::run::CodeWorkflowResolver::new()`, then calls `submit()` once against an unregistered assistant id and asserts `RunSubmissionError::UnknownAssistant` -- a single call that needs no live backend and proves the resolver argument is load-bearing (resolution is `submit`'s first fallible step), not merely type-checking.
- `RunInspectorService`'s doc comment now carries a `# Examples` section that constructs the service from `paladin_storage::waypoint::in_memory::InMemoryWaypointStore`, `paladin_storage::run::in_memory::InMemoryRunRepository`, and the same `CodeWorkflowResolver::new()` route Task 1 settled, then calls `inspect()` once against a thread with no run or Waypoint history and asserts `InspectorError::ThreadNotFound`.
- **The resolver question (RESEARCH.md assumption A1) is settled once, for both services:** `src/application/services/run/resolver.rs` already ships `CodeWorkflowResolver`, a public, `Default`-derived, zero-live-dependency `AssistantResolver` implementation with a plain `new()` constructor, re-exported at `application::services::run::CodeWorkflowResolver`. A tree-wide search (`grep -rn 'impl AssistantResolver for'`) found eight implementations total, several test-only; `CodeWorkflowResolver` is the only non-test, zero-argument-constructible one, so both examples use it directly -- no inline doctest-local resolver implementation was needed, and no production code was added anywhere.
- Re-measured `cargo doc --workspace --no-deps` after both sections landed: still zero warning lines (ADR-0033 bar unaffected). Also re-ran the full `cargo test --workspace --doc` suite: 477 passed, 0 failed across every workspace crate (up from the 462-pass baseline recorded in `34-AUDIT.md` §3, consistent with "may only grow"). Both captured to `36.1-evidence/36.1-09-services-measure.txt`.
- `bash scripts/check-public-api-examples.sh --list` now reports both items `OK`; the `TOTAL` MISSING count dropped from 5 to 3 (`RunEventStreamService`, `AssistantService`, `WaypointRetentionService` remain, owned by plans 36.1-10/36.1-11).

## Decisions Made

- **Resolver route: reuse the shipped `CodeWorkflowResolver`, not an inline impl.** Before writing either doctest, searched the whole tree (`grep -rn 'impl AssistantResolver for'`) and read `src/application/services/run/resolver.rs` in full. `CodeWorkflowResolver::new()` is public, already re-exported at `application::services::run`, requires no arguments, and performs no I/O -- it is strictly simpler than the `AlwaysAccepts`-style inline-fixture technique plan 36.1-08 used for `RunSubmissionPort` (which had no shipped in-memory adapter). Both tasks reuse this route verbatim, satisfying the plan's T-36.1-36 mitigation (two examples must not solve the same collaborator two different ways).
- `RunSubmissionService`'s example exercises `submit()` once against an unregistered assistant id and asserts the specific `RunSubmissionError::UnknownAssistant` variant, rather than stopping at bare construction, to prove the resolver wiring is actually load-bearing.
- `RunInspectorService`'s example exercises `inspect()` once against an empty thread and asserts `InspectorError::ThreadNotFound`, the cheapest call on this service that proves real (not merely type-checked) wiring without a live backend.

## Deviations from Plan

None - plan executed exactly as written. Both examples use plain compiling fences (not `no_run`), since neither construction nor the one exercised call performs real I/O: `InMemoryRunRepository`/`InMemoryRunQueue`/`InMemoryWaypointStore` are in-process stores and `CodeWorkflowResolver` holds an empty in-memory `HashMap`.
