### WR-01: New doctests widely use `.unwrap()`/`.unwrap_err()` instead of `?`, violating the project's own documented convention

**Files modified:**
- `crates/paladin-ports/src/input/assistant_admin_port.rs`
- `crates/paladin-ports/src/input/run_submission_port.rs`
- `crates/paladin-ports/src/input/schedule_admin_port.rs`

- `crates/paladin-ports/src/output/node_cache_port.rs`
- `crates/paladin-ports/src/output/run_queue_port.rs`
- `crates/paladin-ports/src/output/run_repository_port.rs`
- `crates/paladin-ports/src/output/run_schedule_repository_port.rs`
- `crates/paladin-ports/src/output/run_trace_port.rs`

**Commits:**
- `40669bf1` — the 11 `paladin-ports` trait doctests
- `7df4fbd8` — the 2 facade-service doctests

**Applied fix:** In each file's `# Examples` doctest, converted the outer
`#[tokio::main] async fn main()` to `async fn main() -> Result<(), Box<dyn
std::error::Error>>`, replaced every `.unwrap()` on a directly-demonstrated
port/service call with `?`, and added a trailing `Ok(())`. `AssistantId::new`,
`ThreadId::new`, and every `*Error` type in these signatures derive
`thiserror::Error` (confirmed by reading `paladin-core`'s `AssistantIdError`
and `ThreadIdError` definitions before editing), so `?` converts cleanly into
`Box<dyn std::error::Error>` via its blanket `From` impl — no new error
variants or trait-signature changes were needed anywhere.

Two adaptations beyond a literal find-and-replace, both verified to compile
and pass before committing:
- `waypoint_port.rs`'s example chained `store.latest(&thread).await.unwrap().unwrap()`
  — a `Result` unwrap followed by an `Option` unwrap. `?` only applies to the
  `Result` layer, so the `Option` layer became
  `.ok_or("expected the just-saved waypoint to round-trip back out")?`,
  which the standard library's special `From<&str> for Box<dyn Error>` impl
  makes as terse as the original.
- `run/inspector.rs`'s example used `.unwrap_err()` to assert an expected
  failure path. Per the orchestrator's directive for this exact shape, this
  became `.err().ok_or("expected inspect on an unknown thread to fail")?`
  followed by the original `assert!(matches!(err, ...))` — a doctest failure
  here now surfaces as a clean `Err` return rather than a raw panic, which is
  the whole reason the project's convention exists (per REVIEW.md's own
  Issue text).

**Deliberately left unchanged (scoped narrowly, not a partial fix):**
- Every `Mutex::lock().unwrap()` call inside each doctest's mock
  `impl <Port> for <InMemoryX>` block. These are implementation details of a
  throwaway fake backing store, not the demonstrated "Example" call flow
  itself, and cannot be converted to `?` without an invasive, out-of-scope
  change: `std::sync::PoisonError` does not implement `From` into any of
  these ports' own `*Error` types, and the guard it wraps borrows the
  `Mutex` (not `'static`), so it cannot convert into `Box<dyn Error + Send +
  Sync>` either. Adding a new `*Error` variant to carry it would move the
  `paladin-ai`/`paladin-ports` public API surface for a style fix alone —
  confirmed via `make api-surface` staying "unchanged" after every commit in
  this pass.
- `chrono::Duration::from_std(ttl).unwrap()` inside `node_cache_port.rs`'s
  mock `put` impl — same reasoning: internal to the fake backend, not part
  of the demonstrated call flow, and `ttl` there is a `Duration::from_secs(60)`
  literal that cannot practically fail.
- `ThreadId::new("t1").unwrap()` inside the `AlwaysAccepts::submit` mock
  impls in both `run_submission_port.rs` and `src/application/services/run/schedule/service.rs`
  (the review's WR-01 citation list includes `schedule/service.rs:203`).
  Reading the actual file: the outer `async fn main()` in
  `schedule/service.rs`'s doctest already has **zero** `.unwrap()` calls (it
  was already compliant) — the only remaining occurrence is this one, inside
  a closure passed to `.unwrap_or_else()`. That closure's return type is
  `ThreadId`, not `Result<ThreadId, _>`, so `?` cannot syntactically apply
  there regardless of error-type conversion; and `RunSubmissionError` has no
  `From<ThreadIdError>` to convert into even if the closure did return a
  `Result`. `.unwrap()` on a hardcoded, always-valid `"t1"` literal is the
  only viable form here. **No edit was made to `schedule/service.rs`** — it
  needed none.

### WR-02: `cli-configuration.md`'s new garrison-troubleshooting text describes a code path that does not exist

**Files modified:** `docs/src/appendix/cli-configuration.md`
**Commit:** `0bb4e795`
**Applied fix:** Read `PaladinConfig::garrison` (`Option<GarrisonConfig>`) and
`instantiate_garrison` (`src/application/cli/config/loader.rs:113-129`)
directly before editing, confirming the review's exact claim: the whole
`garrison:` block is what's optional (`let Some(garrison_config) = config
else { return Ok(None); }`), and `GarrisonConfig::garrison_type` is a
required `String` field with no `#[serde(default)]`. Replaced the single
incorrect sentence with the review's suggested two-state correction: absent
`garrison:` block → `instantiate_garrison` returns `None`, Paladin runs
without memory; present `garrison:` block with missing/blank `type` → config
deserialization fails before the Paladin ever starts, a startup error rather
than silent memory loss.
