## Warnings

### WR-01: New doctests widely use `.unwrap()`/`.unwrap_err()` instead of `?`, violating the project's own documented convention

**File:** `crates/paladin-ports/src/input/assistant_admin_port.rs:253-283` (and, by the
same pattern, `crates/paladin-ports/src/input/run_submission_port.rs`,
`crates/paladin-ports/src/input/schedule_admin_port.rs`,
`crates/paladin-ports/src/output/assistant_repository_port.rs`,
`crates/paladin-ports/src/output/node_cache_port.rs`,
`crates/paladin-ports/src/output/run_queue_port.rs`,
`crates/paladin-ports/src/output/run_repository_port.rs`,
`crates/paladin-ports/src/output/run_schedule_repository_port.rs`,
`crates/paladin-ports/src/output/run_trace_port.rs`,
`crates/paladin-ports/src/output/waypoint_port.rs`,
`crates/paladin-ports/src/output/webhook_delivery_port.rs`,
`src/application/services/assistant/service.rs:59`,
`src/application/services/run/inspector.rs:98,101`,
`src/application/services/run/schedule/service.rs:203`)

**Issue:** `.github/instructions/rust.instructions.md` ("Testing and Documentation")
states plainly: *"Examples should use `?` operator, not `unwrap()` or deprecated
`try!` macro."* This is imported into `CLAUDE.md` and applies to every session in
this repo. A `git diff` count of `unwrap()` occurrences added by this phase shows
10, 3, 7, 12, 6, 6, 5, 5, 6, 7, 7 occurrences respectively across the eleven
`paladin-ports` files touched, plus scattered occurrences in the facade service
examples — roughly 75 new `.unwrap()`/`.unwrap_err()` call sites across the 19 new
`# Examples` blocks. Two of the nineteen (`src/application/services/run/webhook/service.rs`
and `src/application/services/waypoint_retention.rs`) correctly follow the
convention (a `Result`-returning helper function and `?`, or no fallible calls at
all) — proving the pattern was known and available, just not applied consistently.
Doctest panics on `unwrap()` are also a materially worse failure mode than `?`
propagation: a panicking doctest aborts the whole `cargo test --doc` process for that
crate with a raw panic message, rather than a clean `Err` returned from `main`,
which is why the convention exists.

**Fix:** Convert the `#[tokio::main] async fn main() { ... }` doctest bodies to
`async fn main() -> Result<(), Box<dyn std::error::Error>> { ... ?; ... Ok(()) }`
and replace `.unwrap()` with `?` throughout (mirroring
`src/application/services/run/webhook/service.rs`'s `fn build() -> Result<..., Box<dyn
std::error::Error>> { ... }` wrapper pattern, or `paladin_builder.rs`'s worked
pattern the gate script's own error message already points to). `.unwrap_err()` used
specifically to demonstrate an expected-error path (e.g.
`run_submission_port.rs`'s `always_unwired_returns_not_wired`-style assertions) is a
narrower case and may be acceptable to leave as-is if the project wants to keep
error-path examples terse, but the plain `.unwrap()` calls used purely to unwrap a
happy-path `Result` should convert to `?`.

### WR-02: `cli-configuration.md`'s new garrison-troubleshooting text describes a code path that does not exist

**File:** `docs/src/appendix/cli-configuration.md:413-414`

**Issue:** The new text reads: *"If `garrison.type` is unset, `instantiate_garrison`
returns `None` and the Paladin runs without memory — set `garrison.type` in the
config to fix that."* This is not what the code does. `PaladinConfig::garrison` is
`Option<GarrisonConfig>` (`src/application/cli/config/paladin_config.rs:95`) — the
*whole* `garrison:` block is what's optional, and `instantiate_garrison` returns
`Ok(None)` only when that entire block is absent from the YAML
(`src/application/cli/config/loader.rs:117-119`). `GarrisonConfig::garrison_type`
itself is a required `String` field with no `#[serde(default)]`
(`paladin_config.rs:136-139`): if a user writes a `garrison:` block but omits (or
blanks) the `type:` key, deserialization of the config file fails outright — the
process never reaches `instantiate_garrison`'s `None` branch at all, and the user
gets a config-parse error, not a silently-memoryless Paladin. A reader following
this troubleshooting entry who leaves `garrison.type` blank inside an existing
`garrison:` block will hit a parse error, not the "runs without memory" symptom the
doc describes, and will not find this entry's advice ("set `garrison.type` in the
config") applicable to their actual error message.

**Fix:** Correct the sentence to distinguish the two states, e.g.: *"If the whole
`garrison:` block is absent from the config, `instantiate_garrison` returns `None`
and the Paladin runs without memory — add a `garrison:` block with a `type` value.
If `garrison:` is present but `type` is missing or blank, config loading fails
before the Paladin ever starts (`garrison.type` is a required field) — the symptom
is a startup error, not silent memory loss."*
