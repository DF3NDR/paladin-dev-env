  reads the publish order exclusively through `scripts/publish-crates.sh`'s

## Decisions Made

- **Alias-safe dependency resolution.** Verified live (via the captured `1d4a9724` fixture) that
  several crates declare the core crate under a local `rename: "paladin-core"` while the
  dependency entry's `name` field still reads the true package name `paladin-ai-core`. The gate
  resolves exclusively via `name`, matching the plan's explicit prohibition against reading
  `rename`.
- **Disjoint failure classes.** A crate missing from one side of the `CRATES`/publishable-set
  equality is intentionally never also reported as an ordering violation for that same crate --
  `order_violations` skips any dependency name not present in the `CRATES`-position map, since
  that case is already covered by the set-equality report. Verified via the harness's Behavior 3
  and 4 assertions, each isolated against the zero-violation `metadata-fixed.json` base.
- **Synthetic set-equality fixtures built at test run-time, not committed.** The two set-equality
  behaviors (Behaviors 3 and 4) are exercised by `jq`-deriving a scratch copy of the committed
  `metadata-fixed.json` inside the harness's own `mktemp -d` scratch directory -- adding a new
  publishable package for one case, removing `paladin-content` for the other -- per the plan's
  own instruction to never edit a committed fixture in place.
- **Python3 for the core comparison logic**, matching `check-release-consistency.sh`'s own house
  shape (a `python3` heredoc invoked from inside the `set -euo pipefail` bash function), rather
  than attempting the set-equality/positional-comparison logic in pure `jq` -- the alias-vs-name
  resolution and disjoint-failure-class bookkeeping are materially clearer in Python than as a
  `jq` filter chain.
