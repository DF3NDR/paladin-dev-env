<objective>
Wire the gate into the two places that decide whether a defect reaches a tag: the local composite
gate and pre-merge CI.

Purpose: a gate nobody runs is documentation. Locally, `make check-gates` is the composite the
re-seal exercises, so the new guard belongs in its prerequisite list beside its seven siblings. In
CI, the correction research surfaced matters: the existing workspace dry-run job never runs on a
pull request at all, so "it passed in CI" would have meant "it ran after the merge". The new gate
is cheap and offline, so it goes into a job that already runs on every push and every pull request.
Output: a `check-publish-order` make target inside `check-gates`, a `Check publish order` CI step,
and a dated finding recording the dry-run job's pre-merge blindness.

Governing constraints: D-08 stage 1 — this plan ends with `make check-gates` red, on purpose.
D-00d — the dry-run job's trigger scope is recorded, not fixed.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pull request → the protected default branch | A gate that runs only after the merge cannot stop a defect from being merged; the trigger scope of the job the gate lives in is the whole control |
| untracked working-tree file → the shell linter's file set | A lint target that scans only tracked files reports clean over a script it never opened |
| workflow trigger surface → the recorded trigger-policy table | Any change to a workflow's `on:` block or any new workflow file must be reflected in the table, or the trigger guard fails |
