## Accomplishments

- Bumped the workspace package version, all ten `[workspace.dependencies]` sibling pins (exact-equality pin in `paladin-ports` preserved as `=0.10.1`), the root package's three direct sibling entries, all eleven publishable crate manifests, and the non-publishable `doc-examples` manifest — zero occurrences of `0.10.0` remain in any actual version field anywhere in the workspace (`cargo metadata`'s `[.packages[] | select(.version != "0.10.1")] | length` reads 0).

- Found and fixed a plan gap the orchestrator's own tree-verified facts flagged before dispatch: `crates/paladin-web/src/openapi.rs`'s committed OpenAPI baseline (`openapi.json`) carries the package version and is guarded by a full-string `assert_eq!` test. - Inserted a new `[0.10.1]` section above `[0.10.0]` in all twelve changelogs (root + eleven crates), in the exact bracketed-heading grammar `check-release-consistency.sh` clause 2 matches: the root changelog names both real `v0.10.0` release-day defects (the `paladin-battalion` publish-order dev-dependency and the `create-or-reuse-release.sh` EPIPE race) plus the new `check-publish-order.sh` gate; nine per-crate changelogs state plainly they carry no source change; `paladin-battalion`'s notes its own genuinely-differing published manifest; `paladin-web`'s notes the regenerated OpenAPI baseline. A dated line was appended to the `[0.10.0]` section (text kept intact) stating it published only 3 of 12 crates and is superseded.
- Appended a dated addendum directly under `MIGRATION.md`'s existing scope note, naming `0.10.1` as the version that actually shipped, while keeping the title byte-identical to the base commit — confirmed by direct comparison, not just visual inspection. `.cargo/semver-checks-allowlist.toml` was read in full and confirmed to carry no version field of any kind (`crate`/`lint`/`migration_row`/`requirement_id`/`justification` only); it was not touched.

## Decisions Made

- **Land the OpenAPI baseline regeneration in Task 1's own commit, not a separate one:** matches the real `0.10.0` bump's own precedent commit (`83d219f1`), which touched the manifests, the lockfile, and one line of `openapi.json` together. A lockfile-and-manifest bump that leaves a version-carrying test-guarded generated artifact stale until a later commit is exactly the kind of drift the phase's own threat model (T-37.1-21) exists to catch.
- **Leave `paladin-battalion/Cargo.toml`'s four historical comment lines untouched despite the plan's own literal `<verify>` command summing to a nonzero count:** the same governing principle the plan already applies to `MIGRATION.md`'s title (D-00d, RESEARCH.md Pitfall 4, threat T-37.1-22) — rewriting "the real v0.10.0 release-day defect" to say "v0.10.1" would state something false about a past event. The substantive per-path and metadata-query acceptance criteria (which do not sum across comment lines) all pass.
- **Bump `doc-examples/Cargo.toml` for tree consistency:** zero release risk (`publish = false`, excluded from every publishable-set derivation), and leaving it unbumped would make it the one manifest in the tree still reading `0.10.0` after every other manifest reads `0.10.1` — resolving RESEARCH.md's Open Question 1 per the plan's own instruction.

- **Fix:** Observed red (`cargo test -p paladin-web --lib openapi_matches_committed_baseline` → exit 101, `test result: FAILED`), regenerated via `UPDATE_OPENAPI=1 cargo test -p paladin-web openapi_matches_committed_baseline`, confirmed the resulting diff was exactly the one `"version"` line, then re-ran without the env var and observed green (`test result: ok. 1 passed`).
- **Files modified:** `crates/paladin-web/openapi.json`
- **Verification:** `37.1-CI-EVIDENCE.md` Local sweep rows 24-25, verbatim red and green output recorded.

**2. [D-00d / RESEARCH.md Pitfall 4 / T-37.1-22 — historical prose preserved, not rewritten] Left four pre-existing `paladin-battalion` Cargo.toml comment lines untouched**
- **Found during:** Task 1, when the literal `<verify>` command's sum-of-per-file-counts check was run against the fully bumped tree and did not read 0
- **Issue:** Plan 37.1-04 (an earlier wave in this same phase) added four `#`-prefixed comment lines to `crates/paladin-battalion/Cargo.toml` describing the real `v0.10.0` release-day publish-order defect, two of them literally containing "v0.10.0" and one quoting the real `cargo publish` error text `"^0.10.0"`. This is the exact class of edit the plan's own prohibitions and threat model (T-37.1-22) forbid for `MIGRATION.md`'s title; the same reasoning applies here even though these specific lines are not named by any prohibition.
- **Files modified:** None (deliberately unchanged)
- **Verification:** `cargo metadata`'s `[.packages[] | select(.version != "0.10.1")] | length` reads 0 (every real version field is correct); the exact-equality pin kept its operator; the lockfile was regenerated and committed alongside the manifests. All of Task 1's *substantive* acceptance criteria pass; only the literal sum-across-comments assertion does not, and that gap is recorded here and in `37.1-CI-EVIDENCE.md` rather than silently worked around.
- **Committed in:** `88d174de` (Task 1 commit, i.e. this is a "did not change" deviation, not a separate commit)
