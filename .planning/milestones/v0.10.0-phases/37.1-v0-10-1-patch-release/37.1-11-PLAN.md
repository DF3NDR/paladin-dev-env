<objective>
Hand the maintainer the two irreversible acts, in order, with the exact commands — and stop.

Purpose: the merge and the tag are where this phase leaves the agent's authority entirely. The tag
triggers a publish to a public registry through the project's trusted-publishing link, and a
published version can be yanked but never deleted and never re-used. So the hand-off is preceded by
a decision checkpoint that names that door for what it is, and it carries a short specific runbook
the maintainer can act from directly rather than a pointer to a document.
Output: the tick-commit check record, a reversibility decision checkpoint, the merge and tag
runbook, and a resume file.

**This plan is not autonomous.** It contains two blocking checkpoints and ends in a hard stop.

Governing constraints: D-00b (maintainer-only irreversible acts), D-00c (merge commit, then
annotated tag on it after the default-branch workflow is green), D-00k (no dispatch rehearsal, no
release-candidate tag, no shadow tag), D-00i (hard stop plus resume file), D-10 (the enforced
order).

**ORCHESTRATOR NOTE — this plan starts only on a confirmed resume condition,** and it must not be
auto-advanced past either checkpoint. Both checkpoints are blocking and human-gated; an
automatic-advance mode does not satisfy them.
</objective>

  <instructions>
Three steps, in this order. The agent prints the concrete values — pull request number, tick commit
SHA, repository — in place of the placeholders when it presents this checkpoint.

**Step 1 — merge, using a merge commit.**

Not a squash, not a rebase: the tag has to sit on a two-parent merge commit on the default branch,
and the recorded evidence describes that commit. From the command line:

    gh pr merge <PR-NUMBER> --merge --repo <OWNER>/<REPO>

Or in the web interface, choose "Create a merge commit" explicitly — the dropdown may remember a
different default.

**Step 2 — wait for the default-branch workflow on the merge commit, then read its SHA.**

    git fetch origin --tags
    git rev-parse origin/main
    gh run list --commit "$(git rev-parse origin/main)" --repo <OWNER>/<REPO>

Do not tag until the continuous-integration workflow has concluded `success` on that exact merge
commit. This is the project's documented precondition for cutting a tag, and it is what the release
workflow's own source-verification job checks against.

**Step 3 — create and push the annotated tag on that merge commit.**

    MERGE_SHA="$(git rev-parse origin/main)"
    git tag -a v0.10.1 "$MERGE_SHA" -m "v0.10.1 — patch release: publish-order and release-script fixes"
    git push origin v0.10.1

An annotated tag, not a lightweight one — the post-tag evidence asserts the tag object's type, its
tagger date and its message. Push the tag to the default remote; do not use the release make target.

**What happens next, without you doing anything:** pushing the tag starts the release workflow. It
verifies the tag's source, re-checks release consistency, creates the release object, and publishes
the crates in dependency order through trusted publishing. No registry credential exists or is
needed.

**What the agent will do when you come back:** it re-verifies the tag exists and sits on the merge
commit, records the release run read-only, and verifies the registry. If the run is red, it
diagnoses read-only per the recovery runbook and stops — completing forward, re-running and yanking
are yours.

**What the agent will not do, under any mode:** merge, tag, dispatch or re-dispatch the release
workflow, publish, or yank.
  </instructions>
