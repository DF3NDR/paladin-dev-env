# Phase 37.1: v0.10.1 Patch Release - Context

**Gathered:** 2026-09-19
**Status:** Ready for planning

<domain>
## Phase Boundary

v0.10.x is **actually released**: every publishable crate (list derived from `cargo metadata`,
`publish != false` — twelve today) resolves on the crates.io sparse index at one coherent
version, `0.10.1`, published by `release.yml` through Trusted Publishing from an annotated
`v0.10.1` tag on a `main` merge commit.

Tag `v0.10.0` (on merge commit `1d4a9724`) published 3 of 12 crates (`paladin-ai-core`,
`paladin-ports`, `paladin-herald`) and then failed deterministically at `paladin-battalion`. That
tag's pipeline cannot complete forward — `release.yml` reads manifests and the `CRATES` order from
the tag ref, and the tag cannot move. The maintainer chose recovery option **A** (runbook §4: a
new patch version through the pipeline).

Delivered here:
1. the `paladin-battalion` publish-order defect fixed;
2. the `scripts/create-or-reuse-release.sh:79` `printf | head -n1` / `pipefail` `EPIPE` race fixed,
   with a regression test that feeds a response larger than the pipe buffer;
3. a gate that exercises the real per-crate resolution order (including dev-dependencies), wired
   into `make publish-dry-run`/`release-check` and CI, and proven red on the `1d4a9724` tree;
4. the twelve-manifest bump to `0.10.1` with changelogs and `MIGRATION.md`/allowlist rows;
5. the gate re-seal, release PR, maintainer sign-off, merge, tag and green `release.yml` run;
6. registry verification, the disposition of the three orphaned `0.10.0` versions, and the true
   release record (MILESTONES.md, the `v0.10.0` GitHub Release, Phase 37's open plans, `SHIP-06`).

**Not** delivered here: any new capability; any change under `src/` or `crates/*/src/` beyond what
the three named defects strictly require (none is expected — the fixes are manifest, shell and
gate changes); making `release.yml` dry-runnable without a tag; correcting the stale "eleven
crates" docs count; the `/gsd-complete-milestone` run itself; anything belonging to v0.11.0.

Observed state at discussion time (2026-09-19, HEAD `9154aba7` on `feature/phase-33`):
`origin/main` tip is the PR #55 merge commit `1d4a9724`; `feature/phase-33` carries 14 local-only
commits on top of the old PR head `1bb94063` — all `.planning/`-only, tree otherwise identical to
`origin/main`; `.planning/ROADMAP.md` and `.planning/STATE.md` hold the uncommitted Phase 37.1
insertion. Workspace version reads `0.10.0`.

## Implementation Decisions

### Carried forward (locked by Phase 37 / Phase 29 — not re-asked)

- **D-00a:** Only the maintainer ticks a sign-off box — never an agent, under any mode including
  `--auto` (Phase 29 D-17, Phase 37 D-00a).
- **D-00b:** The maintainer alone performs the irreversible acts — merging the release PR, pushing
  the `v*` tag, and any `cargo yank`. The agent hands over exact commands and stops; it never
  merges to `main`, never pushes a `v*` tag, never publishes, never yanks (Phase 37 D-02, D-16;
  runbook §5).
- **D-00c:** Tag-cut mechanism: version-bump PR merged to `main` with a **merge commit** (not
  squash, not rebase), then an **annotated tag pushed directly to that merge commit** after
  `ci.yml` is green on it. `make release` is not used (Phase 37 D-00c, D-04).
- **D-00d:** Findings are recorded, never fixed silently; amend-at-source — original text is
  retained, additions are dated; `WINDOWS.md` rows are never deleted (Phase 29 D-12/D-24).
- **D-00e:** The 82 % workspace line-coverage floor (ADR-0006) is measured by CI's `coverage` job
  only — this devcontainer has no Docker.
- **D-00f:** Shipped tree outranks any document. The publishable-crate list is whatever
  `cargo metadata` says, never hard-coded (Phase 37 D-00f, D-08).
- **D-00g:** Publishing is via crates.io Trusted Publishing; no standing registry credential
  exists and nothing in this phase may introduce or request one. `paladin-eval`'s placeholder
  bootstrap (Phase 37 D-17) is already done; `0.10.1` is its first pipeline publish, and a
  non-null `trustpub_data` on it is the observable proof of the Trusted Publisher link.
- **D-00h:** Registry proof is a sparse-index (`index.crates.io`) read per publishable crate —
  crate, version, checksum, `yanked` — recorded as a table. The workflow's own log is not accepted
  as proof on its own (Phase 37 D-08).
- **D-00i:** Waiting is a hard stop with a resume file naming the exact resume condition — never a
  parked watcher or a long-lived `gh run watch` agent (Phase 37 D-12).
- **D-00j:** If the real `v0.10.1` release run goes red, the agent diagnoses read-only per runbook
  §1-§2, writes it down, and hard-stops; completing forward, re-runs, re-dispatch and yanks are the
  maintainer's (Phase 37 D-16). A pure infrastructure flake may be re-run exactly once with both
  run IDs and the justifying log line recorded; the retired Docker Hub MinIO image is a real
  failure, not a flake (Phase 37 D-15).
- **D-00k:** `release.yml` cannot be dry-run-dispatched before a ref literally named after the tag
  exists (Phase 37 research Q1). No dispatch rehearsal, no rc tag, no shadow tag.

### Orphans, SHIP ID & the record

- **D-01:** The three orphaned `0.10.0` versions (`paladin-ai-core`, `paladin-ports`,
  `paladin-herald`) are **yanked by the maintainer, and only AFTER the sparse index shows every
  publishable crate at `0.10.1`, `yanked = false`** — so there is never a window in which those
  three crates have no resolvable, non-yanked `0.10.x`. If the `v0.10.1` run goes red, nothing is
  yanked and D-00j applies. The agent hands over the three exact `cargo yank --version 0.10.0
  <crate>` commands at a blocking human-action checkpoint, then verifies read-only that the index
  shows `yanked = true` for each. **One yank-register row per crate** is appended to
  `docs/src/appendix/release-recovery.md` §5 (the register says "do not summarize multiple yanks
  into one row"); reason text: not defective — orphaned partial publish of `v0.10.0`, superseded by
  `0.10.1`. — **Reversibility:** costly — `cargo yank --undo` exists, but a yank changes what new
  resolves select on a public registry and is a maintainer-only act each way.
- **D-02:** A new requirement **`SHIP-06`** — "v0.10.1 is released" — is minted and mapped to
  Phase 37.1, with checkable criteria mirroring this phase's success criteria (defects fixed and
  gated, gates re-sealed on the final commit, tag on the `main` merge commit, every publishable
  crate on crates.io at `0.10.1`, orphans dispositioned, release evidence in MILESTONES.md).
  **`SHIP-05` keeps its original text and is never ticked `[x]`**: it gains a dated
  amend-at-source note — tagged `v0.10.0` on `1d4a9724`, partially published 3/12, superseded by
  `SHIP-06` — and its traceability status reads superseded, not Complete, because what it
  literally says never became true. `SHIP` is an existing prefix (ROADMAP extension protocol
  item 3). ROADMAP Phase 37.1's `**Requirements**: TBD` line is replaced with `SHIP-06`. Same
  reasoning as Phase 37 D-07 (a new ID rather than re-opening `SHIP-04`).
- **D-03:** The `v0.10.0` GitHub Release object is **kept, bannered and flipped to pre-release**.
  A short dated notice is prepended to its body — tagged, only 3 of 12 crates published, superseded
  by `v0.10.1`, use that — the existing 42 KB body is otherwise untouched, and `prerelease=true`
  makes `v0.10.1` unambiguously "Latest". The tag `v0.10.0` is never moved or deleted. This is
  done **after** `v0.10.1` is registry-verified. It is an outward-facing edit of a published
  object: the agent drafts the notice and the exact `gh release edit` command and hands them to
  the maintainer; the agent runs it only if the maintainer says so at that checkpoint.
- **D-04:** **Phase 37.1 absorbs Phase 37's post-tag wave.** 37.1's own plans perform the
  post-merge evidence, registry verification, the MILESTONES.md entry and the single close PR for
  the release that actually happened. In Phase 37: plans `37-09`, `37-10` and `37-11` are marked
  **superseded by Phase 37.1** with a dated note — never deleted, never executed; `37-08` gets a
  SUMMARY that ends at the D-16 hard stop and the maintainer's recovery decision; Phase 37 then
  closes as "SC1-SC3 met; SC4 not met by tag `v0.10.0`, superseded by `SHIP-06`" — verified on what
  is true, not by promise (Phase 37 D-09's own rule). The ROADMAP Phase 37.1 `**Depends on**` text
  that says Phase 37's plans are "re-planned against what this phase ships" is corrected to match

- **D-05:** The MILESTONES.md v0.10.0 milestone entry tells both tags plainly: `v0.10.0` tagged on

  resolvable. `feature/phase-33` is retired: no further commits, deletion left to the maintainer.
  The release PR's diff is therefore exactly what changed since `v0.10.0`.
- **D-07:** **One release PR.** The battalion fix, the script fix, the new gate, the regression
  tests, the twelve-manifest bump, changelogs and the `MIGRATION.md`/allowlist rows all ride
  `release/v0.10.1` → one PR → one merge commit → the tag. The agent pushes the branch and opens
  the PR via `gh` with a curated body (what broke in `v0.10.0`, what changed, gate re-seal summary,

  `GH_TOKEN` is handing the exact commands to the maintainer.
- **D-08:** **Red-gate policy is two-stage.**
  *Build wave* (battalion fix, script fix, gate, tests, bump, changelogs): normal TDD — red is
  expected, and the agent fixes anything **inside the six success criteria**. A red outside them

  not fixed silently.

  unchanged — any red gate, locally or in PR CI, is recorded (command, SHA, failing output) and the
  agent halts at a blocking checkpoint and fixes **nothing**. Returning to the build wave happens
  only on the maintainer's say-so, and the re-seal then restarts from the top on the new head.
- **D-09:** The v0.10.1 sign-off is a **new `## 13.` re-seal section appended to the corpus
  audit** `.project/v0.10.0/09-program-acceptance-audit.md` (after Phase 37's `## 12.`): the

### Claude's Discretion

The maintainer did not select these two areas for discussion; the defaults below were stated at
the close of discussion and accepted. Research may overturn a default only with evidence, and
must say so in RESEARCH.md.

- **Battalion ordering fix — default: path-only dev-dependencies.** Drop `version = "0.10.0"` from
  `paladin-battalion`'s two workspace dev-dependencies (`paladin-llm`, `paladin-storage`) so Cargo
  strips them from the published manifest and they impose no registry-ordering constraint. Leave
  the `CRATES` order alone unless research shows a reason to move it. The comments on those two
  entries (ADR-0031, the "no cycle" notes) are kept and extended to say why the entries are
  path-only. Researcher to confirm: `cargo package`/`cargo publish` behaviour for path-only
  dev-dependencies on the pinned toolchain/MSRV, and whether `cargo-deny`, `cargo semver-checks` or
  the `check-release-consistency` gate object to a path-only workspace dev-dependency.
- **Whether path-only becomes a workspace-wide rule.** `paladin-herald` → `paladin-ports` and the
  root package's `paladin-eval` are also *versioned* workspace dev-dependencies; both are correctly
  ordered today. Default: do not touch them in this phase (smallest diff on a release branch); the
  new gate is what protects them. Record the observation as a finding.
- **Ordering gate depth — default: a static assertion.** For every `CRATES` position, each
  *versioned* workspace dependency of that crate — normal, build **and dev** — must appear earlier
  in the array; crate set and edges derived from `cargo metadata`, array read through
  `scripts/publish-crates.sh`'s `PUBLISH_CRATES_LIB_ONLY=1` sourcing seam (never a second
  hard-coded copy of the order). It also asserts the array and the `cargo metadata` publishable set
  are equal. No live-index per-crate rehearsal — it cannot pass before siblings are published.
- **Proving the gate red on `1d4a9724`.** The evidence must show the gate failing on the
  `v0.10.0` manifests (a fixture copied from that tree, or a run against a `git worktree` of
  `1d4a9724`) naming `paladin-battalion` → `paladin-llm`/`paladin-storage`, and passing on the
  fixed tree. How that is staged is the planner's call.
- **Script fix form.** Any replacement for line 79 with no early-closing reader under `pipefail`
  (parameter expansion `${raw%%$'\n'*}`, a here-string, or `sed -n '1p'` reading to EOF). The
  regression test extends `tests/scripts/create-or-reuse-release_test.sh` with a stubbed `gh`
  response well over 64 KiB and must fail on the old line. Sweep the other release scripts for the
  same `| head`/`| grep -q`-under-`pipefail` shape and record what is found; fix only within SC2's
  intent, otherwise record as a finding.
- Where the gate is wired in CI (an existing job vs a new step), its script name, and whether it
  joins `check-gates`.
- `CHANGELOG.md` `[0.10.1]` wording and whether `[0.10.0]` gets a dated "partially published"
  note; per-crate changelog entries for a no-source-change patch.
- Plan count and wave layout, provided the split is: build wave → re-seal + PR + sign-off →
  **maintainer merge + tag checkpoint** → post-tag wave (verify, yank checkpoint, release banner,
  record, close PR).
- If `main` moves before the merge: update the branch, re-run the re-seal from the top, and the
  maintainer re-confirms §13 against the new SHA.
