<objective>
Close G-50-5b (WINDOWS row 75) the way the owner chose (option (a), UAT test 5): the OpenAI adapter always
sends its output-token limit as `max_completion_tokens`, on the chat path and the vision path, with the
Paladin-side config and parameter names left as `max_tokens`.

Purpose: `gpt-5.4-nano` -- the first seeded OpenAI model -- rejects `max_tokens` with HTTP 400
`unsupported_parameter`, and the defaults guarantee a limit is always present, so every request to it fails
today. That breaks PARITY-04 (the seeded model is unusable) and the config-only swap PARITY-03 promises. Root
cause and full site list: `.planning/debug/openai-max-completion-tokens.md`.

Output: the wire-key rename on `OpenAIRequest` and `OpenAIVisionApiRequest`, flipped wire tests plus a
`gpt-5.4-nano` body test on all three request paths, the smoke harness pointed at `gpt-5.4-nano`, docs,
changelogs, a MIGRATION 9.1 row, ADR-0061's stated limit updated and WINDOWS row 75 fixed.
</objective>
