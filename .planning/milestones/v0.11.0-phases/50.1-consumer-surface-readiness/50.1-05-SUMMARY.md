# Phase 50.1 Plan 05: OpenAIConfig default model and `new(api_key, model)` Summary

**`OpenAIConfig` now names its default model on every construction path (`new(api_key, model)`, `from_env()` -> `OPENAI_DEFAULT_MODEL`, the layered bridge) as a validated, redacting-`Debug` label that changes no adapter-wide limit, with every call site and the measured `method_parameter_count_changed` register entry landed in two commits: `9913ecff` (tracer, additive) and `32c22201` (the one-way constructor change).**

## D-06 reading applied: `proceed-as-locked`

The owner answered the plan 50.1-02 checkpoint with `proceed-as-locked` on 2026-10-20, and this plan applied that reading. The plan's wording that D-06's field "feeds the window chain" is **not** adopted: `OpenAIConfig.model` is a stored default-model label only. `declared_capabilities` is byte-for-byte untouched (the diff of both commits shows no change inside it), the OpenAI adapter-wide window stays `context_window` or 128,000, and `model_overrides` / seeded per-model windows work exactly as before. Test `openai_config_model_changes_no_adapter_wide_limit` builds adapters on `gpt-4o-mini` and `gpt-5.4-nano` and asserts both report `get_capabilities().max_context_tokens == Some(128_000)`. The MIGRATION section 9.2 row states "changes no adapter-wide limit" and that D-06's premise that the field feeds the window chain is not adopted; no section 9.8 window bullet was added because nothing about the window changed.
