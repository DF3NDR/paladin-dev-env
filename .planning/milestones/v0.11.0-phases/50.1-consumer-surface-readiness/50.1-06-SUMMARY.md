# Phase 50.1 Plan 06: AnthropicConfig `new(api_key, model)` and the SURFACE-02 seal Summary

**`AnthropicConfig::new` now takes `(api_key, model)` with `max_tokens` fixed at the compiled 4,096 for every model (owner decision `compiled-default`), the endpoint in the new `ANTHROPIC_DEFAULT_BASE_URL`, every call site and the muster pin migrated in `038bd200`, and `f30eee22` seals SURFACE-02: a final cargo-semver-checks run maps exactly the seven changed `new` fns to their registered lint, DR-19 names all seven types plus the two endpoint-only exceptions, section 9.8's muster paragraph records D-10/D-11, and the harmonise todo is resolved.**

## Checkpoint decision (D-07)

Task 1 (`checkpoint:decision`, one-way door) was put to the owner and answered on 2026-10-20, recorded verbatim:

> `compiled-default` -- `AnthropicConfig::new(api_key, model)` always sets `max_tokens` to the compiled default `ANTHROPIC_DEFAULT_MAX_TOKENS` (4,096) for every model, the same value `from_env()` and the layered path produce; the seeded maximum output is reachable only through `with_max_tokens`.

No live-check lines were supplied (the optional `live_vendor_smoke` run with `ANTHROPIC_MAX_TOKENS=128000` was not run, and no vendor key exists in this environment), so flagged assumption A1-50.1-06 (whether a non-streaming request with `max_tokens: 128000` is accepted) stays unverified; under this answer nothing sends that value by default, so the risk it described (threat T-50.1-17) does not arise from `new`.

Implemented exactly: `new` sets `ANTHROPIC_DEFAULT_MAX_TOKENS`; there is no `registry::seeded_max_output` helper (`grep` finds no such fn, only three unrelated test names containing the words); `from_env()`'s 4,096 default and its variables are untouched; `with_max_tokens` remains the override; the wire field stays mandatory and is still checked against the model's maximum output. The `new` rustdoc, the field doc, the MIGRATION row and the switching-providers page each state the 4,096 default and point at `with_max_tokens`.
