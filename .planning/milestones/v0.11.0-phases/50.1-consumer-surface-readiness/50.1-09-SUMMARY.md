## The `grok-4.7` exception (named per the owner's ruling)

`grok-4.7` is seeded although its `temperature=2.00` probe never produced a response. It failed identically in both runs (run 1 and run 2: `UNREACHABLE: error sending request`), as it does for `grok-4.3`, `grok-4.5` and `grok-4.6`; 0.00 and 0.50 were ACCEPTED in both runs and 2.01 was a clean 400 ("Temperature must be less than 2 but temperature = 2.01"), which establishes the vendor's 0..2 range. The owner ruled that a reproducible vendor-side failure at the top endpoint, seen identically in two independent runs, counts as a measured outcome for that one row. The row is `Range(0.0, 1.99)`: the registry's range type is inclusive on both ends, so "below 2.00" is expressed the way the existing `grok-4.3`/`4.5`/`4.6` rows express it (the largest value under the vendor's stated bound). I read the existing rows and the adapter before choosing: `ParamSupport::admits` has no epsilon, so 2.00 is refused at build. The fallback to "the highest ACCEPTED observed value" (0.50) was not needed because the type can express a bound below 2.00; 1.99 itself was not probed for `grok-4.7` and the comment, the docs footnote `[i]`, the Grok table doc comment, the ADR-0061 pointer line, MIGRATION section 9.8 and both CHANGELOGs say so. Max output is unset (owner: docs "No text output limit"). It applies to `grok-4.7` only and changes no existing row. Pinned by `grok_4_7_seeded_temperature_range_excludes_2_00` (registry) and `grok_4_7_profile_does_not_admit_temperature_2_00` (through the adapter), which also asserts the two `grok-4.20-*` rows still admit 2.0.
