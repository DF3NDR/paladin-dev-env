## Summary

I reviewed the diff against `a1128fc1` for the 45 files, with immediate context around the changed
lines. I also cross-checked the seeded rows against `50.1-SEED-PROBE.md`.

The mechanical work holds up. All seven `*Config::new(api_key, model)` constructors and the knob
builders are consistent. Credential handling is unchanged: `OpenAIConfig`'s `Debug` still redacts
the key, and every client still uses `Policy::none()`. There is no `unwrap`/`expect`/`panic` in
non-test library code in the diff.

I parsed every probe table in the transcript and compared the probe outcomes with the seeded
temperature, top_p, stop and penalty shapes for the OpenAI, Anthropic, DeepSeek, Gemini, Qwen and
Grok rows. They agree. That includes the fixed-temperature versus span split for OpenAI, the

Gemini output limits I checked also match the listing.

constructors, one evidentiary misstatement behind the `grok-4.7` exception, one overstated
validation guarantee on the new `with_base_url` builder, and a misleading CI comment. Details

## Warnings

### WR-01: `new(api_key, model)` docs promise a default-model fallback that no adapter implements

**File:** `crates/paladin-llm/src/kimi/adapter.rs:189`, `crates/paladin-llm/src/deepseek/adapter.rs:193`,
`crates/paladin-llm/src/grok/adapter.rs:180`, `crates/paladin-llm/src/gemini/adapter.rs:333`,
`crates/paladin-llm/src/anthropic/adapter.rs:231`, `crates/paladin-llm/src/qwen/adapter.rs:280`
(and the field doc at `crates/paladin-llm/src/anthropic/adapter.rs:126`)

**Issue:** Each of the six new `new` rustdocs says `model`: "the default model requested when a
call names none". No code path does that. `config.model` is read only by `validate()` (non-empty
check) and by `default_timeout_seconds` at construction. Every request builder uses
`request.model` directly: `anthropic/adapter.rs:519`, `deepseek/adapter.rs:588-598`,
`gemini/adapter.rs:605-615`, and `compat/engine.rs:601-650` for Kimi, Qwen and Grok. A caller who
passes a model to `new` and then sends an `LlmRequest` with an empty model gets a vendor 400
instead of the "default". The OpenAI doc is accurate: it says each request's own model decides.

This phase makes `new(api_key, model)` the headline constructor, so a doc contract that does not
exist is a real hazard. Either the docs must change, or the fallback must be implemented.

**Fix:** Make the docs honest, matching the OpenAI wording:
```rust
/// - `model`: the adapter's default model. It selects the timeout default (300 s for a seeded
///   reasoning model, 60 s otherwise); each request's own `LlmRequest.model` decides what is
///   sent on the wire.
```
Apply the same wording to the `model` field docs. If the fallback is wanted, add
`let model = if request.model.is_empty() { &self.config.model } else { &request.model };` at each
request builder, with tests.

### WR-02: The `grok-4.7` exception misstates the transcript evidence for its sibling rows

**File:** `crates/paladin-llm/src/registry/seeded.rs:1877`, `docs/src/user-guides/switching-providers.md:351`
(also `50.1-09-SUMMARY.md:89`)

**Issue:** The seeded.rs comment says "The same row fails for `grok-4.3`, `grok-4.5` and
`grok-4.6`". The docs footnote [i] says "The same probe failed for `grok-4.3`, `grok-4.5` and
`grok-4.6`". The 2026-10-20 transcript says otherwise. Probe 3 (`temperature=2.00`) for the
2026-10-20 runs reads:
- `grok-4.6`, run 1: ACCEPTED (200).
- `grok-4.5`, run 1: REJECTED (500) "Internal error during token parsing".
- `grok-4.3`: UNREACHABLE in both runs.

I confirmed this by parsing the probe tables. `50.1-SEED-PROBE.md` also lists these as "Differences
found" and defers them to plan 50.1-08. The owner's ruling rests on "reproducible vendor-side
failure ... in two independent runs". The written justification inflates that premise by claiming
the failure is shared across all four Grok rows. Two of the three siblings did not fail identically.
One returned an accepted 2.00, which is positive evidence the vendor does take 2.00 on a sibling.

I am not overriding the ruling or the 1.99 cap. The defect is that the permanent comments and
docs record evidence the transcript contradicts. Separately, `grok_4_6` still reads
`Range(0.0, 1.99)` with a comment that says only "a transport error, three times", even though it
now has an accepted 2.00 observation.

**Fix:** Reword the two passages to the transcript:
```text
`temperature=2.00` was UNREACHABLE for grok-4.3 (both 2026-10-20 runs) and grok-4.7 (both runs);
grok-4.6 ACCEPTED it in run 1 and was UNREACHABLE in run 2; grok-4.5 answered 500 in run 1 and
was UNREACHABLE in run 2.
```
Add a short note on the `grok_4_6` and `grok_4_5` rows that the 2026-10-20 observations differ
from the seeded 2026-10-15 basis. This matches the 50.1-08 "plan decides" deferral.

### WR-03: `with_base_url` docs promise `http`/`https` validation that seven of nine adapters do not perform

**File:** `crates/paladin-llm/src/registry/mod.rs:227`; weak checks at
`openai/adapter.rs:274`, `deepseek/adapter.rs:234`, `kimi/adapter.rs:230`, `grok/adapter.rs:221`,
`qwen/adapter.rs:321`, `ollama/adapter.rs:184`, `openai_compatible/adapter.rs:545`

**Issue:** The shared builder doc says: "The value is checked to be an `http` or `https` URL when
the adapter is built, and an empty or other-scheme value fails construction." The new
`with_base_url` builder is public on all nine configs, and the credential header goes wherever it
points. Only Anthropic (`:278`) and Gemini (`:375`) test `starts_with("http://") ||
starts_with("https://")`. The other seven test `starts_with("http")`. That accepts `httpx://host`,
`http-gateway.internal/v1` (no scheme) and `httpfoo:`, so the "other-scheme value fails
construction" guarantee is false for them.

The DeepSeek test `a_builder_set_non_http_base_url_fails_deepseek_construction` hides this. Its
cases (`ftp://x`, `""`, `api.deepseek.com/v1`) all start with something other than `http`. No test
covers `httpx://`. The practical impact is bounded, because reqwest later fails on a malformed URL.
But the documented guarantee, and the redirect/credential-safety reasoning built on it, is not
what the code enforces.

**Fix:** Share one check and use it in all nine `validate()` methods:
```rust
pub(crate) fn is_http_url(url: &str) -> bool {
    url.starts_with("http://") || url.starts_with("https://")
}
```
Add a case such as `"httpx://x"` to the construction-failure test. If the weaker check is
deliberate, reword the builder doc to "must start with `http`".

### WR-04: CI muster job comment contradicts the Makefile, and the zero-test guard can exit silently

**File:** `.github/workflows/ci.yml:1700-1731` (comment at 1707, guard at 1722-1728);
`Makefile:241-243`

**Issue:** There are two problems.

1. The job comment says Cargo "silently skips a target whose features are inactive (no error,
   zero tests run), hence the zero-tests guard". The Makefile comment for the same target says the
   explicit `--test consumer_surface_muster` form "fails loudly if the consumer's provider
   features are off", and so does the root `Cargo.toml` `required-features` comment. The explicit
   `--test` form does fail loudly, so the stated rationale for the guard is wrong. The guard was
   copied from the `cli-tests` job, where the target is selected differently.
2. GitHub's `shell: bash` runs `-eo pipefail`. In `executed=$(grep ... | tail -1 | grep -oE ...)`
   a no-match makes the pipeline fail, and with `-e` the step aborts on the assignment before the
   `::error::` message can print. The helpful diagnostic is unreachable in the one case it is
   written for.

**Fix:** Correct the comment. Either drop the guard, since `--test` already errors, or make it
reachable:
```bash
executed=$(grep -oE 'test result: ok\. [0-9]+ passed' consumer-surface-output.log | tail -1 | grep -oE '[0-9]+' || true)
```

### IN-01: `tests/consumer_surface_muster.rs` pins the new `new(api_key, model)` shape for only two of seven configs

**File:** `tests/consumer_surface_muster.rs:446-456,523-530`

**Issue:** SURFACE-02 changed seven constructors. The muster pins `AnthropicConfig::new` and
`DeepSeekConfig::new`. Its `required-features` are only `llm-anthropic` and `llm-deepseek`, so
`OpenAIConfig::new` (arity 1 to 2, the largest signature change), Kimi, Qwen, Grok and Gemini are
not guarded. The doc comment on `phase_50_1_config_shapes` says "pinned on `DeepSeekConfig`",
which is accurate but does not make the other six safe against a later re-break.

**Fix:** Add `#[cfg(feature = "llm-openai")]`-gated `let _new: fn(String, String) -> OpenAIConfig
= OpenAIConfig::new;` pins for each remaining config. Add the features to the target's
`required-features`, or gate each pin on its own feature.

`tests/integration/vision_integration_test.rs:139,167`,
`tests/integration/anthropic_provider_test.rs:20,36,77,186`

### IN-03: Anthropic `reasoning` is seeded by a different criterion than Grok and Gemini

**File:** `crates/paladin-llm/src/registry/seeded.rs` (Anthropic rows versus `grok_4_5`, `grok_4_7`
and the Gemini rows)

**Issue:** Grok rows are `reasoning: true` when the listing declares `reasoning_effort`, even if the
default call carried no reasoning text (`grok_4_5`). Gemini rows use listing `thinking=true`.
Anthropic rows use only "default call returned reasoning text". The comment says the Anthropic
listing `capabilities` were truncated in the transcript. So the `reasoning` column, which drives
the 300 s versus 60 s `new` timeout, is not defined consistently across vendors. Two Anthropic
rows get 300 s and the other eight stay at 60 s, although all expose the same thinking features.

**Fix:** State the criterion per vendor in the seeded.rs header and in the switching-providers
page. Or revisit the Anthropic rows once the listing capabilities are re-captured untruncated.

### IN-04: `build_openai` in the live smoke harness does not use the new `OpenAIConfig.model`

**File:** `crates/paladin-llm/examples/live_vendor_smoke.rs:270-277`

**Issue:** `OpenAIConfig` now carries `model`, but `build_openai` still hand-builds `Built` with
the constant. Every other builder reads `cfg.model` through `build_fn!`. If `from_env` ever honours
a model variable, the harness will silently ignore it.

**Fix:** `let (api_key, base_url, model) = (cfg.api_key.clone(), cfg.base_url.clone(), cfg.model.clone());`
and use `model` in `Built`.

### IN-05: `method_parameter_count_changed` is suppressed crate-wide

**File:** `crates/paladin-llm/Cargo.toml` (lint table), `.cargo/semver-checks-allowlist.toml`

**Issue:** Each new allowlist entry notes "Suppressed by the crate-wide allow line". The lint is
allowed for the whole crate, so any future unregistered parameter-count change in `paladin-llm` is
also silently allowed. The allowlist register mitigates this only if reviewers cross-check
it. The measured justification for these seven entries is thorough.

**Fix:** Remove the crate-wide allow after the 0.11 release cut, or keep a CI check that every
fired lint has an allowlist entry (as `check-migration-allowlist` may already do). Confirm that
guard covers this lint name.

### IN-06: `prelude` growth adds nine generic short names

**File:** `src/prelude.rs:32-44`

**Issue:** The prelude now exports `Aegis`, `ErrorHandlerSpec`, `TimeoutPolicy`, `StateDelta`,
`NodeError`, `NodeErrorSource`, `TimeoutKind`, `NodeId` and `Transience`. Adding names to a
glob-imported prelude is a semver-sensitive change. Two glob imports that both supply `NodeId` or
`TimeoutKind` become an ambiguity error at the use site. `make api-surface` and
`.project/current-exports.txt` cover this, and the change is intentional (SURFACE-01). Mention it
in the CHANGELOG under Breaking or Changed, not only Added.

**Fix:** Add a CHANGELOG line for the root `paladin` crate noting the prelude additions and the
possible glob-import ambiguity.

### IN-07: Doc formatting artefacts from the in-place rewrites

**File:** `crates/paladin-llm/src/anthropic/adapter.rs:130-134`,

### IN-08: Layered-path errors now name a model the caller did not state (OpenAI)

**File:** `crates/paladin-llm/src/config/layers.rs:356-371`, `crates/paladin-llm/src/provider_factory.rs:112-115`

**Issue:** `provider_factory.rs` was edited with a comment that a message "names only what was
stated". `resolve_layers` now substitutes `OPENAI_DEFAULT_MODEL` before it computes
`subject(provider, model)`. A missing OpenAI key or a bad base URL on the bridge path will
therefore read "provider 'openai' (model 'gpt-5.4-nano')" even when the caller named no model. This
already holds for Anthropic and DeepSeek. The new comment is only true for the factory's own
labels, so the two statements are inconsistent.

**Fix:** Either accept it and narrow the factory comment to "the factory's own labels", or compute
`subject_text` from the stated model before the compiled default is substituted.
