<planner_decisions>
- **PD-12-1 (placement and mapping).** The orchestrator asked for `settings.validate()` "immediately after the config load, mapped to the existing boot-refusal path". `load_settings` is that load step. `run()` calls it first, and its `Err` reaches `main()`'s `paladin-server failed to start: {e}` line, the same path every other boot refusal takes. The prefix is `invalid configuration: `, the house `invalid <section> configuration:` shape for a whole-file check. The validator's own message supplies the key.
- **PD-12-2 (double validation, decided).**
  - `agent_runtime`: checked with `git grep`, no non-test `agent_runtime.validate()` exists, and `validate_config` only walks `agents`. It is therefore validated exactly once after this plan, with no double work.
  - The treasurer: the existing standalone check stays first and byte-identical, so a bad treasurer still reports `invalid treasurer configuration: …`. `Settings::validate()` then re-runs `TreasurerConfig::validate()`. That call is pure (it reads the same `APP_TREASURER_*` environment in the same process) and cheap (no I/O), so it cannot fail once the first check passed.
  - This mirrors today's existing cadence re-check in `build_cadence`. Removing the standalone check would change a shipped refusal message for no defect.
  - `load_settings`'s rustdoc records this, and `load_settings_keeps_the_treasurer_refusal_first` pins it.
- **PD-12-3 (the `paladin` binary is out).** `src/config/setup/` reads none of `trace`, `web_server`, `agent_runtime` or `treasurer`. Validating them there would refuse configs over sections that binary never uses: a behaviour change without a defect.
- **PD-12-4 (file value only).** No production code calls `TraceConfig::apply_env_overrides`, `AgentRuntimeConfig::apply_env_overrides` or `WebServerConfig::apply_env_overrides` on the server's `Settings`. So `validate()` judges exactly the values the server runs on. The overlays MIGRATION.md section 9.5 documents (`PALADIN_TRACE_*`, `APP_AGENT_RUNTIME_*`) are therefore never applied. That is a candidate new finding, handed back to the orchestrator for the log (D-01, D-04, D-00e) and not fixed here (P-12-2).
- **PD-12-5 (two tasks).** The whole code change is one file and one call. Task 1 carries it end to end with every regression test watched failing first. Task 2 is records, gates and the log, so the plan stays at two tasks.
</planner_decisions>
