<planner_decisions>
- **PD-15-1 (filter in `minimum_delay`, not in `delay_for`).** The zero is filtered where the adapter reads the provider's delay, so `CadencePolicy::delay_for` and its pinned test (`cadence_port.rs:599`, a non-zero delay below base is never raised) stay untouched, and `paladin-ports` stays out of scope (P-15-4). The filter covers both sources (explicit `Retry-After`/`retry-after-ms` and reset-derived), because both reach the port through `err.retry_after()`.
- **PD-15-2 (spawn and await).** `note_failure` spawns the record on the current runtime (`tokio::runtime::Handle::try_current()`), with an owned `Arc<dyn CadencePort>` clone, a `CadenceKey` clone and the minimum, and awaits the `JoinHandle`. Awaiting keeps today's ordering for a call that completes (the next call's gate read sees the record), and spawning means a dropped caller cannot cancel the record. The spawned task logs its own port error with one `warn_port_error` line from a fresh `warned` flag; the caller logs a `JoinError` at `warn` under `CADENCE_LOG_TARGET`. With no runtime handle the record runs inline as today. Rejected: an in-process mirror written synchronously before the first await: it would cover only the in-process port, not the Redis fleet gate the finding is about.
- **PD-15-3 (WINDOWS phase column).** `--phase 43`.
</planner_decisions>
