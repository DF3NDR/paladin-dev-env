<planner_decisions>
- **PD-16-1 (cap the marker; the smaller side).** Lengthening or refreshing the counter cannot be bounded: the marker scales with the entry TTL, which has no upper bound here, and the node cache never learns the counter's key. Capping the marker is local to `put_fenced`, provable for every lock TTL (`L + 30 min <= max(10 L, 1 h)` for all `L >= 0`), and leaves the lock and the counter untouched (P-16-3). The cost: for an entry TTL above 15 minutes the marker can expire before the entry, so a late holder's write of the same node result is accepted after 30 minutes. ADR-0058 (g) already treats a late write of the deterministic result as acceptable (last-write-wins under the in-process Cadence).
- **PD-16-2 (the floor).** `FENCE_MARKER_FLOOR` = 5 minutes, 2.5 times the default 120 s `lock_ttl_secs`, so a short entry's marker still outlasts a default holder's lock window. It replaces the old one-hour floor, which cannot coexist with a ceiling of 30 minutes.
- **PD-16-3 (shared module and feature gates).** `pub(crate) mod redis_fence` is declared in `lib.rs` under `#[cfg(any(feature = "redis-cache", feature = "redis-cadence"))]` (the `redis_url` precedent). Inside it: `MIN_FENCE_COUNTER_TTL` has no further gate (both sides use it); `FENCE_TTL_FACTOR` and `fence_counter_ttl_ms` are `#[cfg(any(feature = "redis-cadence", all(test, feature = "redis-cache")))]` (the cadence adapter, plus the node-cache tests); `FENCE_MARKER_FLOOR`, `FENCE_MARKER_CEILING` and `fence_marker_ttl_ms` are `#[cfg(feature = "redis-cache")]`; any private helper carries the gate of its users. No single-feature build, test or not, then has dead code, and clippy `-D warnings` stays clean.
- **PD-16-4 (extract, then red).** Task 1 first moves both computations into `redis_fence.rs` with today's bodies (behaviour-preserving, all existing tests green), so the invariant test fails at runtime with a real assertion rather than a compile error; only then does the marker body change.
- **PD-16-5 (live test without the cadence feature).** CI's node-cache job builds with `redis-cache` only, so the live test does not take a lock through `RedisCadence`. It reproduces the prior epoch by writing token 3 directly, takes the counter TTL from the shared `fence_counter_ttl_ms` (the one source of truth), and shifts the marker's remaining lifetime by the same amount the counter would have aged, then proves the token-1 write is accepted.
- **PD-16-6 (WINDOWS phase column).** `--phase 43`.
</planner_decisions>
