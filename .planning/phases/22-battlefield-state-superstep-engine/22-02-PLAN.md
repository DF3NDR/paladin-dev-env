<assumption_delta_decision>
**Noun now primary:** *dispatch rule* — a per-field merge function on the Battlefield.

**Signal:** the phase scope moves `DispatchRule` from a derived, closed set of built-in behaviors to
a **chosen** one: `Custom(String)` names a rule resolved at runtime through an engine-level registry
(ENG-FR-09), so the set of dispatch rules is open at the application layer.

**Decision: add-alongside.** The four built-in rules (`LastWrite`, `Append`, `MergeObject`, `Sum`)
stay first-class enum variants implemented in `paladin-core`; `Custom(String)` is added alongside
them as a fifth variant whose resolution is delegated to a caller-supplied resolver. The built-ins
are NOT promoted into registry entries.

**Rationale:** promoting all five to registry lookups would put executable closures on the core
domain path and make `paladin-core` depend on an application-layer registry, violating X-01 and
ENG-FR-09's explicit "registration lives in the engine, never in `paladin-core`."

**Accepted debt:** two resolution paths exist for one concept — an exhaustive `match` for built-ins
and a map lookup for `Custom`. A schema author cannot override `LastWrite` semantics by registering
a rule of that name.

**What would force a later promote:** a requirement to override or shadow a built-in rule's
semantics per graph, or a second consumer of the built-in merge functions outside `Battlefield::merge`.
An invariant test worth adding: registering a custom rule whose name collides with a built-in variant
name is rejected at graph validation rather than silently ignored.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| node delta -> Battlefield merge | Arbitrary JSON from a node (possibly LLM-generated) enters shared typed state |
| custom resolver closure -> merge | Application-supplied executable code runs inside the core merge path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-04 | Information Disclosure | `BattlefieldError::TypeMismatch` / `UnknownField` | medium | mitigate | Variants carry field names and type names only; a unit test asserts no error `Display` string contains a value written into state, so a credential or PII placed in a field cannot leak through an error path |
| T-22-05 | Denial of Service | `Append` / `MergeObject` field growth | low | accept | Growth per run is bounded by `EngineLimits.max_supersteps` and `max_node_visits` (ENG-FR-03) and storage growth is bounded by `WaypointRetentionConfig` (ENG-FR-18, Plan 22-06); no additional per-field cap is required by the PRD |
| T-22-06 | Tampering | custom dispatch resolver returning arbitrary state | medium | mitigate | An unregistered name is a hard `CustomDispatchNotRegistered` error rather than a silent fallback to a built-in rule, so a typo cannot quietly change merge semantics; the resolver's return value is still schema-checked before being stored |
</threat_model>
