<objective>
Close gap G-22-3 (BUG-02) by implementing ENG-FR-02a: eligible-set reachability validation on
`WarGraph::validate`.

ENG-FR-02 removed toposort so cycles could be expressed, and did not add a replacement
connectivity check. The consequence is the silent stranded node: a non-entry node whose only
incoming edges trace back to itself can never become ready, `validate` accepts the graph, and the
run reports `Completed` as though the whole graph executed. That is a truthful-outcome violation,
and everything downstream — the Chronicle, trace export, the eval harness — reads that outcome as
fact.

The strongest evidence the defect is real is that the test suite is shaped around it. This plan
adds the check; plan 22-16 does the fixture audit acceptance 2a requires.

Purpose: make it impossible for a run to report completion over a node that could never have run.
Output: reachability validation listing every offender at once, an explicit dynamic-target
escape hatch, and regression tests that fail before the fix and pass after it.
</objective>

  <action>
Add the error variant to `EngineError` in `crates/paladin-battalion/src/engine/mod.rs`. Carry
**all** offenders in one variant rather than one node per error — ENG-FR-02a permits either shape
and states a preference for listing all, and the UAT requires all offenders in one error. Include
a reason string that explains the eligible-set rule and names the two ways to fix it: make the
node reachable from entry, or mark it as a dynamic target. Follow the enum's existing
`thiserror` conventions and its `#[non_exhaustive]` posture if present.

Add the dynamic-target marker to `WarGraph`. Realise it the way this codebase already realised
`defer` — a `HashSet<NodeId>` of marked ids, a builder method, and an `is_` accessor — rather
than as a new field on `NodeSpec`, which is an enum whose variants would each have to carry it.
Provide the marker as a method that marks an already-registered node, so a node can be both
deferred and a dynamic target; that composability is why marking is preferable to a second
`add_*_node` constructor here, and the rustdoc should say so.

Rustdoc the marker with three things the requirement is explicit about:
- it is the declared escape hatch for nodes reachable only as the target of a runtime jump;
- it shifts responsibility for checking those targets to the later phase that owns runtime jump
  validation (CF-FR-07), and names that;
- jump targets are deliberately **not** inferred from any directive parser, because those targets
  are runtime values and inference would be unsound. Say this in the doc, because the omission
  looks like a gap to anyone who does not know it was a decision.

Implement the eligible-set computation in `validate`:

- Seed a worklist with the entry nodes and every node marked as a dynamic target.
- Expand by following declared edges from each eligible node to its targets, ignoring edge
  conditions — conditions are runtime values, and a statically-declared edge is what proves
  intent here.
- Continue until the worklist empties; this is the fixed point ENG-FR-02a asks for, and a
  worklist gives it naturally.
- Document the two future sources of eligibility as insertion points into this same worklist,
  each naming its owning phase: nodes marked as worker templates, reachable via dynamic fan-out
  (Phase 23), and nodes named as route targets in an eligible node's error-handler policy, which
  is why the computation must be a fixed point rather than a single pass (Phase 25). Neither
  concept exists in the tree today — do not fabricate a field, a flag or a stub type for either;
  document where they plug in and stop there.
- Every declared node outside the eligible set is an offender. Emit them in the graph's
  registration order so the message is deterministic, and return them all in one error.
- When the graph declares nodes but no entry point, every node is trivially ineligible; detect
  that case and set the reason to name the absent entry point as the cause, because listing every
  node in the graph with a generic reachability message would bury the actual mistake.

Order the new check **last** in `validate`, after the limit checks, the undeclared-endpoint
checks and the custom-dispatch registration check. Two reasons, both worth a comment: the more
specific structural errors stay the ones a caller sees, and a graph that fails an earlier clause
has not yet been shown to have meaningful reachability at all.

Leave completion semantics alone. A run still completes when the frontier empties; what changes
is that validation now guarantees every declared node was at least eligible, so that outcome can
no longer be a lie. Say that in the `validate` rustdoc, and update the type-level doc on
`WarGraph` that currently enumerates what validation does and does not reject — it explicitly
says cycles are permitted and lists the checks, and it is now incomplete.
  </action>
