# Phase 22.1 Plan 02: Engine readiness typed guards (BUG-03 defense-in-depth) Summary

**Added `EngineError::UnschedulableCycle` (validate-time) and `EngineError::StarvedNodeAtCompletion` (run-end) as a two-layer typed defense against BUG-03's silent-lie class, plus the deferred-node starvation tier the run-end check requires to stay honest, all test-first with 20-iteration determinism coverage over both new cycle-bootstrap shapes.**

## Performance

- **Duration:** ~55 min
- **Started:** ~2026-09-03T00:15Z (approx, following Plan 22.1-01's completion)
- **Completed:** 2026-09-03T01:06Z
- **Tasks:** 3
- **Files modified:** 4

## Accomplishments

- Added `EngineError::UnschedulableCycle { nodes, reason }` and `EngineError::StarvedNodeAtCompletion { nodes, reason }`, each with full `UnreachableNode`-grade rustdoc explicitly distinguishing the two failure classes: a validate-time "this shape cannot be scheduled" failure decided before any node runs, versus a run-end "the engine's own invariant broke" failure decided after a run's own Vanguard emptied.
- Added `WarGraph::unschedulable_unfed_nodes()`: a fixpoint identifying every declared node in a component that can never receive a fired edge from outside itself (and therefore can never be bootstrapped by the ENG-FR-06a starvation release), exempting `mark_dynamic_target`-marked nodes. Wired into `validate()` via a new `validate_schedulable()` clause, called strictly AFTER `validate_eligible_set()` so every pre-existing `validate_prefers_*` ordering test keeps seeing its current error unmodified.
- Added `superstep::starved_at_completion(graph, frontier)`: D-04's independent run-end truthful-outcome check, deliberately NOT implemented by re-invoking `compute_next_vanguard`. Wired into BOTH places `run()` decides `Completed` (the empty-at-entry early return, and the mid-loop `next_vanguard.is_empty()` branch), returning a typed, checkpointed `StarvedNodeAtCompletion` failure instead of a false `Completed` when it finds a non-dead node still holding an unconsumed fresh fired incoming edge.
- Added `compute_next_vanguard`'s 4th tier, `starved_deferred_release`: the exact same starvation rule as the existing `starved_release` (extracted into a shared `starved_nodes(graph, frontier, deferred: bool)` helper), applied to `defer`-marked nodes instead of excluding them. Without this tier, a legitimately-declared aggregator caught in the same cycle-bootstrap starvation shape BUG-03 fixed for ordinary nodes would never be released, and the new D-04 check would (wrongly) fail the run over it.
- Added `eng_fr_08_determinism_over_twenty_randomized_iterations_for_cycle_bootstrap_shapes`, extending (not rebuilding) the existing 20-seed determinism harness to both Plan 22.1-01 cycle-bootstrap fixtures, asserting byte-identical final `Battlefield`, identical per-node `run_count()`s, and identical `RunOutcome` discriminants across all 20 iterations per shape.
- Regenerated `.project/current-exports.txt` via `scripts/extract-public-api.sh`; the `engine` module is not re-exported through the `paladin` facade crate the baseline tracks, so the content diff is empty apart from the generation timestamp -- confirmed current via `scripts/check-api-surface.sh`, which filters that line before comparing.
- Every pre-existing engine test passes unmodified: all 336 `paladin-battalion` lib tests, the four `validate_prefers_*`/`validate_rejects_self_loop_only_stranded_node_naming_it` ordering tests, E2E-1 (`tests/integration/e2e_crash_resume_test.rs`, 27 tests including `e2e_1_crash_resume_matches_control_run_with_no_reexecution`), and the pre-existing determinism test (diff confirmed purely additive).
- Full workspace `cargo fmt --check` and `cargo clippy --workspace --all-targets --all-features -- -D warnings` both clean.

## Decisions Made

See `key-decisions` in frontmatter above. Summarized:
- `unschedulable_unfed_nodes`'s fixpoint and `dynamic_target` exemption ordering follow D-03's exact 3-step description.
- `validate_schedulable` runs strictly after `validate_eligible_set` (D-02d ordering requirement) -- confirmed by a new test (`validate_prefers_unreachable_node_error_over_unschedulable_cycle`) pinning this ordering the same way the pre-existing `validate_prefers_*` tests pin theirs.
- `starved_at_completion` needs no `pending_from_live` check: under this `Frontier`'s data model, a `Pending` edge is provably from a source that has never executed even once (an executed source has ALL its outgoing edges resolved by `record_execution`), so `any_fresh_fire` alone is sufficient and matches the plan's literal helper spec.
- `compute_next_vanguard`'s 4-tier ordering preserves CONTEXT.md's recommendation: normal-ready -> non-deferred starvation release -> ordinary defer release -> deferred starvation release, so a `defer`-marked aggregator always prefers waiting for a released cycle node over rescuing itself.
- TDD gate commits were combined per task (impl + tests together) rather than split RED/GREEN, documented as a deviation below.

**2. [Process deviation, not a Rule 1-4 fix] TDD gate commits combined per task rather than split RED/GREEN**
- **Found during:** Tasks 1-3, all marked `tdd="true"`
- **Issue:** Plan 22.1-01 (the prior plan) split its TDD task into separate RED and GREEN commits. This plan's own `<action>` blocks write implementation steps before the test-addition step (e.g. Task 1's steps 1-3 add the enum variants and fixpoint, step 4 adds the tests), and the new tests directly reference new production symbols (`EngineError::UnschedulableCycle`, `WarGraph::unschedulable_unfed_nodes`, `superstep::starved_at_completion`, etc.) that must exist for the test module to compile.

**3. [Recovery, not a Rule 1-4 fix] Recovered from an interrupted pre-commit hook's auto-stash**
- **Found during:** Task 1's first commit attempt (before `--no-verify` was applied)
- **Issue:** The project's local pre-commit hook runs a full-workspace `cargo clippy`, which exceeded the 2-minute Bash tool timeout and was killed. The `pre-commit` framework's own auto-stash-on-unstaged-changes step (triggered because `superstep.rs` and `.project/current-exports.txt` were unstaged at the time, staged for a later task commit) had already run and was not restored when the process was killed.
- **Fix:** The `pre-commit` framework backs up its auto-stash as a patch file (not solely via `git stash`) at `~/.cache/pre-commit/patch<timestamp>-<pid>`. Located that file, confirmed its diff matched the exact intended pre-Task-2 working-tree state, and restored it with `git apply <patch-file>` (a non-destructive, read-then-apply operation — no `git stash pop`, `git checkout .`, or `git reset --hard` was used, per the destructive-git-prohibition). Confirmed via byte-identical `diff` against a scratchpad copy taken before the commit attempt. Subsequent commits used `git commit --no-verify`, which this worktree's orchestrator explicitly authorized (`workflow.worktree_skip_hooks: true`) since the orchestrator re-runs the full-workspace clippy on the merged tree after the wave.
- **Files modified:** none (recovery only; no code changes)
- **Verification:** `diff crates/paladin-battalion/src/engine/superstep.rs <scratchpad-copy>` exited 0 before proceeding; `cargo test -p paladin-battalion --lib engine::` (116 passed) and `cargo clippy -p paladin-battalion --all-targets -- -D warnings` (clean) both re-run after recovery, before any further commit.
