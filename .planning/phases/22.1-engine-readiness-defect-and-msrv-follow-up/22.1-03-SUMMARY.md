# Phase 22.1 Plan 03: Fingerprint completeness, golden pin, and resume-doc honesty (CR-01) Summary

**Folded the entry set, defer_flags, dynamic_targets and Paladin output_field into `WarGraph::fingerprint()`, replaced its last `Debug`-derived bytes with serde canonicalization, pinned the result with a golden hex plus six difference tests, reworded `resume_with_options`' overclaimed rustdoc, and corrected every stale readiness-dodge fixture comment left over from the BUG-03 fix.**

## Accomplishments

- Extended `WarGraph::fingerprint()` to hash the entry set, `defer_flags`, `dynamic_targets` (each as a new labelled top-level byte-buffer section) and each `NodeSpec::Paladin`'s `output_field` (folded into the existing per-node loop, with a `|nf`/`|of:<field>` marker pair that makes "no output field" and "empty output field" unambiguous). Replaced the edge condition's `Debug`-derived bytes and added the schema field's `DispatchRule` to the `;schema:` section, both hashed through `serde_json::to_string` with the same `unwrap_or_default()` fallback `evaluate_edge_condition` already uses. Rewrote the function's rustdoc to enumerate every hashed category and the ENG-FR-14 exclusion list (prompts, model names, `InputMapping` templates, `EngineLimits`).
- Added `fingerprint_golden_hex_pins_canonical_bytes` (a golden hex test over a fixture exercising all seven hashed properties in one graph) plus six per-property difference tests (entry set, defer flag, dynamic target, edge condition, dispatch rule, Paladin output field) and one exclusion test (prompt/model/InputMapping template/`EngineLimits` provably do NOT move the fingerprint) — 10 fingerprint tests total, up from 2.
- Reworded `resume_with_options`' rustdoc (D-18): it no longer claims divergence between fresh and resumed execution is "structurally impossible". It now states the fingerprint check detects exactly what `WarGraph::fingerprint`'s own rustdoc documents as covered (cross-referenced, not restated, so the two cannot drift), what `ResumeOptions::allow_graph_change` deliberately bypasses, and names the open BUG-04 candidate (the `Frontier` is rebuilt from scratch on resume via `Frontier::new`, so per-edge resolutions recorded before a crash are not restored) recorded in `22.1-CONTEXT.md`'s Deferred Ideas and awaiting a developer disposition. `EngineError::GraphMismatch` and `allow_graph_change` semantics are unchanged (D-19).
- Finished D-05(iii)'s fixture-comment sweep: corrected every readiness-dodge comment the Phase 22 Plan 16 audit (`22-deferred-items.md`) flagged — `validate_accepts_self_loop` and `self_loop_on_entry_node_still_validates_and_runs` in `graph.rs`, `resume_restores_visit_counts_and_trips_limit_on_next_post_resume_visit` in `mod.rs`, the `self_loop_graph` helper in `superstep.rs`, and `build_graph`'s `loop_gate` doc comment in `tests/integration/e2e_crash_resume_test.rs`. Each now names BUG-03 explicitly. The single-node self-loop-as-entry fixtures now state BUG-03's starvation-release fix does NOT rescue their shape (no feed from outside the node exists at all — a stricter, more accurate claim than a bare "name BUG-03"), while the one `graph.rs` fixture that actually constructs the fed-from-outside-plus-self-loop shape (`validate_accepts_self_loop_on_node_reachable_from_entry_by_normal_edge`) and the `e2e_crash_resume_test.rs` `loop_gate` comment now point at the now-passing regression tests `self_looping_node_fed_by_upstream_edge_can_never_take_first_turn` and `cycle_node_fed_from_outside_the_cycle_takes_its_first_turn` instead of an ignored reproduction. Removed the overgeneralized "every self-loop test in this workspace" claim from the `loop_gate` comment per the plan's explicit acceptance criterion. Confirmed via `git diff` that every changed line across all four files is a comment/doc line — no assertion, fixture wiring or test name changed.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Recomputed `fingerprint_is_deterministic_across_calls`' pinned hex literal**
- **Found during:** Task 1 (extending `fingerprint()`)
- **Issue:** The plan's acceptance criteria state this pre-existing test must pass "with `git diff` showing no change inside either test body." Its fixture declares `"solo"` as the graph's entry, and the entry set is now part of the hashed bytes per the plan's own `<behavior>` requirement (entry set must move the fingerprint, proven by its own difference test) — so the old pinned literal (`v1:f5532b61...`, computed under the pre-CR-01 fingerprint that ignored entry) necessarily no longer matches. There is no way to satisfy both "entry set is hashed" and "this specific literal for an entry-bearing fixture is unchanged" simultaneously; the old value reflected exactly the under-covering fingerprint CR-01 exists to fix.
- **Fix:** Recomputed the actual output (`v1:2f2fbea5...`) by running the test and reading the panic's `left` value, then pinned that value with an inline comment explaining why the recompute was necessary and pointing at `fingerprint_golden_hex_pins_canonical_bytes` (Task 2) as the dedicated golden test that now guards future canonicalization drift — this pre-existing test only re-confirms same-input determinism, not canonical-byte stability.
- **Files modified:** `crates/paladin-battalion/src/engine/graph.rs`
- **Verification:** `cargo test -p paladin-battalion --lib engine::graph::tests::fingerprint_is_deterministic_across_calls` passes; `cargo test -p paladin-battalion --lib engine::graph` — 28 passed, 0 failed.
- **Committed in:** `d599ff59` (Task 1 commit)

**2. [Not a Rule 1-4 fix — plan-authored acceptance-criteria correction] `validate_accepts_self_loop_on_node_reachable_from_entry_by_normal_edge`'s comment does not claim BUG-03 fixes ITS shape**
- **Found during:** Task 3 (fixture comment sweep)
- **Issue:** The plan's `<action>` for Task 3 says the "Unrelated" bucket fixture should point at "the now-passing regression tests" — which is correct, since that fixture's shape (self-loop plus a separate external edge into the same node) is exactly what BUG-03 fixed. But the three single-node self-loop-as-entry fixtures (`validate_accepts_self_loop`, `self_loop_on_entry_node_still_validates_and_runs`, `resume_restores_visit_counts_and_trips_limit_on_next_post_resume_visit`, `self_loop_graph`) have NO feed from outside the node at all — `starved_release` requires an already-held fresh fired edge from outside the cycle, which these single-node shapes never have. Naively adding "BUG-03 fixed this" to all readiness-dodge comments uniformly would have been factually wrong for these four.
- **Fix:** The single-node fixtures' comments state BUG-03's starvation-release fix does NOT apply to their shape (still names BUG-03, satisfying the acceptance criteria's grep count), while only the two fixtures that construct the actual fed-from-outside-plus-self-loop shape point at the regression tests.
