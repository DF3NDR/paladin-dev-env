## Phase Boundary

Phase 22.1 closes the four items Phase 22's gap-closure checkpoint (22-17) could not settle
in-repo, and nothing else. Its requirement anchors are ENG-02 (cyclic superstep execution with
truthful outcomes) and ENG-05 (three Waypoint backends, Postgres suite proven to execute).

1. **Readiness defect (BUG-03, to be registered).** A node that is both self-looping and fed by
   an upstream edge can never take its first turn, yet the run reports `Completed`
   (`Frontier::is_ready` in `crates/paladin-battalion/src/engine/superstep.rs` treats the node's
   own still-`Pending` self-edge as blocking). Reproduction: the `#[ignore]`d test
   `self_looping_node_fed_by_upstream_edge_can_never_take_first_turn`
   (`cargo test -p paladin-battalion --lib engine::superstep -- --ignored`). **By code reading
   (see D-01), the same mechanism starves every non-entry node inside any cycle that is fed from
   outside the cycle** — `entry -> a -> b -> a` never runs `a`, because `b -> a` stays `Pending`
   and `b` is never provably dead. The fix is a frontier-semantics change, developed test-first,
   plus the defect's registration in the program's defect register.
2. **MSRV position.** The workspace advertises `rust-version = "1.85"` but the `=2.1.0`-pinned
   `rmcp`'s `transport-child-process` feature (the Arsenal STDIO adapter) requires
   `process-wrap ^9.0`, whose every release needs rustc ≥ 1.86 (9.0.0) or ≥ 1.87 (9.0.1 and
   later). The X-11.2 stop-and-flag decision is made here (D-06…D-11) and enacted: manifests,
   CI job, README, MIGRATION.md §9.3, CHANGELOG, mdBook — one change.
3. **G-22-1 closing evidence.** A fully green `postgres-integration` run after the 22-17 fixes,
   recorded as the gap's closing evidence (D-12…D-14). The run 22-17 cited (33688238662) has a
   green Postgres job inside a workflow run whose overall conclusion is `cancelled` (superseded
   by the next push under the CI concurrency group) and whose MSRV, Security Audit and License &
   Dependency Policy jobs failed — so the evidence bar is restated.
4. **CR-01 (22-REVIEW.md).** `WarGraph::fingerprint()` omits `defer_flags`, `dynamic_targets`
   — and, verified in this discussion, the **entry set** — from its hashed bytes, so `resume`'s
   fingerprint-mismatch check cannot detect a scheduling-relevant graph change; the rustdoc on
   `WarEngine::resume_with_options` (`engine/mod.rs:461`) claims divergence is "structurally
   impossible". Fix the hash pre-release and reword the claim (D-15…D-19).

## Implementation Decisions

The PRD (doc 01) and overview §3 rules remain the FR-level source of truth. The decisions below
settle only what the four items left open. Do not re-litigate anything Phase 22's CONTEXT
(D-01…D-12 there) or the PRD already states.

### Readiness fix semantics (BUG-03)
- **D-01: Scope is the general cycle-bootstrap defect, not the self-loop special case.** The
  self-loop is the degenerate instance of one mechanism: a `Pending` incoming edge whose source can
  only ever run *after* the target (a back-edge into a cycle that contains no entry node) gates the
  target's first execution forever, and `propagate_dead` never marks that source dead because it
  has its own `Pending` incoming edge. `validate_accepts_two_node_cycle` (`graph.rs`) is a
  validate-only readiness dodge of exactly this kind ("`a` is entry because a cycle needs to start
  somewhere"). ENG-FR-02's "cycles allowed" is hollow if only entry-anchored cycles can run. Fix
  the mechanism; the registered defect describes the general shape with the self-loop as its
  minimal reproduction. — **Reversibility:** costly — Phases 23 (Muster) and 25 (Aegis) build on
  this readiness rule, and once v0.10.0 ships, changing scheduling semantics again alters how
  stored threads resume.
- **D-02: Behavioural contract (the invariant the fix must satisfy).** (a) Every declared node in
  the eligible set that receives at least one fired incoming edge executes at least once before the
  run can report `Completed`; (b) ENG-FR-06 join semantics for acyclic joins are unchanged — a
  diamond still waits for every incoming edge from a live source, a not-firing branch still
  resolves the join; (c) ENG-FR-04/08 determinism holds over the new shapes (≥20 randomized
  iterations, byte-identical Battlefields); (d) E2E-1 (`tests/integration/e2e_crash_resume_test.rs`)
  and every existing engine test pass without assertion changes.
- **D-03: Preferred mechanism — starvation release, with rejection as the guard.** Research and
  planning start from this candidate, and may substitute another only if it is shown to violate
  D-02: when `compute_next_vanguard` would return an empty Vanguard while some non-dead node has a
  fresh fired incoming edge and is blocked only by `Pending` edges from live, never-executed
  sources, release those starved nodes (in `node_order`, deterministically) instead of completing —
  the same "fallback when nothing else is executable" shape the existing `defer` release already
  uses. It introduces **no new persisted engine state** (computed from edge states and
  `last_executed`, both rebuilt during a run), never triggers when any node is genuinely ready, and
  covers self-loops, single-entry cycles and multi-entry cycles alike. Alternatives considered:
  dominator-based static back-edge classification (fails multi-entry cycles); seeding only the
  node's own self-edge as resolved (fixes the symptom, leaves D-01's general case); rejecting
  entry-less cycles at `validate()` (truthful but forbids `entry -> a -> b -> a`). The last one is
  retained **as the guard**: any graph shape the chosen mechanism still cannot schedule must fail
  at validation with a typed `EngineError` naming the nodes — never run to a lying `Completed`.
- **D-04: Belt-and-braces truthful-outcome check at run end.** Independently of the mechanism, if
  the engine is about to report `Completed` while a non-dead eligible node still holds an
  unconsumed fired incoming edge, the run ends in a typed error naming those nodes (a new
  `EngineError` variant; `#[non_exhaustive]` per X-10 if the enum is not already). This turns any
  future regression of D-02(a) into a loud failure instead of a silent lie, mirroring how BUG-02
  moved from silence to rejection.
- **D-05: Fixtures and registration, test-first.** (i) The existing reproduction test is
  un-ignored with **no assertion changes** and must go green (it is the RED test; do not write a
  new one for the self-loop case). (ii) A second RED test for the general case
  (`entry -> a -> b -> a`, `a` and `b` non-entry, bounded by an edge condition) is written before
  the fix, in the same commit order the traceability protocol checks for BUG-01/BUG-02
  (failing-then-passing visible in history). (iii) The nine "readiness dodge" fixtures audited in
  22-16 keep their entry-node arrangements (an entry self-loop stays legal) but their comments —
  which currently name `Frontier::is_ready`'s self-edge gating as the reason — are corrected so
  no comment describes fixed behaviour as current. (iv) The defect is registered as **BUG-03** in
  `.project/v0.10.0/00-program-overview.md` §7, as a row in
  `.project/v0.10.0/08-traceability-matrix.md`, and as **ENG-FR-06a** in
  `.project/v0.10.0/01-battlefield-state-and-execution-engine.md` (the join-readiness FR it
  amends), with BUG-02's pre-release classification: no MIGRATION.md §9.1 entry, no §9.2 register
  row (the engine module is absent at the `v0.9.0` tag — confirmed in 22-16). The developer
  decided at the 22-17 checkpoint that registration happens when 22.1 is planned; editing those
  three `.project/` files is therefore in scope for this phase's first plan.

### MSRV position (X-11.2 stop-and-flag resolution)
- **D-06: The declared floor rises; "move the rmcp pin" is rejected on evidence.** crates.io index
  data (2026-09-02): every `rmcp` release from 0.15.0 through 3.2.0 depends on `process-wrap ^9.0`
  when `transport-child-process` is enabled; `process-wrap` 9.0.0 declares `rust-version` 1.86.0
  and 9.0.1/9.0.3/9.1.0/10.0.0 declare 1.87.0; 8.x (1.77) is outside `^9.0`. No rmcp version
  restores 1.85 with the STDIO transport, and `rmcp` 3.x itself declares 1.88. The Phase 12.1
  exact pin `rmcp = "=2.1.0"` stays. Dropping `transport-child-process` would remove a shipped
  Arsenal capability (X-03 forbids) and is rejected. The 1.85 figure was derived from edition
  2024's minimum (Milestone 11, PRD OQ-1), never measured; Phase 22's new `msrv` job is the first
  measurement and has never been green. — **Reversibility:** costly — published crates advertise
  the floor; lowering it later means re-pinning every dependency that moved.
- **D-07: Target floor is Rust 1.88, subject to one measurement.** 1.88 is the lowest floor that
  (a) satisfies `process-wrap` (needs 1.87) **and** (b) clears **RUSTSEC-2026-0009** on `time`
  (patched ≥ 0.3.47, which declares `rust-version` 1.88) **without adding a security exception**.
  The `time 0.3.45` pin-back from 22-17 (commit `44e13fbd`) is the sole cause of the red Security
  Audit and License & Dependency Policy jobs on run 33688238662 (`error[vulnerability]
  RUSTSEC-2026-0009`); `time` reaches the tree via `rust-s3`/`aws-creds` (optional `s3`) and
  `lopdf`/`pdf-extract` (`paladin-content`) under `--all-features`. Alternatives considered and
  rejected: 1.87 + a new RUSTSEC-2026-0009 exception (adds to the exception sprawl SEC-01 and
  ADR-0024 govern, for a floor only one release lower); 1.86 with `process-wrap` held at `=9.0.0`
  (a transitive `.0` pin plus the same `time` exception). Every crate 22-17 pinned back has a
  current release at ≤ 1.88 (`darling` 0.24.1, `home` 0.5.12, `idna_adapter` 1.2.2 at 1.86, the
  `icu_*` 2.3.x family, `serde_with` 3.22.0, `tonic` 0.14.6 — all 1.88). **Measurement gate:**
  research runs `cargo +1.88 check --workspace --all-features --all-targets` on the lockfile from
  D-08; if any crate needs > 1.88, hold that crate at its newest ≤ 1.88 release via MSRV-aware
  resolution (D-09) provided it carries no advisory; if that is impossible, this is a fresh X-11.2
  stop-and-flag with the measured number — do not silently pick a higher floor. The bump is a
  documented minor-version change (X-11.2; v0.10.0 is minor).
- **D-08: Revert the 22-17 lockfile pin-backs rather than layer on them.** Commit `44e13fbd`
  downgraded 20 `Cargo.lock` entries solely for 1.85 (`darling`/`darling_core`/`darling_macro`
  0.23.0→0.21.3, `home` 0.5.12→0.5.11, `icu_collections`/`icu_locale_core`/`icu_normalizer`/

  2.2.0→2.1.2, `idna_adapter` 1.2.2→1.2.1, `num-conv` 0.2.2→0.1.0, `serde_with`/`serde_with_macros`

### Fingerprint coverage (CR-01) and the resume-safety claim
- **D-15: Fix the hash now, while it is free.** Phase 22 D-04 rated the canonical byte layout
  one-way *after release*; the engine is absent at the `v0.9.0` tag and no Waypoint exists outside
  this branch, so this phase is the only cheap window. Fold into `WarGraph::fingerprint()` every
  property that changes **scheduling or merge semantics**: the existing node ids, edges and schema
  field names; **the entry set** (currently omitted — a different entry node reschedules the whole
  run and passes the check today); `defer_flags`; `dynamic_targets`; each schema field's
  `DispatchRule` (a `LastWrite`→`Append` change alters every merge on resume); and each Paladin
  node's `output_field`. Excluded, per ENG-FR-14: prompts, models, `InputMapping` templates, and
  `EngineLimits` (raising a limit to let a resumed run continue is a legitimate operator action).
  All lists sorted deterministically as today. — **Reversibility:** one-way after v0.10.0 ships
  (Phase 22 D-04) — every stored Waypoint's fingerprint mismatches on a later change.
- **D-16: Canonical bytes never depend on `Debug` output.** Edge conditions are currently hashed via
  `format!("{:?}", edge.condition)`; a derive change would silently move the fingerprint. Serialize
  conditions (and dispatch rules) through their serde representation in canonical form instead.
- **D-17: A golden fingerprint test pins the hex** of a fixed fixture graph exercising every hashed
  property, so any future canonicalization change fails CI visibly instead of breaking `resume` for
  released users (making D-04's one-way hazard observable). Plus difference tests: same graph with
  one node deferred, one node marked dynamic target, a different entry set, a different edge
  condition, a different dispatch rule, a different `output_field` — each must change the
  fingerprint — alongside the existing determinism and insertion-order tests.
- **D-18: Reword the resume-safety claim to what is actually guaranteed.** `engine/mod.rs:461`
  ("a divergence between fresh and resumed execution is structurally impossible") becomes a
  statement of what the fingerprint check detects (the D-15 list, cross-referenced to
  `WarGraph::fingerprint`'s rustdoc), what `allow_graph_change` deliberately bypasses, and a pointer
  to the frontier-reconstruction finding under Deferred Ideas until that finding has a disposition.
  Do not re-assert an unqualified impossibility.
- **D-19: No behavioural change to `resume`'s error surface.** `EngineError::GraphMismatch` and
  `ResumeOptions::allow_graph_change` keep their current semantics; only what counts as "the same
  graph" tightens.
