**Readiness fix semantics (BUG-03)**
- D-01: Scope is the general cycle-bootstrap defect, not the self-loop special case — a `Pending`
  incoming edge whose source can only ever run after the target (a back-edge into a cycle with no
  entry node) gates the target's first execution forever, and `propagate_dead` never marks the

- D-02: Behavioural contract — (a) every declared node in the eligible set that receives ≥1 fired

## Summary

This phase has almost no external-library research surface — its four items are entirely resolved
by reading this repository's own code and CI configuration, and by running real measurements
against them. Three of the four items were fully measured in this research session rather than
merely reasoned about:

1. **The readiness defect (D-01…D-05).** `Frontier::is_ready` (`superstep.rs:705-727`) requires
   **every** incoming edge to be resolved (non-`Pending`) before a node is scheduled. A self-loop
   edge (`b -> b`) only resolves once `b` has executed — so if `b` has ANY other incoming edge that
   also has never fired independently, `b`'s own unresolved self-edge blocks the first execution
   that would resolve it. This reproduces exactly at `entry -> b`, `b -> b`: `entry -> b` fires,
   `b -> b` stays `Pending` forever, `is_ready` requires `!any_pending`, so `b` never enters a
   Vanguard, `propagate_dead` never marks `b` dead (it has one fired-eventually edge), and
   `compute_next_vanguard` returns empty → `RunOutcome::Completed` with `b`'s `run_count() == 0`.
   The ignored reproduction test at `superstep.rs:1385` already encodes this exact shape and already
   asserts CORRECT behaviour (never inverted). `compute_next_vanguard` (`superstep.rs:737-761`) is
   the exact slot the CONTEXT.md's D-03 starvation release names — it already has one fallback tier
   (the `defer` release) after the normal-ready pass, so a second fallback tier fits the established
   shape.

2. **The MSRV position (D-06…D-11).** **Measured, not assumed, in this session:** restoring the
   pre-`44e13fbd` lockfile (`git show 44e13fbd^:Cargo.lock`) under `resolver = "3"` and running
   `cargo +1.88 check --workspace --all-features --all-targets --locked` **succeeded with zero
   errors** (6m35s, full workspace incl. every crate and every feature). `cargo metadata` over that
   same resolution shows **zero** packages declaring `rust_version` > 1.88 among 439 packages that
   declare one at all — `process-wrap 9.1.0` needs 1.87.0, `time 0.3.47` needs 1.88.0, both inside
   the 1.88 floor. `cargo audit` against the restored lockfile reports **zero** vulnerabilities
   (vs. the current lockfile's `error: 1 vulnerability found!` on RUSTSEC-2026-0009/`time`), with no
   new advisory introduced. This directly confirms D-07's 1.88 figure and D-08's "revert, don't
   layer" instruction are both correct as measured.

3. **CI evidence extraction (D-12…D-14).** `gh run view <run> --json conclusion,status,jobs` and
   `gh run view --job <id> --log` both work non-interactively in this session (GH_TOKEN present).
   Re-running the exact query CONTEXT.md cites against run `33688238662` reproduces its claim
   precisely: overall `conclusion: cancelled`, with `MSRV (Rust 1.85)`, `Security Audit` and
   `License & Dependency Policy` all `failure` inside that same run, alongside a `success` Postgres
   job — confirming the evidence bar restated in D-12 is necessary (a green job alone proves
   nothing about the run's overall verdict).

4. **The fingerprint fix (D-15…D-19).** `WarGraph::fingerprint()` (`graph.rs:403-437`) hashes only
   node ids, edge `from`/`to` pairs + `Debug`-formatted condition, and schema field names. It does
   **not** touch `self.entry`, `self.defer_flags`, or `self.dynamic_targets` — all three are struct
   fields sitting unused a few lines above the function, confirmed by direct read. `EdgeCondition`
   and `DispatchRule` both already derive `Serialize`/`Deserialize` (`campaign.rs:34`,
   `battlefield.rs:70`), so D-16's "serialize through serde representation, not `Debug`" has no
   blocking type gap to solve — it is a mechanical swap. `GraphFingerprint::from_canonical_bytes`
   (`paladin-core/waypoint.rs:165`) is a thin `blake3::hash` wrapper with a `v1:` version tag,
   unaffected by what bytes are fed to it.

**Primary recommendation:** Treat this phase as a code-reading and measurement phase, not a
library-adoption phase. Every one of the four items has a verified, load-bearing measurement in
this document; the planner's job is sequencing the edits, not further research.

### Pattern 1: Starvation release as a third `compute_next_vanguard` pass

**What:** After the existing normal-ready pass and the existing `defer`-release fallback pass, add
a third fallback: if both are empty, scan for nodes that are non-dead, have at least one edge whose
resolution is `Fired` at or after their `last_executed` threshold (i.e. would satisfy `is_ready`'s
"fresh fire" half), but are blocked purely because another incoming edge is still `Pending` from a
source that is itself live (not dead) and has never executed. Release those nodes, ordered by
`node_order` (matching the existing `defer` release's ordering discipline, ENG-FR-04).

**When to use:** Exactly the fallback tier CONTEXT.md D-03 specifies — only engaged when the
Vanguard would otherwise be empty, never when any node is genuinely ready by the existing rule.

**Example (existing code this pattern extends — `superstep.rs:737-761`):**
```rust
// Source: crates/paladin-battalion/src/engine/superstep.rs (this repo, read this session)
fn compute_next_vanguard(graph: &WarGraph, frontier: &Frontier) -> Vec<NodeId> {
    let mut ready = Vec::new();
    let mut seen = HashSet::new();
    for edge in graph.edges() {
        let target = &edge.to;
        if graph.is_deferred(target) || seen.contains(target) {
            continue;
        }
        if frontier.is_ready(graph, target) {
            seen.insert(target.clone());
            ready.push(target.clone());
        }
    }
    if !ready.is_empty() {
        return ready;
    }

    let mut deferred_ready = Vec::new();
    for node in graph.node_order() {
        if graph.is_deferred(node) && frontier.is_ready(graph, node) {
            deferred_ready.push(node.clone());
        }
    }
    deferred_ready
    // D-03 inserts a third fallback here, gated on `deferred_ready.is_empty()`,
    // scanning `graph.node_order()` for starved-but-fireable nodes.
}
```

### Pattern 2: Deterministic byte-canonicalization for hashing (existing pattern, extend it)

**What:** `WarGraph::fingerprint()` already sorts every collection before hashing (node ids, edges
by `(from, to)`, schema field names) specifically because `HashMap`/`HashSet` iteration order is
per-process-randomized. D-15's new fields (`entry`, `defer_flags`, `dynamic_targets`) must follow
the exact same discipline: sort before writing to the byte buffer.

**When to use:** Any new field folded into the canonical byte stream.

**Example:**
```rust
// Source: crates/paladin-battalion/src/engine/graph.rs:404-436 (existing pattern to extend)
let mut node_ids: Vec<&NodeId> = self.nodes.keys().collect();
node_ids.sort();
// D-15: apply the identical pattern to self.entry, self.defer_flags,
// self.dynamic_targets (all currently HashSet<NodeId> or Vec<NodeId> — sort
```

### Anti-Patterns to Avoid

- **Hashing via `format!("{:?}", ...)` for anything that must be stable:** the current
  `edge.condition` hash uses `Debug` formatting (`graph.rs:427`). A `#[derive(Debug)]` field-order
  or representation change on `EdgeCondition`/`DispatchRule` would silently change every stored
  fingerprint with no compiler warning. D-16 replaces this with the type's own serde
  representation (both already derive `Serialize`), which is the stable contract, not `Debug`.
- **Layering new lockfile pins on top of old ones (D-08's explicit rejection):** 22-17's approach
  (downgrade 20 entries by hand for a floor that turned out to need to rise anyway) is exactly the
  anti-pattern D-08 names — revert to the pre-pin-back resolution and let the new floor admit it
  cleanly, rather than accumulating manual pins that each need independent justification.
- **Treating a green job inside a `cancelled`/superseded workflow run as evidence (D-12):** proven
  live this session — run `33688238662`'s Postgres job is `success` while three other required
  jobs in the *same run* are `failure`, and the run's own overall `conclusion` is `cancelled`. A
  job-level query without checking the run's `conclusion` field would have missed this.

## Common Pitfalls

### Pitfall 1: Fixing `is_ready` by special-casing self-loops only

**What goes wrong:** A tempting narrow fix is "if the only unresolved incoming edge is the node's
own self-loop, treat it as resolved." This fixes the reproduction test but not D-01's general case:
`entry -> a -> b -> a` (no self-loop at all) starves `a` by the identical mechanism — `b -> a` stays
`Pending` because `b` itself can never run first (it's fed only by `a`, which is starved).

**Why it happens:** The ignored reproduction test's fixture happens to be a self-loop, which makes
the self-loop-special-case fix look sufficient if only that one test is consulted.

**How to avoid:** D-01 explicitly names the general shape and D-05(ii) mandates a second RED test
for the non-self-loop cycle (`entry -> a -> b -> a`) written *before* the fix. Verified in this
session: `graph.rs`'s `validate_accepts_two_node_cycle` test (line 474) already accepts this exact
topology structurally — the readiness bug is purely in `Frontier::is_ready`'s runtime behaviour,
confirmed by the fact that `validate()` has no opinion on it (a separate, already-passing check).

**Warning signs:** A fix that only touches self-loop detection code, or that special-cases
`edge.from == edge.to`, is narrower than D-01's mandate.

### Pitfall 2: The starvation release firing when a node is genuinely still blocked

**What goes wrong:** An overly permissive starvation release could schedule a node whose blocking
edge is `Pending` from a source that WILL still run later in this same graph (just not yet), producing
a spurious early execution that violates D-02(b)'s join-semantics-unchanged requirement.

**Why it happens:** The starvation release must only engage as an empty-Vanguard fallback (mirroring
the `defer` release's own gating), not as a general readiness relaxation. If it is checked in the
main `is_ready` pass instead of as a third fallback tier, a diamond join (`ENG-FR-06`) could resolve
one branch before its sibling branch that is legitimately still pending.

**How to avoid:** Gate the starvation release strictly behind `ready.is_empty() &&
deferred_ready.is_empty()` (D-02(b)'s acyclic-join-semantics-unchanged clause depends on this), and
add the D-04 belt-and-braces check as an independent safety net rather than relying on the release
logic alone to be correct.

**Warning signs:** `diamond_join_executes_target_exactly_once` or
`false_branch_is_proven_not_firing_and_join_still_runs_once` (both existing tests in
`superstep.rs`, confirmed present this session at lines 1610 and 1636) start failing or become
order-dependent.

### Pitfall 3: MSRV toolchain auto-install silently picking a different micro-version

**What goes wrong:** `cargo +1.88 check` without an exact toolchain installed triggers `rustup`'s
auto-install, which resolves "1.88" to the latest 1.88.x patch — observed live this session
(`warn: the missing active toolchain '1.88-x86_64-unknown-linux-gnu' has been auto-installed`). If
CI's `dtolnay/rust-toolchain@1.88` action resolves differently than a developer's local
`rustup toolchain install 1.88.0`, a floor that "works locally" could still fail in CI on a stricter
patch resolution.

**How to avoid:** Pin the exact `1.88.0` in local verification (as this session did) but recognize
`dtolnay/rust-toolchain@1.88` in `ci.yml` floats to the latest 1.88.x patch by design — this is the
existing, accepted pattern already used for the "1.85" job today (`dtolnay/rust-toolchain@1.85`),
so D-10 preserves it rather than pinning a micro-version in CI.

### Pitfall 4: Treating `deny.toml`'s absence of a new `error` as proof of no new advisory

**What goes wrong:** `cargo deny check` and `cargo audit` can disagree on severity classification
(warning vs. error) for the same advisory ID depending on their respective config files. D-08
requires "no entry is added to `.cargo/audit.toml`, `deny.toml` or `SECURITY-EXCEPTIONS.md`" — this
session verified `cargo audit`'s pass/fail delta (current lockfile: `error: 1 vulnerability found!`;
restored lockfile: clean), but did **not** re-run `cargo deny check` end-to-end (not installed in
this environment) or `scripts/check-advisory-register.sh`. The planner's verification task must run
both, not assume `cargo audit`'s result generalizes to `cargo deny`.

**Warning signs:** `make security` (which runs both `cargo-audit` and `cargo-deny`, per
`security.instructions.md`) is the authoritative gate — run it, don't infer from `cargo audit` alone.

## Code Examples

### The exact defect mechanism (verified via direct read, `superstep.rs:698-727`)

```rust
// Source: crates/paladin-battalion/src/engine/superstep.rs (this repo)
fn is_ready(&self, graph: &WarGraph, node: &NodeId) -> bool {
    let Some(incoming) = self.incoming.get(node) else {
        return false;
    };
    if incoming.is_empty() {
        return false;
    }
    let threshold: i64 = self.last_executed.get(node).map_or(-1, |&s| s as i64);
    let mut any_pending = false;
    let mut any_fresh_fire = false;
    for idx in incoming {
        match self.edge_resolution(graph, *idx) {
            Some((true, resolved_at)) => {
                if resolved_at as i64 >= threshold {
                    any_fresh_fire = true;
                }
            }
            Some((false, _)) => {}
            None => any_pending = true,   // <-- a node's OWN unresolved self-edge sets this
        }
    }
    !any_pending && any_fresh_fire        // <-- ANY pending edge blocks scheduling, forever,
                                           //     if that edge's only resolver is the node's
                                           //     own first execution
}
```

## Open Questions

1. **Exact wording of the D-03 starvation-release guard's `EngineError` variant**
   - What we know: D-03 requires "any graph shape the mechanism still cannot schedule must fail at
     validation... naming the nodes"; D-04 requires a separate run-end belt-and-braces variant.
   - What's unclear: Whether one new `EngineError` variant serves both the validate-time guard and
     the run-end check, or two are needed (CONTEXT.md's Claude's Discretion leaves naming open).
   - Recommendation: Two variants read more truthfully to `#[non_exhaustive]` callers — a
     validate-time "this graph shape cannot be scheduled" error is a different failure class from a
     run-end "the engine's own invariant broke" error, and conflating them would make the run-end
     variant's `#[error(...)]` message describe two different failure moments. Left to the plan.

2. **Whether the starvation-release third pass needs its own "fresh fire" threshold logic
   duplicated from `is_ready`, or can call `is_ready`-adjacent helpers**
   - What we know: `is_ready`'s `any_fresh_fire`/`any_pending` computation is exactly the
     information the starvation release needs (which edges are fired, which are pending, from which
     sources).
   - What's unclear: Whether refactoring `is_ready` to expose a `(any_pending, any_fresh_fire,
     pending_sources)` triple (rather than duplicating the loop) is worth the churn to
     already-tested code, given D-02(d)'s "every existing engine test passes without assertion
     changes" constraint.
   - Recommendation: Factor a private helper returning per-node edge-resolution state once, called
     by both `is_ready` and the new starvation pass — avoids duplicating the `edge_resolution` loop
     without touching `is_ready`'s existing public behaviour or its tests' assertions.
