## Summary

Reviewed the BUG-03 (starvation-release), BUG-04 (resumed-frontier persistence) and MSRV-1.88
follow-up work across `paladin-battalion`'s superstep engine, `paladin-core`'s `Waypoint` type,
all three `WaypointPort` backends, the workspace manifests, and the accompanying docs/CI/project
files.

**Prior CR-01 (22-REVIEW.md) confirmed closed.** The earlier finding — `WarGraph::fingerprint()`
omitted `defer_flags`/`dynamic_targets`, letting a resumed graph silently swap defer/dynamic-target
semantics under an unchanged fingerprint — is fixed: `graph.rs:548-619` now folds the entry set,
`defer_flags`, `dynamic_targets` and each schema field's serde-canonical `DispatchRule` into the
hashed bytes, each collection sorted before hashing, with a golden-hex test
(`fingerprint_golden_hex_pins_canonical_bytes`) and one difference test per newly-covered property.
That specific under-coverage gap is closed.

The BUG-03 starvation-release logic (`Frontier::starved_nodes`/`starved_release`/
`starved_deferred_release`, `starved_at_completion`) and the BUG-04 `FrontierSnapshot`
persist/restore path (`Frontier::snapshot`/`from_snapshot`, the `Waypoint.frontier` field, and its
propagation through all three `WaypointPort` backends) are carefully reasoned about in the doc
comments and are backed by targeted regression tests reproducing the exact starvation and
frontier-loss shapes the two bugs describe; I traced the logic by hand against several edge cases
(self-loop-plus-upstream-edge, general two-node cycle, deferred aggregator starved by its own
back-edge, join-shape resume under `allow_graph_change`) and found the implementation matches the
documented invariants.

However, while auditing the fingerprint fix in depth (the file this phase's CR-01 touches most),
I found a new, more fundamental defect in the SAME function: the canonicalization scheme used to
build the hashed byte buffer is delimiter-based and unescaped, so two structurally different
`WarGraph`s can be crafted to fingerprint identically whenever a `NodeId`/`FieldName` contains one
of the separator characters the encoding relies on (`|`, `-`, `:`). Since neither `NodeId::new` nor
`FieldName::new` restricts the character set (only non-emptiness is validated), this is directly
reachable with ordinary, plausible identifiers (e.g. hyphenated node names) — not merely a
theoretical delimiter-injection curiosity. This undermines the exact "structurally impossible
divergence" guarantee CR-01's own fix was written to restore, by a different mechanism than the one
already reported. See CR-01 below (fresh numbering for this review).

Two smaller findings (a library-code `.expect()` and a stale doc description of what
`fingerprint()` covers) round out the report.

## Critical Issues

### CR-01: `WarGraph::fingerprint()`'s canonical byte encoding is not collision-free — crafted node/field names produce identical fingerprints for different graphs

**File:** `crates/paladin-battalion/src/engine/graph.rs:548-619`

**Issue:** `fingerprint()` builds its hashed byte buffer by concatenating raw, unescaped
`NodeId`/`FieldName`/condition-JSON bytes, separated only by ASCII delimiters (`|`, `-`, `:`) that
are themselves legal characters inside a `NodeId` or `FieldName` — neither type restricts its
character set beyond non-emptiness (`crates/paladin-core/src/platform/container/waypoint.rs:130-134`
for `NodeId::new`; `crates/paladin-core/src/platform/container/battlefield.rs:44-50` for
`FieldName::new`). Because the encoding carries no length prefix and no escaping, the byte stream
produced for one node/edge boundary is indistinguishable from the byte stream produced by a
different split of the same bytes across two nodes/edges — so two graphs with different node sets
or different edge sets can hash to the *same* `GraphFingerprint`.

Concretely, in the `nodes:` section (`graph.rs:569-583`), each node is encoded as
`id + ("|of:" + field | "|nf") + "|"`. Two independent Function nodes named `"a"` and `"b"` encode
to `"a|nf|" + "b|nf|"` = `"a|nf|b|nf|"`. A single Function node named `"a|nf|b"` encodes to
`"a|nf|b" + "|nf" + "|"` = the identical `"a|nf|b|nf|"`. With every other hashed section empty (no
edges, entry set differing only in the swapped node name, etc.), these two structurally distinct
graphs — one with two nodes, one with one node — fingerprint identically.

The `edges:` section (`graph.rs:584-593`) has the same shape with more realistic triggers: each
edge encodes as `from + "-" + to + ":" + condition_json + "|"`. A single edge `"a" -> "b-c"` encodes
to `"a-b-c:null|"`. A single edge `"a-b" -> "c"` encodes to the identical `"a-b-c:null|"`. Hyphenated
node ids (`"worker-1"`, `"step-a-b"`) are an entirely ordinary naming convention, not an adversarial
edge case, which makes this reachable without any deliberate attempt to defeat the check.

Since `WarEngine::resume`/`resume_with_options` (`crates/paladin-battalion/src/engine/mod.rs:568-635`)
relies entirely on fingerprint equality to detect a graph change and reject (or, under
`allow_graph_change`, knowingly accept) a divergent resume, a crafted or merely coincidental pair of
node/field names can make `resume` proceed against a *genuinely different* graph — different node
set, different edges, different defer/dynamic-target markers — while `latest.graph_fingerprint ==
graph.fingerprint()` reports a match. This is the exact "structurally impossible divergence"
guarantee CR-01 (22-REVIEW.md) fixed for the defer-flag/dynamic-target *coverage* gap, broken again
here by an *encoding* gap in the same function — for a workflow-authoring surface where node ids and
field names plausibly originate from external graph definitions (the medieval-military ubiquitous
language guide itself uses hyphenated multi-word names as an idiom), this is a real, not merely
theoretical, resume-integrity/data-corruption risk, not a cosmetic one.

**Fix:** Replace the ad hoc delimiter-separated concatenation with a length-prefixed or otherwise
unambiguous encoding before hashing, e.g. write each field's byte length (as a fixed-width integer)
immediately before its bytes so no byte sequence can be reinterpreted as a different split:

```rust
fn push_field(buf: &mut Vec<u8>, bytes: &[u8]) {
    buf.extend_from_slice(&(bytes.len() as u64).to_le_bytes());
    buf.extend_from_slice(bytes);
}

// nodes:
for id in &node_ids {
    push_field(&mut buf, id.as_str().as_bytes());
    match self.nodes.get(*id) {
        Some(NodeSpec::Paladin { output_field, .. }) => {
            buf.push(1); // "has output field" tag, unambiguous vs. the id's own bytes
            push_field(&mut buf, output_field.as_str().as_bytes());
        }
        _ => buf.push(0),
    }
}
// edges: push_field(from), push_field(to), push_field(condition_json) per edge, no "-"/":" joins
```

This is a D-17-class change (the rustdoc already documents that the byte layout is pinned by a
golden-hex test and "must not be done without a deliberate format-version bump") — bump
`GRAPH_FINGERPRINT_VERSION` to `"v2"` alongside the fix so every previously-stored fingerprint is
recognized as stale rather than silently reinterpreted, and update
`fingerprint_golden_hex_pins_canonical_bytes` and its sibling difference tests for the new encoding.
Add a regression test asserting that the two constructed collisions above (`"a"`+`"b"` vs.
`"a|nf|b"`; edge `"a"->"b-c"` vs. edge `"a-b"->"c"`) now produce *different* fingerprints.

## Warnings

### WR-01: `.expect()` in spawned superstep task violates the project's "no unwrap/expect/panic in library code" convention

**File:** `crates/paladin-battalion/src/engine/superstep.rs:425-428`

**Issue:** Inside the per-node `tokio::spawn`ed future, the semaphore permit acquisition is
unwrapped with `.expect("semaphore is never closed")`:

```rust
let _permit = sem
    .acquire_owned()
    .await
    .expect("semaphore is never closed");
```

`Semaphore::acquire_owned` only errors if the semaphore is explicitly `.close()`d, which nothing in
this codebase currently does to the locally-constructed `semaphore` — so this is unreachable today.
CLAUDE.md and `.github/instructions/rust.instructions.md` are explicit and repeated on this point:
"Avoid `unwrap()`/`expect()` and `panic!` in library code — return `Result`" / "Don't use `unwrap()`
or `expect()` unless absolutely necessary." This call sits inside a spawned task in non-test library
code (there is no `#[cfg(test)]` guard around it), so a future change anywhere that gains access to
`semaphore` and calls `.close()` (or a refactor that shares the semaphore across a wider scope) would
turn a currently-benign invariant into a panic inside a detached `tokio::spawn`ed task — which
`JoinHandle::await` in the caller (`superstep.rs:464-467`) does convert into a proper `EngineError`,
but only via the join error path, and only after the fact.

**Fix:** Thread the join-error conversion path already used at the call site through this failure
too, e.g. by not `.expect()`ing at all and instead propagating a `NodeError`/panicking-message via
the existing `Result` plumbing:

```rust
let _permit = match sem.acquire_owned().await {
    Ok(permit) => permit,
    Err(_) => {
        // Semaphore is never closed by this engine; treat as an internal
        // invariant violation reported the same way a node's own error is.
        return (nid, started_at, 0, None, 0u64,
            NodeRunOutcome::Failed(NodeError(
                "internal error: superstep semaphore closed unexpectedly".into(),
            )));
    }
};
```

or, at minimum, replace the free-form `.expect()` message with a `debug_assert!`/early-return that
does not panic in a release build.

### WR-02: `.project/v0.10.0/01-battlefield-state-and-execution-engine.md`'s ENG-FR-14 description is stale relative to the implemented fingerprint coverage

**File:** `.project/v0.10.0/01-battlefield-state-and-execution-engine.md:219`

**Issue:** The requirements doc still describes `WarGraph::fingerprint()` as "a hash over node ids,
edge specs, schema — NOT over prompts/models." That was accurate before this phase's CR-01 fix, but
`graph.rs:507-548`'s current rustdoc (and the implementation itself) also hashes the declared entry
set, `defer_flags`, and `dynamic_targets` — precisely the properties CR-01 (22-REVIEW.md) reported as
missing and this phase closed. Neither `08-traceability-matrix.md`'s BUG-03/BUG-04 rows nor
`00-program-overview.md` mention the extended coverage either, so a reader consulting only the
`.project/v0.10.0` requirements set (rather than `graph.rs`'s own rustdoc) would believe the
defer-flag/dynamic-target fingerprint gap CR-01 found still exists.

**Fix:** Update the ENG-FR-14 bullet to list entry set, `defer_flags`, `dynamic_targets` and each
schema field's `DispatchRule` alongside node ids/edge specs/schema field names, and add a one-line
cross-reference to the CR-01 fix (D-15/D-16/D-17 in `graph.rs`'s own comments) so the two documents
stay in sync.
