  <name>Task 1: Confirm the branch-lineage storage contract</name>
  <decision>Add `fork_of: Option<WaypointId>` to `Waypoint` and `WaypointSummary`, marking the branch root and propagating along the branch (D-14).</decision>
  <context>This is a stored-payload contract read by `replay`/`fork`, by `latest_on_branch`, by the Chronicle read facade and (from plan 24-11) by the HTTP history endpoint. It is additive and free today because v0.10.0 has not shipped and the SQLite/Postgres backends store the whole Waypoint as a JSON payload column. After release, changing what `fork_of` means requires re-deriving lineage for every persisted Waypoint in every deployment.</context>
  <options>
    <option id="propagate-along-branch">
      <name>`fork_of` marks the branch root and every Waypoint on the branch inherits it (recommended, D-14)</name>
      <pros>A branch becomes a queryable attribute; `latest_on_branch` is a filter over `history`; the whole tree reconstructs from `WaypointSummary` alone with no full-Waypoint loads; a fork of a fork carries the newer root.</pros>
      <cons>Lineage is denormalised — the same root id repeats on every Waypoint of a branch, and a mis-set value on one Waypoint mis-attributes it.</cons>
    </option>
    <option id="root-only">
      <name>Set `fork_of` only on the fork's first Waypoint</name>
      <pros>Strictly normalised — the root is recorded exactly once.</pros>
      <cons>`latest_on_branch` would need to walk `parent_waypoint_id` back to a root on every call, defeating D-14's "reconstructible from `WaypointSummary` alone"; contradicts D-14.</cons>
    </option>
  </options>
  <resume-signal>Select: propagate-along-branch, root-only, or describe a different lineage model</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| branch identity -> child thread id | A colliding derivation would let one branch read or overwrite another branch's subgraph history |
| stored payload -> deserialiser | A pre-field payload must not be misread as a branch member |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-24-21 | Tampering | `ThreadId::child_on_branch` identity collision letting a fork read the mainline child's Waypoints | high | mitigate | The same length-prefixed injective encoding as `ThreadId::child`, pinned by an adversarial-concatenation injectivity test (the 22.1 CR-01 fix) |
| T-24-22 | Tampering | A pre-`fork_of` payload deserialising into an unintended branch | medium | mitigate | `#[serde(default)]` plus a strip-key deserialisation test for both `Waypoint` and `WaypointSummary` |
| T-24-23 | Information Disclosure | Branch history leaking across threads through a marker-based lookup | medium | mitigate | Branch isolation comes only from the derived thread id; `checkpoint_ns` stays a debugging record and is never used as a lookup key |
| T-24-24 | Denial of Service | Retention pruning a suspended branch's protected Waypoint | medium | mitigate | The retention protection match is a wildcard over `AwaitingInput`, unchanged by the payload reshape, and a branch-resident case is added to its test |
| T-24-SC | Tampering | package-manager installs | low | accept | No new package is installed by this plan |
</threat_model>
