Inside the retry loop's per-attempt body, arm the bounds the node's resolved `TimeoutPolicy` declares:

- `run_timeout`: a hard wall-clock cap on the attempt. Race the attempt future against a
  `tokio::time::sleep` of that duration; on expiry cancel the attempt, discard its work, and produce
  `NodeError { source: Timeout(TimeoutKind::Run), transience: Transient }` so it feeds the retry
  predicate like any other transient failure.
- `idle_timeout`: a timer that fires when no progress event has been observed for that duration, and
  that resets on each progress event — a stream chunk, a node trace event emitted by the node, or an
  explicit `ctx.heartbeat()`. Observe beats through the `HeartbeatHandle`; prefer awaiting a change
  over polling. On expiry produce `Timeout(TimeoutKind::Idle)`, also `Transient`.

Both timers are per attempt: a new attempt arms fresh bounds. `TimeoutPolicy { run_timeout: None,
idle_timeout: None }` arms nothing and must be indistinguishable from having no `TimeoutPolicy` at
all — Test 6 is the guard. Zero durations never reach here: plan 25-03 rejects them at validation.

Which bound fired is carried by the typed `TimeoutKind`, never by message text. Every test asserts
the variant, and Test 7 makes that explicit.

Use the paused-clock idiom `engine/retry.rs` established, as its module rustdoc instructs — do not
invent a second timing-test style, and do not sleep in wall-clock time. Add the mock port these tests
need (a scriptable beat-then-stall port with a paused-clock-friendly schedule) to

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| node or provider -> progress signal | A node or port reports progress, and that report suppresses a safety timer |
| `EngineLimits.run_timeout` -> run lifetime | An operator-configured bound decides when a run is cut off |
| timed-out attempt -> Battlefield | A cancelled attempt's partial work must not survive |
