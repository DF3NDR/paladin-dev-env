Create `crates/paladin-battalion/src/engine/cache_key.rs` holding the key composition, per D-28:
`key = H(graph_fingerprint, node_id, input_component, paladin_config_fingerprint)` over a canonical,
**length-prefixed** byte stream in the same discipline `WarGraph::fingerprint()` uses — no unescaped
delimiter may separate two author-controlled strings, for the same collision reason the fingerprint's
own `v1` -> `v2` bump existed. Compose the key so the graph fingerprint and node id come first, so
`invalidate(prefix)` can target one graph or one node.

- `input_component` for a Paladin node is the rendered input string the `InputMapping` produced for
  this dispatch.
- `input_component` for a Function node under `CacheKeySpec::Default` is a canonical hash of the
  **full** Battlefield snapshot — conservative and correct, since a Function node's read set is not
  statically knowable — narrowed to the listed fields under `CacheKeySpec::Fields`.
- The muster payload is included whenever `NodeContext.muster` is `Some`.
- `paladin_config_fingerprint` hashes model, system prompt, temperature, max loops and stop words,
  for Paladin nodes only, so a prompt or model change invalidates naturally (FT-FR-20).

Including the graph fingerprint is what makes a cross-graph collision impossible by construction
rather than by a runtime check — Test 1 is that guarantee's guard, and RESEARCH Pitfall 6 is the
failure it prevents.

In `superstep.rs`, wire the cache around the retry loop:

- **Before attempt 1**, if the node has a `CachePolicy` and the engine has a backend, compose the key
  and `get`. On a hit that is unexpired, merge the stored delta, record
  `outcome: Succeeded, attempt: 1, cache_hit: true`, emit `NodeStarted`/`NodeFinished { cache_hit:
  true }`, and execute nothing. A `get` error is a **miss**, logged, never a failure.
- **After a successful attempt**, `put` the merged delta under the policy's TTL. A `put` error is
  logged and never fails the run — the cache is an optimisation by construction (D-29).
- A failed attempt never issues a `put`, and no error outcome is ever cached.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cache key -> shared cache keyspace | A composed key addresses entries that may have been written by a different graph, node or configuration |
| cached `StateDelta` -> Battlefield merge | Stored state re-enters a live run without re-execution or re-validation |
| cache backend availability -> run outcome | An external store's failure must not decide whether a run succeeds |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-25-61 | Tampering | cross-graph or stale-configuration cache hit | high | mitigate | The key includes the graph fingerprint and the Paladin config fingerprint, so a graph edit or a prompt change invalidates naturally and a cross-graph collision is impossible by construction, not by a runtime check (D-28, D-34, RESEARCH Pitfall 6), pinned by `key_includes_the_graph_fingerprint`, `changing_the_graph_re_executes` and `changing_the_system_prompt_re_executes` |
| T-25-62 | Tampering | key collision from unescaped concatenation | high | mitigate | The key uses the same canonical length-prefixed encoding `WarGraph::fingerprint()` adopted at its `v1` -> `v2` bump, so no author-controlled string can be crafted to collide with a different composition |
