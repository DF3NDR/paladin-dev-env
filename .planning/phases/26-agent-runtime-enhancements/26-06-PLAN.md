<objective>
Make `response_format` observable on the wire for the four provider paths that have a native
constrained-JSON mode, and teach `MockLlmAdapter` to record it — so plan 26-17's structured executor
can assert the service sets it, and so a caller who asks for JSON gets the provider's own
constrained decoding rather than only a prompt instruction.

Purpose: plan 26-03 added the field and proved it inert. This plan is the other half — the field
becomes real on the wire, with one mockito assertion per path, without touching a single capability
flag (ADR-0042).

Output: `response_format` handling in `openai/adapter.rs`, `compat/engine.rs`, `gemini/adapter.rs`
and `deepseek/adapter.rs`; a recorded `response_format` on `MockLlmAdapter`; a per-provider note in
the tool-integration guide pointing at the fuller table plan 26-21 writes.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-authored JSON schema → outbound provider request body | Caller data crosses a network boundary to a third-party service |
| provider response under a constrained mode → the parser | The provider's constrained output is still untrusted input |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-09 | Information Disclosure | a `response_format` schema logged with a request body | low | mitigate | Schemas are caller-authored and are never logged with request bodies (D-41); no adapter in this plan adds a body log, and the existing redaction rule for provider bodies is untouched |
| T-26-25 | Tampering | trusting a provider's constrained mode as validation | medium | mitigate | Correctness never depends on the native mode: the caller also appends the instruction block and the parse/shape check still runs (D-27, D-30). The compat engine's deliberate schema-to-object degradation is documented at the call site so nobody later reads a JSON-object response as schema-validated. |
| T-26-26 | Spoofing | an adapter silently gaining a tool-calling surface | medium | mitigate | ADR-0042 stays deferred: no `tools` field, no `function_call` emission, no capability flag change; `test_capabilities_tool_calling_matches_request_surface` is in this plan's verify command and its acceptance criteria |
| T-26-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no package |
</threat_model>
