<objective>
Ship retry and fallback as **port-shaping** middleware: the middleware sets what the run should use,
and the service's one model-call site honours it. Delegate all the mathematics to Phase 25's
existing implementations rather than copying them, and give `ModelFallbackConfig` a provider-name
resolution path so a fallback chain can be configured as well as composed in code.

Purpose: RT-FR-09's requirement is explicit that these "MUST delegate to the PRD-04
implementations". The interesting design work is therefore not the retry logic — it exists — but
where the choice of *which port to call* lives, which is the question the assumption-delta detector
raised for this plan.

Output: `middleware/resilience.rs` with `ModelRetryMiddleware` and `ModelFallbackMiddleware`; a pure
`RetryPredicate::admits` in core with `retry::should_retry` refactored onto it; the single
port-resolution point in `execute_with_retry_and_temperature`; `ModelFallbackConfig::resolve_chain`.
</objective>

<assumption_delta_decision>
The `assumption-delta scan` for Phase 26 returned `detected: true` with one `pluralization` signal on
the term **fallback** ("retry/fallback middleware that delegates to the FT-05 implementation"). This
plan owns that seam, so the decision is recorded here.

- **Primary noun:** *the effective `LlmPort` for one model call.* Before this plan the run had one
  port, implicitly the service's own field. After it, a run's port may come from the service
  default, from a `FallbackLlmAdapter` built by `ModelFallbackMiddleware`, or (Phase 27) from a
  per-run scope. The noun that is now primary is not "the service's port"; it is "the port this call
  resolves to".
- **Decision: `promote`.** The resolution is promoted to exactly one point — a single accessor on
  `ModelCallContext` that returns the effective port, with the service's own `llm_port` **seeded**
  as the default rather than sitting on the far side of an `else`. `execute_with_retry_and_temperature`
  calls that accessor once; no other site chooses a port. The `Option<Arc<dyn LlmPort>>` field shape
  is unchanged and exactly as D-11 locks it — what is promoted is the resolution, not the wire
  shape, so nothing in D-11 is re-litigated.
- **Rationale:** add-alongside would leave the singular assumption ("the service's port is the port")
  written into a branch, and the next variant — Phase 27's `RunScope`-derived choice, or a per-node
  override — would add a third branch and a new precedence question. With one resolution point the
  next variant is a new default source, not a new branch.
- **Invariant test (accepted):** `model_call_port_is_resolved_at_exactly_one_point` — every model
  call in a run goes through the single accessor, for every supported source of port choice. It goes
  red the moment a future phase reintroduces a second resolution site.
</assumption_delta_decision>
