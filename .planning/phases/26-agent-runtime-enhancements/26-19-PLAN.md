<objective>
Make the tool loop real for shipped providers and name the tool-error policy the tree already has:
a prompt-level tool-call protocol that renders a tool catalogue and synthesizes a `function_call`
from the model's JSON envelope, a `FinishOnPlainAnswer` middleware so a tool-loop agent stops when it
answers, one shared error formatter with redact-then-bound sanitization, and a corrected `M-B-03`
that says what actually changed.

Purpose: two premises in the source documents are wrong about this tree and both are corrected here.
PRD RT-FR-24 and `MIGRATION.md` M-B-03 assume v0.9 aborted a run on tool failure — it did not, it
already fed the failure back. And RT-FR-23's "tool loop enabled" cannot be delivered at all without
a protocol, because no shipped adapter emits `function_call` and nothing renders a tool catalogue.

Output: `middleware/tool_protocol.rs`; `ToolResultFormatter::format_error`;
`redact_secret_patterns`; `PaladinError::ArmamentFailed`;
`PaladinExecutionService::with_tool_error_config`; the rewritten M-B-03.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-03 | Information Disclosure | a secret inside a tool error reaching the model, a log or an error | high | mitigate | Every fed-back reason passes through `redact_secret_patterns` **then** `bounded_excerpt` — the ordering `redaction.rs`'s module doc calls load-bearing, because bounding first can slice a secret across the truncation boundary and leak the tail (D-34, security.instructions.md). `redaction_precedes_bounding` positions a secret at the boundary specifically to catch a reversed implementation, and the acceptance criteria assert the call order by line number. |
| T-26-10 | Spoofing | a model synthesizing a call to a tool it was not given | medium | mitigate | The envelope is only honoured when the named tool is present in `list_armaments()`; an unknown name leaves `function_call` as `None` and the text is returned to the model (`an_unknown_tool_name_in_the_envelope_is_not_synthesized`). `validate_call` still gates arguments afterwards, so the synthesis path is no weaker than a native one. |
| T-26-61 | Tampering | overwriting a real adapter's `function_call` | medium | mitigate | The middleware acts only when `function_call` is `None`, so a consumer-supplied port or a future native implementation always wins (`a_response_that_already_has_a_function_call_is_untouched`) |
| T-26-26 | Spoofing | an adapter silently gaining a tool-calling surface | medium | mitigate | ADR-0042 is untouched: no `LlmRequest.tools`, no adapter file modified, capability flags unchanged, and `test_capabilities_tool_calling_matches_request_surface` is in this plan's verify command and acceptance criteria |
| T-26-62 | Tampering | fed-back tool errors read as instructions | medium | mitigate | The error lands in the tool-result position of the accumulated output, in the same framework-authored shape it lands in today, with the PRD's "you may retry or proceed without it" sentence — it is data in a result slot, not a system instruction (D-33, D-41) |
| T-26-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no package |
