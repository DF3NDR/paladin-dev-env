<objective>
Prove the whole Platform API architecture end-to-end on one thin path before any layer is built out:
a run submitted over HTTP is persisted, enqueued, picked up by a worker, driven through the real
`WarEngine`, and reaches `Completed` — observable through `GET /v1/runs/{run_id}`.

Purpose: PRD 06 §1's problem statement is that execution is welded to the HTTP connection. This plan
severs that weld on a single path so every later plan expands out from a proven skeleton instead of
discovering an architectural dead end after ten committed layers. It also lands the phase's literal
first test (PRD 06 §5 item 1, D-02): the pure status machine.

Output: `RunId`/`RunStatus`/`Run`/`AssistantRef` in `paladin-core`; `RunRepositoryPort`,
`RunQueuePort` and `RunSubmissionPort`; InMemory adapters for the first two; a facade
`RunSubmissionService` + minimal `RunWorkerPool`; `RunApiState`/`run_router` with `POST /runs` and
`GET /runs/{run_id}`; and one end-to-end test that exercises all of it.
</objective>

|-----------|----------|-----------|----------|-------------|-----------------|
| T-27-01 | Tampering | `RunStatus::try_transition` / `update_status` | high | mitigate | Status changes are only reachable through `try_transition`; the InMemory adapter routes every write through it so an out-of-band status write cannot compile. Exhaustive cross-product test in Task 2. |
