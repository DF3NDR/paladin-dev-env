<objective>
Close code-review finding CR-01 (critical) and the adjacent WR-01 (warning), both in the webhook
delivery path — the phase's most security-relevant surface: an outbound HTTP client that carries a
credential-shaped header to a caller-chosen URL.

CR-01: on any non-2xx response the service buffers the receiver's **entire** body into memory before
the 256-character truncation applies, and the client sets no response-size cap. Any authenticated
`User`-role principal can point a webhook at a host they control, answer every attempt with a 5xx and
a multi-gigabyte body, and repeat it by submitting more runs — a repeatable memory-exhaustion vector.

WR-01: when the run lookup that supplies the signing secret fails with a transient backend error, the
service silently signs with an empty key and sends anyway, burning one of the delivery's five attempts
and delivering a payload whose signature a correct receiver must reject.

Purpose: PLAT-05 / PLAT-FR-14, D-41/D-42/D-43, and `security.instructions.md`'s manual
credential-handling review, which this plan extends rather than replaces.

Output: a bounded response reader in the webhook client, its use on the only path that reads a body,
a send-suppressing retry on signing-key load failure, and tests for each.
</objective>

    - Reading a 1 MiB response body through the bounded reader with a 64 KiB cap returns exactly
      64 KiB worth of characters and stops; the remainder is never buffered.
    - A body smaller than the cap is returned whole and unchanged.
    - A body whose byte length is exactly the cap is returned whole, with no off-by-one truncation and
      no extra chunk read.
    - Invalid UTF-8, or a multi-byte character straddling the cap, yields a lossy replacement rather
      than a panic or an error.
    - A 5xx delivery attempt against a receiver returning a very large body still records a `Retrying`
      outcome with a `last_error` inside the 256-character budget, with any secret pattern redacted.

  <action>
    In `client.rs`, add `pub(crate) const MAX_ERROR_BODY_BYTES: usize = 64 * 1024;` and
    `pub(crate) async fn read_bounded_body(response: reqwest::Response, cap: usize) -> String`.
    Implement it as a chunk-at-a-time drain that accumulates into a `Vec<u8>` and stops the moment the
    accumulated length reaches `cap`, taking only the prefix of the chunk that fits; decode the result
    with `String::from_utf8_lossy`. A transport error mid-read yields whatever was accumulated so far
    rather than discarding it (the diagnostic is still useful) — never a panic, never an `unwrap`.
    Rustdoc it with the threat it closes: the response body is attacker-influenced (the target URL is
    caller-chosen, only address-class-constrained by the SSRF guard), a 5xx is retried up to
    `max_attempts`, and the caller can trigger unlimited deliveries — so the bound must apply during
    the read, not after it. State that `Content-Length` is deliberately not trusted as the bound,
    because a receiver controls it.

    them: a mockito 500 whose body is an order of magnitude larger than a small test cap (assert the
    returned length equals the cap); a small body (assert it is returned whole); and a body exactly at
    the cap (assert no truncation and no error). Use a small explicit cap in the tests rather than the
    64 KiB constant so they stay fast.

    the timeout/connect-error path, `retry_or_dead` and every status decision untouched. Note in the

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Caller → webhook target URL | Any authenticated principal chooses the destination; only its address class is constrained. |
| Webhook receiver → `paladin-server` process | The receiver's status line, headers and body are attacker-influenced input read by this process. |
| Delivery row → `GET /runs/{id}/webhook-deliveries` | Captured diagnostics are persisted and readable over the API. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-27-22-01 | Denial of service | unbounded response-body read on the failure path (CR-01) | critical | mitigate | `read_bounded_body` caps the read at `MAX_ERROR_BODY_BYTES` as it streams; `Content-Length` is not trusted; a mockito body an order of magnitude over the cap proves the stop. |
| T-27-22-02 | Tampering / Repudiation | delivery sent with a signature from an unloadable key (WR-01) | high | mitigate | The error arm reschedules and returns before any request is issued; a receiver mock with `expect(0)` proves no send. |
| T-27-22-03 | Information disclosure | a credential inside a receiver's error page persisted in `last_error` | high | mitigate | Redact-then-truncate order preserved: the bounded body still passes through `redact_secret_patterns` before `bounded_excerpt`. |
| T-27-22-04 | Information disclosure | credential header forwarded to a redirect target | high | mitigate | Unchanged and re-asserted: the client's no-redirect policy and its existing test stay in place; 3xx dead-letters. |
