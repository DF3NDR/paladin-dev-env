<objective>
Close verification gaps 4 and 5, the two remaining CI-gate failures.

Gap 4: the `api-surface` job fails on a real diff that is not a real API change — the committed
`.project/current-exports.txt` was generated with a local nightly whose `cargo-public-api` output
orders `RunWorkerPool<W>`'s synthesised auto-trait bounds differently from CI's nightly
(`Sync + Send` locally, `Send + Sync` on CI, repeated across the Freeze/Send/Sync/Unpin/UnsafeUnpin
impls). Regenerating alone would fix today and break again on the next nightly; canonicalising the
ordering fixes the class.

Gap 5: `tests/integration/e2e_platform_api_test.rs` — PRD 06 acceptance criterion 1, the full
assistant → run → SSE → `AwaitingInput` → webhook → resume → complete → history → fork lifecycle —
is never executed by CI. Its `[[test]]` entry requires the `web-server` feature; the `test` job runs
`--lib --bins`, the `integration` job enables `integration-tests` (which does not imply
`web-server`), and `feature-flags.yml`'s `web-server` leg is `--lib` only. The test passes locally.

Purpose: PLAT-06 — the phase's production-shaped-surface claim rests on gates that actually run and
actually mean something.

Output: a toolchain-order-independent extraction, a regenerated baseline proven to contain no real
API change, and a named CI job that runs the flagship end-to-end test on every push and PR.
</objective>

  <reversibility rating="reversible">A filter in a developer script; removing it and regenerating restores the previous behaviour exactly.</reversibility>
  <files>scripts/normalize-api-bounds.py, scripts/extract-public-api.sh</files>
  <read_first>
    - `scripts/extract-public-api.sh` — the header lines, the `cargo public-api --simplified` append
      and its `|| { ... }` failure handler, and the `Total public items:` summary.

      applies symmetrically to both sides.
    - `.project/current-exports.txt` lines 3613-3631 — the exact `RunWorkerPool<W>` block that drifts,

    - `.planning/phases/27-platform-api/27-VERIFICATION.md` — gap 4, including the observation that

  </read_first>
  <behavior>
    - Two input lines identical except that one writes an adjacent marker-bound pair in the opposite
      order normalise to the same output line.
    - A maximal run of adjacent marker bounds is emitted in alphabetical order; a lifetime, a
      non-marker trait or any other token ends the run and is left where it is.
    - A line containing no marker-bound run is passed through byte-identically.
    - Item names, paths, generics, argument lists and return types are never reordered or rewritten.
    - `python3 scripts/normalize-api-bounds.py --self-test` exercises all four cases and exits 0.
  </behavior>
  <action>
    Create `scripts/normalize-api-bounds.py`: a standard-library-only stdin-to-stdout filter that
    canonicalises the ordering of adjacent auto-trait marker bounds. Match maximal runs of `+`-joined
    fully-qualified marker paths drawn from a fixed, explicit set — `core::marker::Send`,
    `core::marker::Sync`, `core::marker::Unpin`, `core::marker::Freeze`, `core::marker::UnsafeUnpin` —
    and re-emit each run with its members sorted alphabetically and joined with the same separator
    spacing the input used. Anything not in that set terminates the run and is untouched. Keep the set
    a named module constant with a comment explaining that it is deliberately closed: a broader match
    risks reordering semantically-ordered bounds.

    Add a `--self-test` mode covering the four behaviours above, including one real line lifted from
    the `RunWorkerPool<W>` block in both observed orders, asserting they converge. Print a single `ok`
    line and exit 0 when all cases pass; print the failing case and exit non-zero otherwise.

    Wire it into `scripts/extract-public-api.sh` by piping the `cargo public-api --simplified` output
    through it before the append, keeping the existing failure handler working (the script already runs
    under `pipefail`). Extend the script's header comment with why the filter exists: rustdoc's
    synthesised auto-trait `impl` bounds have no guaranteed order across toolchain versions, so an
    un-normalised baseline records a property of the machine that generated it rather than a property
    of the API.
  </action>
  <acceptance_criteria>
    - `python3 scripts/normalize-api-bounds.py --self-test` exits 0 and prints a line matching `ok`.
    - `printf 'a + core::marker::Sync + core::marker::Send)\n' | python3 scripts/normalize-api-bounds.py` and `printf 'a + core::marker::Send + core::marker::Sync)\n' | python3 scripts/normalize-api-bounds.py` produce identical output.
    - `printf 'pub fn foo(bar: &str) -> usize\n' | python3 scripts/normalize-api-bounds.py | grep -qx 'pub fn foo(bar: &str) -> usize'`.
    - `grep -c 'normalize-api-bounds.py' scripts/extract-public-api.sh` is 1.
    - `bash -n scripts/extract-public-api.sh` exits 0.
  </acceptance_criteria>
  <verify>
    <automated>python3 scripts/normalize-api-bounds.py --self-test 2>&amp;1 | grep -q "ok" &amp;&amp; test "$(printf 'a + core::marker::Sync + core::marker::Send)\n' | python3 scripts/normalize-api-bounds.py)" = "$(printf 'a + core::marker::Send + core::marker::Sync)\n' | python3 scripts/normalize-api-bounds.py)"</automated>
