<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Trace record → process log stream | Every record becomes a log line an operator, log shipper or aggregator can read. |
| Run execution path → sink implementations | Third-party or misbehaving sink code runs alongside a production run. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-28-06-01 | Information disclosure | Log lines carrying state values or prompt text | high | mitigate | The record carries field names and byte sizes by default; `NodeProgress::StreamChunk` carries a byte count and never the text; `ParleyRaised` carries no prompt; the log sink serializes whatever the record holds and adds nothing. |
| T-28-06-02 | Denial of service | Default-on logging flooding an operator's log pipeline | medium | mitigate | Bounded queue with counted drops upstream; the heartbeat rate limit; `trace.log_sink` and `RUST_LOG=paladin::trace=off` both silence it without a code change (D-11). |
| T-28-06-03 | Tampering | A sink altering run behaviour | high | mitigate | `build_run_sink` produces a `CompositeSink` behind the never-awaited dispatcher; `worker_run_result_is_identical_with_and_without_sinks` asserts result equality; the prohibition above states the rule. |
| T-28-06-04 | Repudiation | Producers below the engine stamping their own counters | medium | mitigate | Every below-engine producer takes `Arc<dyn TraceEmitter>`, never a raw sink; the worker pulls one handle per run; `fallback_hop_lands_in_the_run_sequence` proves interleaving (D-03). |
</threat_model>
