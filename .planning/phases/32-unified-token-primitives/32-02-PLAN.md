<objective>
Build the second half of this phase's collapse: one context-window resolver. This plan writes the
equivalence snapshot first, against the code as it stands with two independent precedence walks
(D-13), then creates `paladin_llm::window` — the shared resolver with an explicit fallback-policy
enum rather than a strict boolean (D-01), placed as a top-level module returning both the resolved
count and the step that produced it (D-02) — with its four precedence tests. Plans 32-03 and 32-04
then make `Commissary` and `HistoryTrimmer` call it.

Purpose: `Commissary::new`'s inline capability-or-fallback guard and `HistoryTrimmer::resolve_limit`
are the same precedence walk written twice, with different terminal behaviour (one refuses, one
defaults). A fourth precedence source added later would have to be added in both places, and the two
could silently disagree about what "unknown window" means. One function with an explicit policy
makes the refusal a type, not a convention.

On D-13's ordering: the snapshot's subject is the WINDOW resolution, and plan 32-01 changed only the
exactness argument — it never touched a resolved window. Writing the fixtures here, green against the
inline guard and against `resolve_limit`'s three-step body, before either is replaced, is exactly the
pre-refactor baseline D-13 specifies.

Output: six committed-green equivalence fixtures; a new `paladin_llm::window` module with a
policy enum, a source enum whose labels preserve `HistoryTrimmer`'s logged wording, a resolved-window
value, its own error type and five tests; the module registered in `paladin-llm`'s module list and
re-exported from the facade.
</objective>

<assumption_delta_decision>
The deterministic detector fired one `pluralization` signal on this phase's scope (term: `fallback`,
in the ROADMAP success criterion "config-table hit, provider-capability hit, default fallback and
strict refusal"). A second kind of terminal fallback is genuinely being introduced: until now the
only terminal step was `HistoryTrimmer`'s framework default, and `Commissary`'s caller-supplied
fallback lived in a separate, unnamed inline expression.

- **Primary noun:** the *window source* — which of four steps produced a resolved context window.
  `WindowSource` in `paladin_llm::window` is now the primary representation; `history.rs`'s
  three-variant `LimitSource` is demoted to a detail of one consumer.
- **Decision: promote.** Plan 32-04 deletes `LimitSource` and consumes `WindowSource` directly
  rather than keeping both enums alive side by side. Adding the new general representation
  *alongside* a still-required `LimitSource` would leave two enums with the same shape — exactly the
  duplication this phase exists to remove — and a fifth precedence source would again have to be
  added twice. CONTEXT.md D-05 offers either option; promotion is the one consistent with the phase's
  own charter.
- **Companion invariant test (accepted):** the source-label invariant test in `window.rs` walks an
  exhaustive array of every `WindowSource` variant and asserts each label is non-empty, unique, and
  carries its required substring. A future phase that adds a variant without a label, or renames a
  label out of the substrings `HistoryTrimmer`'s precedence tests assert on, goes red immediately
  rather than silently regressing the logged source an operator reads.
</assumption_delta_decision>
