  <action>
Build `34-AUDIT.md` §5, the Phase 35 work list, from every `MB-nn` row in §2, and §6, the Phase 36
work list, from every `RD-nn` row in §3 and every `EX-nn` row in §4. The partition rule is
absolute: an `MB` goes to 35, an `RD` or `EX` goes to 36, and nothing else enters either list.

Both lists use the columns
`| Order | ID | Classification | Size | Location | Cites (Phase N — item (REQ)) | Blocks | Evidence anchor |`.
`Classification` is exactly one of the four the ROADMAP names: missing page, stale content, rustdoc
warning or broken intra-doc link, non-compiling or obsolete example. `Size` is the `S`/`M`/`L` the
originating row already carries — copy it, do not re-derive it, and if a row lacks a size that is a
defect to fix in the originating row first. `Location` is the page path, or the `file:line`, or the
example path — whatever the originating row carries, in the same form so a grep for the location
finds both rows. `Cites` is copied from the originating row. `Blocks` names the IDs this item must
precede, and is the column that drives the ordering.

Order each list per D-21: first the `L` items that block others — a missing page that stale pages
should link to, a rustdoc family whose fix pattern repeats across many rows, an example that other
examples' README sections reference — then the remainder in page order for §5 (following
`docs/src/SUMMARY.md`'s nav order, with orphans at the end) and in crate order for §6 (rustdoc
rows grouped by crate, then the example rows). Fill the `Blocks` column honestly: leave it empty
when an item blocks nothing rather than inventing a dependency to justify a position.

Where many `RD-nn` rows share one fix pattern — the same broken link target repeated across a
crate, or one undocumented item family — group them under a single ordered lead item and list the
followers' IDs in its `Blocks` cell, but keep every follower as its own row. Phase 36 closes items
by ID; collapsing followers into a count would break that.

Head each list with a short statement of what the list is sufficient for, naming the consuming
command (`/gsd-plan-phase 35`, `/gsd-plan-phase 36`), stating that those phases may re-batch but
must close every ID, and repeating the measured HEAD SHA with the D-23 re-run rule: if the branch
moves before they plan, they re-run the D-12/D-16 commands and diff against these rows rather than
trusting the counts.

Then reconcile in both directions and record the reconciliation in the audit: every `MB`/`RD`/`EX`
ID that appears anywhere in §2, §3 or §4 appears in exactly one work list, and every ID in a work
list resolves to an originating row. Record the counts per list and per classification.

Append the reconciliation commands to `34-EVIDENCE.md` as numbered rows plus the SC5 `git status`.
