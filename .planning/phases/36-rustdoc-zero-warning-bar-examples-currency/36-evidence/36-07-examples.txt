Design note: the AwaitingInput Waypoint's own `vanguard` field is the parleying node itself
(`approve`) -- confirmed empirically from `superstep.rs`'s HITL-01 suspension arm. `replay`/
`fork` never populate `responses_by_node` (only `resume_with` does), so replaying from the
pause point re-dispatches the Gate's "first visit" path and raises a brand-new parley id on
a new branch -- exactly what the run output shows. Resuming that new branch with the OPPOSITE
decision (`false` instead of `true`) produces a genuinely divergent `path` result ("cancel:
release withheld" vs. the mainline's "act: release deployed"), satisfying the plan's
"replay ... and print the divergent result" must-have without needing `fork`'s edit-merge
(which would have required a graph shape where the fork point precedes the routing decision,
not the Gate's own resolution -- the Gate is the routing edge's own source here).
