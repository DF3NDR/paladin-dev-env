Design note: the AwaitingInput Waypoint's own `vanguard` field is the parleying node itself
(`approve`) -- confirmed empirically from `superstep.rs`'s HITL-01 suspension arm. `replay`/
`fork` never populate `responses_by_node` (only `resume_with` does), so replaying from the
pause point re-dispatches the Gate's "first visit" path and raises a brand-new parley id on
a new branch -- exactly what the run output shows. Resuming that new branch with the OPPOSITE
decision (`false` instead of `true`) produces a genuinely divergent `path` result ("cancel:
release withheld" vs. the mainline's "act: release deployed"), satisfying the plan's
"replay ... and print the divergent result" must-have without needing `fork`'s edit-merge
(which would have required a graph shape where the fork point precedes the routing decision,
not the Gate's own resolution -- the Gate is the routing edge's own source here).

## Task 2: examples/graceful_shutdown.rs

Command: `timeout 120 env -u OPENAI_API_KEY -u ANTHROPIC_API_KEY -u DEEPSEEK_API_KEY cargo run --example graceful_shutdown`
Exit code: 0 (program terminates on its own well within the 120s bound -- actual wall time ~1.4s)

Full stdout:
```
Graceful Shutdown: Drain, Grace Period, Toggle

1. Drain in-flight work (EX-74)

   (In a deployed server, ShutdownCoordinator::cancel_and_wait is driven by the
    process's SIGTERM/SIGINT handler -- this program triggers it directly so it
    terminates on its own, never waiting on a real signal.)

   coordinator drain outcome = Drained
   run outcome               = Halted, waypoint 01a0b142-8ca5-7291-b06d-f788324dc49a
   checkpoint durable at the cut: 2 completed record(s), vanguard re-lists [NodeId("slow")] for resume
     node fast -> Succeeded
     node slow -> Skipped { reason: "shutdown" }
   fast_result = Some("fast finished") (finished before the grace deadline)
   slow_result = None (still None -- aborted, never merged)

2. Configure the grace period (EX-75)

   before APP_ENGINE_SHUTDOWN_GRACE_SECS: shutdown_grace_secs = 30
   after  APP_ENGINE_SHUTDOWN_GRACE_SECS: shutdown_grace_secs = 1

   running the drain again with the overridden grace wired into the engine:

   coordinator drain outcome = Drained
   run outcome               = Halted after 1.03s (bounded by the overridden 1s grace, not the default 30s)
   slow_result = None (still None -- aborted at the new, shorter grace)

3. Toggle graceful shutdown off and on (EX-76)

   APP_ENGINE_GRACEFUL_SHUTDOWN=false -> graceful_shutdown = false
   disabled -> exits immediately without waiting: TimedOut (in_flight = 1)

   APP_ENGINE_GRACEFUL_SHUTDOWN=true  -> graceful_shutdown = true
   enabled  -> waits for in-flight work to drain: Drained (in_flight = 0)

Done -- fully offline, no provider API key was read.
```

Design note: Part 1 fans out two entry nodes ("fast", "slow") in one superstep so the Halted
Waypoint's own `completed` records show both outcomes side by side (`Succeeded` for the node
that finished inside the grace window, `Skipped { reason: "shutdown" }` for the one aborted
past it) -- confirmed against `over_grace_node_is_aborted_and_recorded_skipped`'s documented
behavior (`crates/paladin-battalion/src/engine/superstep.rs` test module). Part 2 reuses the
same fan-out graph with `EngineConfig::shutdown_grace_secs` wired straight into
`WarEngine::with_shutdown_grace`, and measures wall-clock elapsed time to prove the abort
happened at the overridden 1s bound, not the unmodified 30s default. Part 3 mirrors
`paladin-server.rs`'s own `graceful_shutdown ? shutdown_grace_secs : 0` derivation to make the
toggle's documented behavior ("exits immediately without waiting" vs. "waits up to
shutdown_grace_secs for in-flight runs to drain") concretely observable through the same
`ShutdownCoordinator` API Part 1 used, rather than only printing two config values.
