Task 1: examples/node_result_cache.rs (EX-81, EX-82, gated redis-cache, build-only)
------------------------------------------------------------------------------------------------

Files: examples/node_result_cache.rs, Cargo.toml

Program: constructs a RedisNodeCache (RedisNodeCacheConfig::default(), localhost:6379) and
wires it onto a WarEngine via with_node_cache (EX-81); runs a single-Function-node graph twice
under different threads -- run 1 executes the node and stores the result (cache_hit=false), run
2 is served from the cache (cache_hit=true, no re-execution, proven via a shared AtomicU64
execution counter and the persisted Waypoint's own NodeExecutionRecord.cache_hit field); then
toggles APP_NODE_CACHE_ENABLED off via NodeCacheConfig::apply_env_overrides, builds a THIRD
graph with no CachePolicy attached and an engine with no cache backend wired (attaching a
CachePolicy to a node whose engine has no backend is a typed validation error, never a silent
no-op -- confirmed against crates/paladin-battalion/src/engine/mod.rs's own
`a_cache_policy_without_an_engine_cache_fails_validation` test), and re-runs to show the node
re-executes (EX-82). This program needs a running Redis server (`make services-up`), so per D-16
it is BUILD-VERIFIED ONLY -- never executed by any automated check here or in CI. The header
comment states this explicitly.

Task 2 (part 1): examples/observability_tracing.rs (EX-100, EX-101, EX-102, EX-108)
------------------------------------------------------------------------------------------------

Files: examples/observability_tracing.rs

observability_tracing.rs -- default features, fully runnable offline:
  Part 1 (EX-100): runs a small Function-node graph with a custom in-process RecordingSink
    (a TraceSink) attached via a CompositeSink, and prints every captured TraceRecord's
    envelope (seq/at/thread_id/run_id) plus the real TraceEvent variant name it carried.
  Part 2 (EX-101): constructs a TraceConfig and prints its resolved log_sink/persist/
    state_values/otel.enabled fields, then calls the facade's own sink-composition function
    (paladin::infrastructure::telemetry::build_run_sink) twice -- once with log_sink=false (no
    sink attached at all) and once with only that field flipped to true (a sink attaches) --
    showing the changed field's effect directly through the same function production code uses.
  Part 3 (EX-102): sets PALADIN_TRACE_OTEL_ENABLED=true in-process, reloads the config via
    apply_env_overrides, and shows config.otel.enabled flips true -- but states that export
    additionally requires the `otel` Cargo feature, which THIS build lacks, so build_run_sink's
    OTel branch is compiled out and nothing observable changes even with the flag on. Points at
    the sibling observability_otel_export program.
  Part 4 (EX-108): reads the persisted run_traces rows back from the same run (flushed via a
    PersistingTraceSink over an InMemoryRunTraceStore) through RunTracePort::read, printing
    run_id/seq/event name per row.

Task 3: examples/eval_scenarios_demo.rs (EX-105, EX-106, EX-107)
------------------------------------------------------------------------------------------------

Files: examples/eval_scenarios_demo.rs (no Cargo.toml change -- paladin-eval is an
unconditional dev-dependency of the root package, confirmed at Cargo.toml:318)

Program: builds a one-Paladin-node WarGraph (built with a mock-adapter-backed Paladin, never
actually called -- ScenarioRunner substitutes its own scripted PaladinPort at run time, keyed by
Paladin name) and registers it under ScenarioRunner via register_graph.
  Part 1 (EX-105): declares a two-case Scenario directly in Rust (the same Scenario/Case/
    Assertion types a .eval.yaml file deserializes into -- paladin_eval::eval_scenarios! itself
    expands to a fn main() incompatible with this program's own main(), so this program drives
    the SAME types and the SAME ScenarioRunner::run_case the macro's expansion drives), and runs
    both cases, printing each case name and PASSED/FAILED.
  Part 2 (EX-106): prints PALADIN_EVAL_LIVE's current value and what enabling it changes (a real
    provider call instead of the scripted mock text), then calls check_live_mode(false) and
    matches on the typed refusal (Err(FlagNotSet)) rather than propagating it -- proving the
    non-live gate refuses immediately without ever reading a provider key.
  Part 3 (EX-107): writes a real .eval.yaml scenario file to a tempfile::tempdir(), prints the
    exact `paladin eval run "<glob>"` CLI command line, then drives the SAME glob pattern through
    ScenarioRunner::trials (proving 1 trial resolves) and Scenario::from_path + run_case
    in-process, printing the resulting case's PASSED/FAILED -- so the printed command and the
    demonstrated behaviour are the same thing. The workspace's own CLI binary is never spawned as
    a subprocess (it is gated behind the `cli` feature).
