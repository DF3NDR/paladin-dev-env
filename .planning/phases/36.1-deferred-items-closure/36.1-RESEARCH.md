## D-03 feasibility — VERIFIED FEASIBLE, no public signature change needed

**The `FailRun` arms exist at two locations**, not one — CONTEXT.md's citation
(`paladin_execution_service.rs:1640-1652`) covers only the handoff-execution arm. A second,
structurally identical arm exists for regular (non-handoff) Arsenal tool execution:

| Arm | File:line | Context |
|---|---|---|
| Handoff execution `Err` branch | `src/application/services/paladin/paladin_execution_service.rs:1637-1653` | `match self.effective_tool_error_mode(&effective_function_call.name) { ToolErrorMode::FeedToModel => { self.formatter.format_error(&effective_call, &e.to_string()) } ToolErrorMode::FailRun => { return Err(PaladinError::ArmamentFailed { tool: effective_function_call.name.clone(), reason: e.to_string() }); } }` |
| Regular Arsenal tool `Err` branch | `src/application/services/paladin/paladin_execution_service.rs:1756-1774` | Same shape: `ToolErrorMode::FeedToModel => self.formatter.format_error(&effective_call, &e.to_string())`, `ToolErrorMode::FailRun => return Err(PaladinError::ArmamentFailed { tool: effective_call.tool_name.clone(), reason: e.to_string() });` |

Both arms currently pass raw `e.to_string()` into `reason` under `FailRun`. **Both must be fixed**
(the plan's scope should cover both, not just the CONTEXT-cited one — this is the same defect
class the row names, and Row 38's own description cites only line 1648 but the ledger row text
doesn't preclude the second occurrence; fixing only one would leave the second arm re-triggering
the same class of finding).

**The formatter:** `src/infrastructure/adapters/arsenal/tool_result_formatter.rs`.

```rust
// Line 245 — pub fn, returns a FULL multi-line block, not a bare sanitized string:
pub fn format_error(&self, call: &ArmamentCall, reason: &str) -> String {
    // "🔧 Tool Execution: {tool}\nResult: FAILED\nError: {sanitized}\nYou may retry …\n"
}

// Line 273 — the ACTUAL sanitizer, currently private (module-private, not pub(crate)):
fn sanitize_tool_text(text: &str) -> String {
    let redacted = paladin_llm::redaction::redact_secret_patterns(text);
    paladin_llm::redaction::bounded_excerpt(&redacted, paladin_llm::redaction::RESPONSE_EXCERPT_CHAR_BUDGET)
}
```

`format_error`'s doc comment (line 220-225) confirms `sanitize_tool_text` is "the ONE sanitization
point for tool text this module uses". **Reusing `format_error` verbatim for `reason` would be
wrong** — it would embed "🔧 Tool Execution: {tool}\nResult: FAILED\n…\nYou may retry with
corrected arguments…" inside `PaladinError::ArmamentFailed.reason`, which is displayed via
`#[error("tool `{tool}` failed: {reason}")]` — producing a nonsensical doubled/multi-line error
message. The doc comment on `ArmamentFailed.reason`
(`crates/paladin-core/src/platform/container/paladin_error.rs:161-163`) says reason should be
"the same **sanitized text** `ToolResultFormatter::format_error` would have fed back to the
model" — i.e. the sanitized *content*, not the full formatted wrapper. This confirms
`sanitize_tool_text`'s output is the correct thing to put in `reason`, not `format_error`'s output.

**The fix:** change `fn sanitize_tool_text` (line 273) to `pub(crate) fn sanitize_tool_text`, then
in both `FailRun` arms replace `reason: e.to_string()` with
`reason: crate::infrastructure::adapters::arsenal::tool_result_formatter::ToolResultFormatter::sanitize_tool_text(&e.to_string())`
(it is an associated function, not a method — no `&self` in its signature — so it is called as
`ToolResultFormatter::sanitize_tool_text(...)`, not `self.formatter.sanitize_tool_text(...)`).

**Why this doesn't move `make api-surface`:** `scripts/extract-public-api.sh` runs
`cargo public-api --simplified` (line 38), which enumerates only publicly-*reachable* items.
`pub(crate)` is crate-internal visibility — `cargo public-api` never lists it. **Both files are
in the same crate** (facade `paladin`/`paladin-ai`; `paladin_execution_service.rs` already
imports `crate::infrastructure::adapters::arsenal::tool_result_formatter::ToolResultFormatter` at
line 78, confirming same-crate reachability), so `pub(crate)` is sufficient — no need for a new
`pub fn` on `ToolResultFormatter`, which WOULD move the API surface and violate D-03's "no public
item changes" bound.

**Where the pinning test belongs:** the `#[cfg(test)] mod middleware_wiring_tests` module
(`paladin_execution_service.rs:5262`), which already contains
`fail_run_produces_a_structured_error` (line 5852, asserting `reason.contains("boom")` — a loose
assertion that would NOT catch a raw-secret regression) and the `FailingArsenal` test double
(struct at line 5768, `impl ArsenalPort for FailingArsenal` at line 5787). A new test
`fail_run_redacts_a_secret_in_the_reason` should construct `FailingArsenal::new("...a
secret-shaped string like Authorization: Bearer sk-live-...")`, run under `ToolErrorMode::FailRun`,
and assert `!reason.contains("sk-live-...")` — mirroring the existing redaction-fixture pattern at
`tool_result_formatter.rs:448` (`format_error_redacts_a_secret_in_the_reason_before_bounding`,
which builds `"upstream rejected: Authorization: Bearer sk-live-abcdef0123456789"` and asserts the
digits are absent from the formatted output). Because both `FailRun` arms are structurally
identical and route through the exact same code path with different tool-name-source variables,
one pinning test per arm (or one test exercising each of the two call sites via the handoff vs.
regular-tool code paths) closes the gap Row 38 names.

**MIGRATION.md §9.1 already documents the sanitized contract** (row `M-B-03`, verified verbatim):
"This phase adds `FailRun` as a new opt-in (`PaladinError::ArmamentFailed { tool, reason }`) and
sanitizes the fed-back text (redact-then-bound, D-34) before the model ever sees it — the
sanitization is the ONLY observable difference for an existing user." Per CONTEXT D-26's own
conditional, **no `MIGRATION.md` edit is needed** — the fix restores an already-documented
contract rather than correcting stale documentation.

### Anti-Patterns to Avoid
- **Do not call `self.formatter.format_error(...)` for `reason`** — it returns a whole
  "Tool Execution: …\nResult: FAILED\n…\nYou may retry…" block, not a bare sanitized string; this
  would produce a garbled `PaladinError::ArmamentFailed` Display message.
- **Do not add a new `pub fn` to `ToolResultFormatter` for D-03** — this widens the public API
  surface and violates D-03's explicit "no public item changes" bound; `pub(crate)` is sufficient
  and invisible to `cargo public-api`.
- **Do not use `paladin-storage`'s in-memory adapters inside `paladin-ports` doctests** —
  `paladin-ports/Cargo.toml` has no dependency on `paladin-storage` (verified: only
  `paladin_core`, `async-trait`, `serde`, `thiserror`, `uuid`, `chrono`, `tokio`, `serde_json`,
  `futures`, `log`, `md5`, `mime_guess`); a doctest can only reach items in its own crate or its
  crate's dependencies. Adding `paladin-storage` as a dev-dependency of `paladin-ports` would also
  violate `CLAUDE.md`'s "dependencies flow inward only" rule (ports is application-layer,
  paladin-storage is infrastructure).
- **Do not fence the 19 new doctests `rust,ignore`** — D-10 explicitly forbids `ignore`; the
  existing `scripts/check-public-api-examples.sh` gate only checks for the heading text (verified
  by reading the script: it never inspects fence attributes), so an `ignore`-fenced heading would
  silently pass the gate while violating D-10's independent, stricter requirement that the plan
  must self-enforce (e.g. by confirming the doctest pass count in `cargo test --workspace --doc`
  grows by exactly 19, and by grepping the 19 new sections for the literal string `ignore`).

## Common Pitfalls

### Pitfall 1: Confusing `format_error`'s full block with the bare sanitized reason
**What goes wrong:** Calling `self.formatter.format_error(&call, &e.to_string())` and assigning
its return value directly to `PaladinError::ArmamentFailed.reason` embeds "🔧 Tool Execution:
{tool}\nResult: FAILED\nError: {text}\nYou may retry…" into a field whose `#[error(...)]` Display
already prefixes `"tool `{tool}` failed: {reason}"`, producing a garbled, doubled error message.
**Why it happens:** `format_error` and `sanitize_tool_text` have similar-sounding purposes but
different return shapes; `sanitize_tool_text` is the private helper actually referenced by
`ArmamentFailed`'s own doc comment.
**How to avoid:** Use `sanitize_tool_text` (made `pub(crate)`) directly, not `format_error`.
**Warning signs:** A test asserting `reason.contains("boom")` would NOT catch this mistake (the
existing `fail_run_produces_a_structured_error` test at line 5852 uses exactly this loose
assertion) — write the new pinning test to check the reason does NOT contain formatting
boilerplate like `"Tool Execution:"` in addition to checking the secret is redacted.

### Pitfall 2: Treating `check-public-api-examples.sh --list`'s "OK" as "compiles cleanly"
**What goes wrong:** Assuming an existing `OK` row is a safe compilation-fence model to copy.
**Why it happens:** The script only checks for the heading text (`# Examples`), never fence type
or actual compilation — `FormationExecutionService`'s OK row is fenced ` ```ignore ` and its
example (`FormationExecutionService::new(paladin_port)`) would not even type-check as written
(missing imports, wrong arity is unverified since `ignore` skips it entirely).
**How to avoid:** Cross-check any "OK" row used as a style model against its actual fence
attribute before copying its shape; prefer the `VaultPort`/`TokenCounterPort` rows, which use
`no_run`/plain fences and do compile.
**Warning signs:** Grep the 19 new headings' surrounding fences for the literal string `ignore`
before closing SC2 — D-10 forbids it even though the gate script won't catch a violation.

### Pitfall 3: `paladin-ports` doctests silently failing to import a shipped adapter
**What goes wrong:** Writing a `RunRepositoryPort` doctest that does
`use paladin_storage::run::in_memory::InMemoryRunRepository;` — this will fail to compile because
`paladin-ports` (where the doctest physically lives) has no dependency edge to `paladin-storage`.
**Why it happens:** The orchestrator's own question 7 flags this exact trap; it is easy to assume
"the type exists in the workspace" implies "the doctest can import it," which is false — a
doctest's reachable namespace is bounded by ITS OWN crate's `Cargo.toml`, not the whole workspace.
**How to avoid:** For all 12 `paladin-ports` doctests, write a minimal local `struct` + `impl
TraitName for LocalStruct` inline in the doctest body, never an `use paladin_storage::...` import.
**Warning signs:** `cargo test --workspace --doc` failing with "unresolved import" or "no
external crate `paladin_storage`" on any of the 12 Port doctests.

### Pitfall 4: Reordering the closing-plan's ledger work before the fixing commits exist
**What goes wrong:** Minting a `fixed`-destined `WINDOWS.md` row before its closing commit's SHA
exists means the description's `"Closed by <sha> (36.1-NN)."` template has no SHA to cite.
**Why it happens:** `gsd-tools windows fixed <id>` takes no reason argument (confirmed:
`cmdWindowsMarkFixed` parses only a single positional `id`) — the commit SHA must live in the
row's `description`, set at `append` time, not at `fixed` time.
**How to avoid:** Follow D-18 literally: append happens (with the commit SHA already known, i.e.
after the fixing commit) as the FIRST step of the closing plan, then `fixed` is called
immediately after. This is why the ledger work is scoped to the closing plan, not the earlier
waves — the earlier waves' commit SHAs must already exist.
**Warning signs:** A `WINDOWS.md` row whose description says "Closed by <sha>" with a literal
placeholder or a wrong/nonexistent SHA.
