## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| external tool / MCP server → facade service | an untrusted Armament response body or transport error message enters `PaladinExecutionService` | tool/provider output that may carry an API key — **the phase's only credential-bearing boundary** |
| facade service → structured error surface | `PaladinError::ArmamentFailed.reason` is logged, displayed and returned to callers | sanitized (redact-then-bound) text |
| formatter module → application service | `ToolResultFormatter::sanitize_tool_text` widened to crate visibility | none outward — `pub(crate)`, not on the public API baseline |
| build configuration → test assertion | the `cli`-isolation guard reads the declared `[features] default` array, not the compiled feature set | repository-public manifest text |
| doctest namespace → crate dependency graph | a `paladin-ports` doctest may reach only its own crate's dependencies | none — architectural (dependency direction) |
| example code → reader's own wiring | a reader copies a `# Examples` block into their application | placeholder values only |
| documentation page → contributor action | a reader copies a path, command or workflow from the book | illustrative CI/CD and test-tree content |
| local gate → required CI check | `check-public-api-examples.sh` wired into the `lint` job gates every future PR | gate exit status |
| ledger / closure table → downstream phases and release tooling | Phase 37, `36.1-VERIFICATION.md`, ship and milestone commands read `WINDOWS.md` counts and the closure table by identifier | disposition records, commit SHAs |
| local measurement → CI measurement | devcontainer and runner toolchains may differ; the gate lives on the runner | recorded figures and run conclusions |
| repository → published changelog | changelog bullets reach users with no access to planning artifacts | public release notes |

## Observations (outside the register — non-blocking)

The plan-time register is complete, so this audit verified mitigations and did **not** scan for new
threats. Three things surfaced while gathering evidence. None is a threat, none changes
`threats_open`, and none is actioned here.

- **O-1 — `unwrap()`/`expect()` in new `# Examples` blocks.** 44 occurrences across 12 files added
  this phase, 43 of them in `crates/paladin-ports` trait examples, all in visible (not `# `-hidden)
  lines. T-36.1-31 is scoped to the webhook service's fallible constructor, which is handled
  correctly, so the register is satisfied. This is a *convention* gap against
  `rust.instructions.md` ("Examples should use `?` operator, not `unwrap()`"), not a security one.
- **O-2 — Ledger row 38 carries no SHA in its own description.** Structural, not an omission: the
  row was authored open in Phase 36, `windows fixed <id>` accepts no reason, and T-36.1-54 forbids
  the hand edit that would add one. Traceability is preserved in the closure table (line 17). A
  reader starting from `WINDOWS.md` alone must follow one hop to `36.1-EVIDENCE.md`.
- **O-3 — Seven `fixed` ledger rows that pre-date this phase also lack a SHA.** Out of scope for
  T-36.1-55 (which governs rows this phase minted or moved); recorded so a later auditor does not
  rediscover it as new.

**Standing caveat (unchanged by this phase):** there is still no merge-gating static taint analysis
of first-party Rust — CodeQL runs advisory-only. T-36.1-05, the one credential-handling change in
this phase, was therefore verified by the manual redact-before-truncate review that
`.github/instructions/security.instructions.md` names as the primary control, plus its pinning test.
