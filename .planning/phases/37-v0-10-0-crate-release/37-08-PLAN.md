<objective>
Hand the two human acts to the maintainer in the right order, verify read-only what can be
verified between them, and stop.

Purpose: this is the seam D-09's two-wave split is built around. D-03 puts the §11 tick after the
PR's CI is green and after the evidence is appended, so the maintainer signs what is visible;
D-02 reserves the merge and the tag push for the maintainer at one blocking checkpoint; D-12 makes
the wait a hard stop with a resume file rather than a parked watcher.
Output: a ticked §11 box (by the maintainer), a recorded post-tick final SHA, a read-only
confirmation that `paladin-eval` resolves on the registry, and the merge-plus-tag hand-off — then
the phase stops until the tag exists.

**This plan commits nothing to `feature/phase-33`.** The maintainer's tick commit must be the
branch's last content commit, so the notes this plan leaves (the updated `.continue-here.md` and
this plan's SUMMARY) stay in the working tree and are committed by plan 37-09 on `chore/37-close`,
which is cut from the tagged `main`. Uncommitted `.planning/` files during the merge-and-tag
window are harmless: the merge happens server-side on GitHub, tagging does not read the working
tree, and no `cargo publish` runs in that window.

**Reversibility.** D-02 and D-04 are rated `one-way` in CONTEXT.md, and this plan carries those
ratings on the task that implements them. It deliberately does **not** insert a
`checkpoint:decision` to re-ask them: the maintainer already chose these exact options during
`/gsd-discuss-phase`, and re-asking a decision already made is checkpoint fatigue, not a gate. The
irreversible acts are themselves gated — as blocking-human checkpoints performed by the human.

Governing constraints: the phase prohibitions P1-P5 in `37-01-PLAN.md` apply. Both checkpoints use
`gate="blocking-human"` rather than the plain blocking gate, because this project's
`.planning/config.json` carries an active auto-chain flag under which an ordinary blocking gate can
be auto-approved — which would defeat D-00a and D-02 entirely.
</objective>

  <instructions>
Three steps, strictly in this order.

**Step 1 — Merge the PR with the merge-commit method.** Not squash, not rebase. This repository
has all three methods enabled and the ruleset does not constrain the choice, so the method is
yours to get right: the tag is cut on the merge commit, and 204 plans' SUMMARYs and audits cite
SHAs that must stay reachable from `main` (D-04). All required status contexts must be green on
the post-tick head first; there is no bypass actor on the `main` ruleset, so a green PR is the
only path.

```
gh pr merge <PR-number> --merge
```

Then capture the merge commit SHA:

```
gh pr view <PR-number> --json mergeCommit --jq '.mergeCommit.oid'
```

**Step 2 — Wait for `ci.yml` to conclude success on that merge commit.** Roughly 60-90 minutes.
Do not tag before it finishes. The release pipeline's pre-publish consistency gate queries for a
recorded `success`-concluded `ci.yml` run on the tagged SHA itself; tagging early makes that gate
report a CI mismatch, and the documented recovery is to re-run the same release run once CI
catches up — avoidable noise on release day.

```
gh run list --workflow ci.yml --branch main --json headSha,status,conclusion
```

**Step 3 — Create and push the annotated tag on the merge commit.**

```
git fetch origin
git tag -a v0.10.0 <merge-commit-sha> -m "v0.10.0 Durable Agent Execution Runtime"
git push origin v0.10.0
```

The tag must point at the merge commit itself, not at any other ancestor of `main` — the pipeline
verifies the tagged commit is contained in `main`, and this phase's own verification asserts the
stronger fact that the tagged commit *is* the merge commit.
