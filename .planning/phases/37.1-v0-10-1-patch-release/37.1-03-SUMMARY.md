# Phase 37.1 Plan 03: Wire the Publish-Order Gate into check-gates and Pre-Merge CI Summary

**Added a `check-publish-order` Makefile target to `check-gates` and a `Check publish order` CI step to the License & Dependency Policy job (not the push-to-main-only Publish Dry Run job) — `make check-gates` now fails on the real, still-unfixed `paladin-battalion` publish-order defect, reachable both locally and pre-merge, exactly as D-08 stage 1 requires.**

## Performance

- **Duration:** ~25 min
- **Tasks:** 3 completed

## Accomplishments

- `check-publish-order` is a `.PHONY` Makefile target in the exact one-line shape its seven
  `check-*` siblings already use (help comment + single `@./scripts/check-publish-order.sh`
  recipe line), appended to `check-gates`'s prerequisite list without reordering or touching any
  of the seven existing names. `release-check` and `publish-dry-run` are untouched.
- `make check-publish-order` and `make check-gates` both exit non-zero, naming the same two
  forward-pointing `paladin-battalion` dev-dependency edges plan 37.1-02's gate already proved
  red against a real worktree capture of `1d4a9724`. All seven pre-existing `check-gates`
  prerequisites individually still exit 0 — the new guard is the only failing one.
- A `Check publish order` step (`./scripts/check-publish-order.sh`) was added to the
  **License & Dependency Policy** job (`.github/workflows/ci.yml`, job key `cargo-deny`) —
  placed after the CodeQL dismissal-register step and before the shell-guard regression step,
  alongside the job's six other offline `check-*.sh` steps. That job carries no job-level `if:`
  condition and already runs on every `push` and every `pull_request`.
- The existing **Publish Dry Run** job was deliberately left untouched: it is gated
  `if: github.event_name == 'push' && github.ref == 'refs/heads/main'`, meaning it never ran on
  a pull request at all — a materially worse gap than "blind to publish order while running."
  `git diff .github/workflows/ci.yml` shows insertions only, with no line touching `on:`,
  `github.event_name` or `github.ref` anywhere in the file; `./scripts/check-workflow-triggers.sh`
  still exits 0 — the recorded trigger-policy table needed no edit.
- A dated Findings entry was added to `37.1-CI-EVIDENCE.md` quoting the Publish Dry Run job's
  real condition and recording, at the point the gate was actually wired, why it was placed in
  the other job and why widening the Publish Dry Run job's trigger was not done.
- Both `scripts/check-publish-order.sh` and `tests/scripts/check-publish-order_test.sh` were
  confirmed git-tracked before trusting `make lint-shell` (which only scans tracked files) —
  `make lint-shell` reports `shellcheck clean`, and `make test-shell-guards` passes with the new
  9-assertion suite discovered automatically through the existing `tests/scripts/*_test.sh` glob
  (no new wiring needed), interleaved with the other five guard suites for 80 total assertions.
- Four new Local sweep rows (7-10) were added to `37.1-CI-EVIDENCE.md`, closing with an explicit
  statement that the `make check-gates` red recorded here is expected at this point in the

- `cargo check --workspace --all-targets --all-features` still passes — no Rust source touched.
- Neither `scripts/check-publish-order.sh`/its test nor `crates/paladin-battalion/Cargo.toml`

## Decisions Made

- **CI job choice: License & Dependency Policy, not Publish Dry Run.** The Publish Dry Run job's
  actual gate (`if: github.event_name == 'push' && github.ref == 'refs/heads/main'`) means it
  never runs pre-merge at all. The License & Dependency Policy job has no job-level condition and
  already runs the sibling `check-*.sh` guards and `make test-shell-guards` on every push and
  pull request, so the new gate reaches pre-merge CI through an existing, already-broad trigger
  surface rather than a new or widened one.
- **The composite gate is left red on purpose.** `make check-gates` and `make check-publish-order`
  both exit non-zero at the end of this plan, naming the unfixed `paladin-battalion` edges — per
  D-08 stage 1, fixing `crates/paladin-battalion/Cargo.toml` is plan 37.1-04's work, and doing it
  here would erase the red-to-green proof the phase's own success criteria depend on.
