## Accomplishments

- Fixed the real `v0.10.0` release-day defect at its source: `paladin-battalion`'s `paladin-llm` (CRATES position 5) and `paladin-storage` (position 10) dev-dependencies no longer carry a `version =` key, so Cargo omits both entries from the published manifest entirely — no requirement, no registry lookup, no ordering constraint — while local `cargo test -p paladin-battalion` (800 tests) still resolves them by path unchanged.
- Proved the fix with the gate itself: `./scripts/check-publish-order.sh` (no fixture flag, live tree) went from the `VIOLATIONS_FOUND` exit 1 that plans 37.1-02/03 recorded (rows 6/9/10) to `✅ OK: 12 crate(s) checked in publish order` exit 0, and `make check-gates` followed it green — the same command, the same tree, one manifest edit apart.
- Went beyond gate-level proof to manifest-level proof: extracted the `Cargo.toml` from the actual `.crate` archive `cargo package -p paladin-battalion --no-verify` produced (`Packaged 72 files, 2.4MiB (490.2KiB compressed)`) and confirmed by direct inspection that `paladin-llm`/`paladin-storage` do not appear anywhere in the packaged `[dev-dependencies]` tables — only `criterion` and `tokio` remain, matching documented Cargo behavior.
- Confirmed all four adjacent gates are unmoved: `cargo deny check` (advisories/bans/licenses/sources all ok), `cargo semver-checks check-release --baseline-version 0.9.0` (no semver update required), `make api-surface` (unchanged, baseline file confirmed not regenerated via `git status --porcelain`), and the fmt/clippy/lint-shell/doc-check/check-api-examples sweep.
- Recorded the workspace-wide observation as a finding, not a fix: 3 other versioned workspace dev-dependency edges (`paladin-herald`→`paladin-ports`, root→`paladin-web`, root→`paladin-eval`) still exist and are all correctly ordered today; none touched, per CONTEXT.md's own deferred item for a v0.11.0 workspace-wide path-only rule.

## Decisions Made

- **Manifest fix over reordering:** dropped the `version =` key from the two offending dev-dependencies rather than moving `paladin-battalion` later in `scripts/publish-crates.sh`'s `CRATES` array. This was the plan's own prohibition (do not reorder `CRATES`) and RESEARCH.md's independently-reached recommendation — smaller diff, zero risk to the array the real `v0.10.0` release already published 3 crates through successfully.
- **Two cargo-deny yanked-crate warnings recorded, not chased:** `spin 0.9.8` (carried forward from RESEARCH.md, already known) and `chacha20 0.10.0` (newly observed at this plan's Task 2 — not previously named in RESEARCH.md or this file). Both confirmed pre-existing and unrelated to this plan's edit because `Cargo.lock` is untouched (`git status --short Cargo.lock` / `git diff --stat Cargo.lock` both empty) — this plan only removes a version-requirement string from two already-path-resolved workspace members, so the resolved dependency graph cannot have changed.
- **The 3 remaining versioned workspace dev-dependency edges stay versioned:** `paladin-herald`→`paladin-ports`, root package→`paladin-web`, root package→`paladin-eval` are all correctly ordered today (confirmed live via `cargo metadata` cross-referenced against `CRATES` positions). Making path-only a workspace-wide rule is CONTEXT.md's own named deferred item for v0.11.0 release-tooling hardening — widening this diff on a release branch for edges that are not broken buys no defect coverage, and `check-publish-order` already protects all of them going forward.
