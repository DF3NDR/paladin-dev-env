<objective>
Re-seal the release gate set on the head that is about to become a release candidate, and write
the sign-off the maintainer will read.

Purpose: the previous tag was cut against a gate table that was green and, in one row, structurally
blind. This re-seal re-runs the same set at the patch version and adds the row that would have
caught what the blind one missed. It also changes the order of events: the sign-off box is minted
here, before the pull request is opened, so the tick can be a real merge gate rather than a
formality recorded after the fact.
Output: eight recorded gate results plus the house sweep, a new re-seal section in the corpus
acceptance audit ending in a fresh unticked box, and one dated paragraph in the pointer file.

**This plan carries a conditional blocking halt, which is why it is not autonomous.** D-08's second
stage starts here. If any gate is red — locally now, or in pull-request CI later — the agent
records the command, the head SHA and the failing output, stops at a blocking checkpoint, and
fixes nothing. On green the plan runs through without interruption.

Governing constraints: D-09 (the section's shape and its own box), D-10 (the sign-off is a hard
merge gate, in a fixed order), D-00a (only the maintainer ticks), D-00e (the coverage floor is
measured by the pull-request run only), D-08 stage 2 (record and halt, never fix).
</objective>
