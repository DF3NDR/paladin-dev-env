# Phase 37.1 Plan 12: Prove the Tag Equals the Merge Commit, Cut `chore/37.1-close`, and Record the Release Run's Per-Crate Publish Outcomes

**Proved the `v0.10.1` tag sits exactly on the pull request's merge commit (equality, not just containment), cut `chore/37.1-close` from the tagged `origin/main` with a clean empty stray-commit range, and recorded the release run's three attempts with the publish job's own per-crate table showing all 12 crates live at `0.10.1` and the three orphaned `0.10.0` versions yanked.**

## Performance

- **Duration:** ~55min
- **Tasks:** 3 (`type="auto"`)
- **Files modified:** 4 (`37.1-CI-EVIDENCE.md`, `.continue-here.md`, `STATE.md`, `ROADMAP.md`) plus this new summary

## Accomplishments

- **Task 1 — tag-equality proof.** `git rev-parse v0.10.1^{commit}` → `f7dae2676580786e9541fefee8f787623b46c70f`. `gh pr view 56 --json mergeCommit --jq .mergeCommit.oid` independently reports the identical SHA — **equality**, not merely `git merge-base --is-ancestor` containment (which also passed, as the weaker of the two proofs). The merge commit has exactly two parents (`1d4a9724` — previous `main` tip; `f3fc061d` — the tick commit); recorded honestly that git's own parent *order* places the tick commit second, not first, because `gh pr merge --merge` always orders base-then-head — the fact (two parents, both identified correctly) holds regardless of which one git calls "first". The tag is annotated (`git cat-file -t v0.10.1` → `tag`), tagger `Am0rfu5`, dated `2026-09-21T21:50:30Z`. The tag-after-green precondition was compared by timestamp, not assumed: the merge commit's `ci.yml` run concluded `success` at `21:40:06Z`, ten minutes before the tag was pushed.
- **Task 2 — cut `chore/37.1-close` from the tagged `origin/main`.** Done as the very first action of this session, before any commit, per the order_of_work's explicit sequencing — this let the three files plans 37.1-10/37.1-11 had deliberately left uncommitted on `release/v0.10.1` carry over cleanly (`tree(f3fc061d) == tree(f7dae267)`, confirmed identical before the switch). Confirmed `git branch --show-current` = `chore/37.1-close` and `git merge-base --is-ancestor v0.10.1^{commit} HEAD` succeeds. **Stray-commit range checked and found empty**: `git rev-list f3fc061d..release/v0.10.1` → 0 commits — nothing needed reconciling or carrying forward.
- **Task 3 — release-run evidence, publish health from the job's own table.** Recorded all three attempts of run `35659477719` (attempt 1: `failure`, `403 Forbidden` on `paladin-eval`; attempt 2: `failure`, same 403, predates the fix; attempt 3: `success`). Recorded the publish job's own conclusion (`success`, job `106552936579`) **separately** from the workflow's overall conclusion, with the explicit reasoning why the overall conclusion alone is not admissible. Transcribed the publish job's per-crate outcome table exactly as emitted (10 `already-at-this-version`, `paladin-eval` and `paladin-ai` `published-now`), confirmed it matches `scripts/publish-crates.sh`'s own `CRATES` array order exactly. Cross-checked all 12 names against `cargo metadata`'s live publishable list. Probed all 12 crates read-only against `index.crates.io`: **12/12 live at `0.10.1`, `yanked: false`**. Probed the three orphaned `0.10.0` versions the same way: **all three `yanked: true`**, confirming the maintainer's own verbatim report against the registry directly. Recorded `Verify Tag From Main` (job key `verify-tag-source`, the source-verification job) and `Pre-Publish Consistency Gate` (the release-consistency job) both `success`, and that `Create Release` succeeded — the exact step whose response-size race broke `v0.10.0`'s own release run, now proven fixed in production.
- **No re-dispatch, re-run, publish or yank by any agent.** Every read in both tasks was a single live query against the remote or the registry — no wait, no poll, no retry loop.
