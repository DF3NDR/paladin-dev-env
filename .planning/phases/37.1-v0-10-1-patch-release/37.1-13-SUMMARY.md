# Phase 37.1 Plan 13: Registry Verification -- One Index Row Per Derived Publishable Crate, Count-Asserted, Plus the Trusted-Publishing Proof

**Proved on the registry itself, not the workflow's log, that all 12 `cargo metadata`-derived publishable crates sit at `0.10.1` with a checksum and a not-yanked reading, and that `paladin-eval`'s new version carries a non-null `trustpub_data` record -- the observable proof of the Trusted Publisher link.**

## Performance

- **Duration:** ~20min
- **Tasks:** 2 (`type="auto"`)
- **Files modified:** 1 (`37.1-CI-EVIDENCE.md`) plus this new summary

## Accomplishments

- **Task 1 -- count-asserted registry table.** Derived the publishable-crate list live
  (`cargo metadata --format-version 1 --no-deps | jq -r '[.packages[] | select(.publish ==
  null)] | length'` -> `12`; the same filter's name list -> the 12 `paladin-*` names).
  Probed `index.crates.io` once per crate (`curl -sf -H 'User-Agent: paladin-release-verify
  (github.com/DF3NDR/paladin-dev-env)' https://index.crates.io/pa/la/<crate>`), filtered each
  response to its `0.10.1` line, and recorded `vers`, `cksum` and `yanked` per crate in a
  12-row table. Row count (12) equals the derived count (12), the derived count is greater
  than zero, every row reads `0.10.1` present and `yanked: false`. Every crate resolved on
  its first read (elapsed ~40m31s since the publish job's own conclusion at
  `2026-09-21T23:14:08Z`), so no fallback second read was exercised for any crate. Recorded
  explicitly that the release workflow's own log was not used as proof for any row.
- **Task 1 -- the orphan re-read and its deviation.** Re-read the three previous-version
  crates (`paladin-ai-core`, `paladin-ports`, `paladin-herald`) at `0.10.0` and found all
  three `yanked: true` -- not the "still not yanked" reading the plan's literal step 5
  expected. Recorded this as a Rule 1 / D-00d deviation: the D-01 ordering precondition
  (yank only after every publishable crate reads not-yanked) was already satisfied and
  already acted on earlier in this same session, by plan 37.1-12 Task 3's own not-yanked
  reading followed by the maintainer's out-of-band yank. This plan states the true current
  reading rather than fabricating a stale one, and points at the earlier reading as the
  satisfied precondition.
- **Task 2 -- trusted-publishing proof.** Read `https://crates.io/api/v1/crates/paladin-eval`:
  its `0.10.1` version entry carries `trustpub_data: {"provider":"github","repository":
  "DF3NDR/paladin-dev-env","run_id":"35659477719","sha":"f7dae267..."}` -- non-null, naming
  exactly this release run and the tag's own peeled commit. Its earlier `0.0.1` bootstrap
  version (token-published) reads `trustpub_data: null` -- the before/after contrast. Sampled
  `paladin-ai` and `paladin-battalion` at `0.10.1`: both read the identical non-null shape.
  Recorded explicitly that every read was an unauthenticated `GET` and that no registry
  credential exists in this environment.
- **Task 2 -- consolidated carried-findings list.** Gathered this phase's eight dated
  findings (three unfixed `pipefail`-shaped pipelines, the version-less semver allowlist, the
  retained `MIGRATION.md` title, the `doc-examples` manifest bump, the stale "eleven crates"
  count, the pre-existing `CHANGELOG.md` date, the pull-request-blind `publish-dry-run` job,
  and the Trusted Publisher environment-name mismatch discovered during the real release run)
  into one numbered, dated list in `37.1-CI-EVIDENCE.md`, each item naming its owner.
- **No yank, publish, re-dispatch or authenticated request performed by this plan.** Every
  read in both tasks is a single unauthenticated `GET` against `index.crates.io` or
  `crates.io`'s public API.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Stale precondition in the plan's own literal wording] The three previous-version orphans could not be recorded as "still resolvable and not yanked" -- they are already yanked**
- **Found during:** Task 1, step 5
- **Issue:** The plan's action text instructs recording the three orphaned `0.10.0` crates as
  "still resolvable and not yanked," establishing the precondition plan 37.1-14's yank
  checkpoint depends on. By the time this plan executed, that precondition had already been
  established (plan 37.1-12 Task 3's own registry probe, recorded earlier in the same evidence
  file, read all three as not-yanked) AND the maintainer had already yanked all three
  out-of-band immediately afterward, reported verbatim as "all three yanked." A live re-read
  now correctly shows `yanked: true` for all three -- recording "not yanked" would have been a
  false claim about the registry's current state.
- **Fix:** Recorded the true current reading (`yanked: true`, with checksums) for all three,
  and added an explanatory paragraph stating that the D-01 ordering precondition was satisfied
  by the earlier 37.1-12 Task 3 reading, that the yank happened immediately after it, and that
  plan 37.1-14's yank checkpoint is therefore gated true in principle but moot in practice
  since the act it would gate already occurred.
- **Files modified:** `.planning/phases/37.1-v0-10-1-patch-release/37.1-CI-EVIDENCE.md`
- **Verification:** The plan's own Task 1 `<verify>` automated check does not assert a specific
  `yanked` value for the orphans (it only checks the main 12-crate table's row count and
  presence of `0.10.1`), so this deviation does not break the task's own automated gate;
  re-ran the full Task 1 `<verify>` one-liner after the edit -- passes.
- **Committed in:** `b3ca4160` (Task 1 commit)
