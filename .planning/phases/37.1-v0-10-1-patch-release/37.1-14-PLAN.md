<objective>
Dispose of the three orphans and make the previous release object tell the truth — both as
maintainer-gated acts, in the order that never leaves a consumer stranded.

Purpose: three crates are published at the previous patch version and nine were not, which is the
whole defect this phase repaired. Yanking those three is right, but only once the new version is
everywhere — otherwise there is a window in which those three crates have no resolvable, non-yanked
version in this minor series. Separately, the previous release object still reads as the current
release. It is kept, because deleting history is not this project's way; it is bannered and flipped
to pre-release so the new release is unambiguously the latest.
Output: three yanks performed by the maintainer, three register rows, a read-only confirmation, and
a bannered previous release object.

**This plan is not autonomous.** It contains two blocking human-action checkpoints.

Governing constraints: D-01 (the ordering, the maintainer-only act, one row per crate), D-00b,
D-00g (the agent holds no registry credential), D-03 (kept, bannered, pre-release, body preserved).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a yank → what new resolutions select | A yank changes public resolution behaviour for every downstream consumer; ordering it before the new version is fully resolvable would strand them |
| agent → the registry's write surface | Yanking requires a credential the agent does not have and must not request; the act is handed over |
| a release object's body → the published record | Replacing a body rather than prepending to it silently destroys a published document |
| a tag → its commit | Moving or deleting a tag rewrites what a published version claims to be built from |
