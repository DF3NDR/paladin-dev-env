### 2026-09-19 — `publish-dry-run` is pull-request-blind, not merely "green and blind" (corrects CONTEXT.md D-05)

CONTEXT.md's D-05 (the MILESTONES.md v0.10.0 entry shape) says the entry should tell "the two
defects and why gate row 6 was **green and blind**" — inheriting Phase 37's framing that the
existing `make publish-dry-run` / CI `publish-dry-run` job ran, passed, and was merely blind to
inter-crate publish *order* because `cargo publish --workspace --dry-run` resolves sibling crates
from a local overlay rather than the live registry.

RESEARCH.md's re-inspection of `.github/workflows/ci.yml` found this understates the gap. The
existing `publish-dry-run` CI job is gated
`if: github.event_name == 'push' && github.ref == 'refs/heads/main'` — it has **never run on a
pull request**, only after a merge to `main`. Pre-merge, on any PR (including the one that carried
the `v0.10.0` defect), it did not gate at all — it wasn't blind to ordering while running, it
simply never ran. This is worse than "green and blind" and is recorded here in full so that plan
37.1-03's CI-wiring choice for the new SC3 publish-order gate has a written basis: the new gate
must be wired as its own fast job/step that runs on `pull_request` as well as `push`, never by
loosening the existing `publish-dry-run` job's trigger to cover pull requests (that job is
expensive — `cargo publish --workspace --dry-run` — and broadening it is explicitly ruled out as a
way to satisfy this gap). CONTEXT.md D-05's "green and blind" phrase is retained verbatim
(amend-at-source, D-00d) — this entry is the dated correction sitting alongside it, not a rewrite.

### 2026-09-19 — Publish-order gate wired into License & Dependency Policy, not Publish Dry Run (plan 37.1-03)

Plan 37.1-03 wired `scripts/check-publish-order.sh` (plan 37.1-02) into pre-merge CI. The **Publish
Dry Run** job's actual condition, quoted verbatim from `.github/workflows/ci.yml:2004`:

```yaml
if: github.event_name == 'push' && github.ref == 'refs/heads/main'
```

This confirms, at the wiring site itself, the finding recorded above
("`publish-dry-run` is pull-request-blind"): that job **never runs on a pull request**, only after
a merge to `main` — so a step added there would never have gated the PR that actually carried the
`v0.10.0` defect. Consequence stated plainly: pre-merge, that job does not gate at all; it is not
merely blind to publish order while running.

For this reason the new `Check publish order` step was added instead to the **License & Dependency
Policy** job (`.github/workflows/ci.yml`, job key `cargo-deny`, name `License & Dependency Policy`)
— a job with no job-level `if:` condition, running under the workflow's own broader triggers
(`push: branches: ['**']` and `pull_request: branches: [main, 'release/**']`), and already home to
six other offline `check-*.sh` guard-script steps plus `make test-shell-guards`. The gate is pure
`cargo metadata` + shell analysis (seconds, no build, no network), so it costs nothing extra riding
alongside those existing steps.

**Widening the Publish Dry Run job's trigger to cover pull requests was deliberately not done
here** — that job is expensive (`cargo publish --workspace --dry-run`) and its default-branch-only
scope is intentional; broadening it is explicitly out of this phase's scope (this plan's own
`must_haves.prohibitions`). The diff that added the new step touches no `on:` block and no line
containing `github.event_name` or `github.ref` anywhere in the file (verified:
`git diff .github/workflows/ci.yml` shows insertions only), and
`./scripts/check-workflow-triggers.sh` still exits 0 — the recorded trigger-policy table needed no
edit.
