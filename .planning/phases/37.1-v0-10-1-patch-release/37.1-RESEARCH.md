## Summary

This phase fixes exactly two shell/manifest defects that broke the real `v0.10.0` release
(`paladin-battalion`'s forward-pointing dev-dependencies, and an `EPIPE` race in
`create-or-reuse-release.sh:79`), adds one new CI/local gate that would have caught the first
defect before it reached the tag, bumps twelve manifests to `0.10.1`, and re-runs the release
pipeline through Trusted Publishing. Every "Claude's Discretion" default in CONTEXT.md was tested
empirically against this repo's pinned toolchain (rustc/cargo 1.97.1, MSRV 1.88) and is **CONFIRMED
by evidence**, with one important correction: **CONTEXT.md's own D-06 commit count is already
stale.** The range `1bb94063..HEAD` currently contains **16** commits, not 14 — two more landed
during the discuss-phase session that produced CONTEXT.md itself. The range boundary is still
correct; the count in prose is not, and will likely drift further before execution. The planner
must treat `1bb94063..HEAD` as a live git range re-resolved at execution time, never a fixed count.

The second most important finding is architectural, not textual: the existing CI `publish-dry-run`
job (`.github/workflows/ci.yml:2000`) that runs `cargo publish --workspace --dry-run` is gated
`if: github.event_name == 'push' && github.ref == 'refs/heads/main'` — it **never runs on a pull
request**, only after a merge to `main`. This means the "Local sweep row 29 was green and blind"
story from Phase 37 understates the gap: that dry run wasn't just structurally blind to publish
*order*, it never ran pre-merge in CI *at all*. The new SC3 gate (cheap, pure `cargo metadata`
analysis, no build) must be wired to run on `pull_request` as well as `push`, as its own fast
job/step — not by loosening the existing expensive `publish-dry-run` job's trigger.

**Primary recommendation:** implement the battalion fix as path-only dev-dependencies (confirmed
correct and sufficient by direct `cargo package` reproduction); implement the script fix as bash
parameter expansion (`${raw%%$'\n'*}`), which is structurally immune to the EPIPE class rather than
merely working around it; implement the new gate as a pure-`cargo-metadata`-driven shell script
(no network, no build) sourcing `CRATES` via the existing `PUBLISH_CRATES_LIB_ONLY=1` seam, wired
into `make check-gates` locally and as its own fast CI job/step that runs on `pull_request`.

## EPIPE Script Fix (SC2) — Discretion Question 5

**Confirmed the defect, reproduced it end-to-end through the real regression-test harness pattern,
and confirmed a fix. All three candidate forms work; parameter expansion is recommended.**

**The exact line (unchanged from CONTEXT.md's citation):**
```bash
# scripts/create-or-reuse-release.sh:79, inside _cor_gh_call()
status_line=$(printf '%s\n' "${raw}" | head -n1 | tr -d '\r')
```
`raw` here is **already a fully-captured bash variable** (from an earlier `raw=$(... "${GH}" api
... 2>&1)` command substitution on line ~76) — the vulnerability is re-piping an in-memory string
through `printf | head`, not a live network stream.

**Root cause, precisely characterized (not just "large response fails"):** the failure is a race
between `head -n1`'s internal read-buffer size and the pipe's kernel buffer capacity (1 MiB max
per `/proc/sys/fs/pipe-max-size` in this environment, but the *default* unrequested pipe capacity
is the traditional 64 KiB). `head -n1` only needs the first line to decide to exit, but its
underlying `read()` calls may pull far more than one line's worth of bytes per call; whether it
drains the writer's *entire* payload before making that decision (avoiding any race) or exits
after a partial drain (triggering the writer's next blocked `write()` to receive `EPIPE`, i.e. bash
exit 141) depends on total payload size relative to that buffer. **Empirically on this box:** a
multi-line HTTP-response-shaped payload of ~70 KB did NOT trigger the failure; the same shape at
100 KB and above triggered it deterministically (5/5 tests at 100 KB, 150 KB, 200 KB, 300 KB, 500
KB). The real incident's reported "~46 KB" trigger size and this box's ~70 KB non-trigger size are
both plausible — the exact threshold is sensitive to `head`'s implementation, coroutines version,
and scheduling, which is precisely why the regression test must use a payload comfortably larger
than any plausible buffer (recommend 200 KB+, not merely "a bit over 64 KiB") to be deterministic
across CI runners.

**Full end-to-end reproduction against the real, unmodified script** (not a synthetic bash
snippet): using the exact stub-based pattern `tests/scripts/create-or-reuse-release_test.sh`
already uses (a `gh` stand-in echoing `HTTP/2.0 200 OK\n\n<body>`), fed a `lookup_body` of ~200 KB:
```
GH_BIN="$SCRATCH/gh-stub.sh" bash scripts/create-or-reuse-release.sh --tag v1.2.3 --repo test/repo
# exit code: 141
```
This is the SIGPIPE (128+13) `set -e`/`pipefail` abort, reproduced against the literal repo file.

**Fix candidates evaluated (all three from CONTEXT.md's menu), each tested against the same 200 KB
stub, all succeed:**

| Form | Mechanism | Verdict |
|------|-----------|---------|
| `status_line="${raw%%$'\n'*}"` (+ `${status_line//$'\r'/}` for CR-stripping) | Pure bash parameter expansion — **no subprocess, no pipe at all** | **Recommended.** Structurally immune to the entire EPIPE class (there is no pipe to race), not merely tuned to survive it. Verified equivalent on empty `raw` (returns `""`) and single-line `raw` with no trailing newline (returns the whole string unchanged) — both match `head -n1`'s existing behavior. |
| `head -n1 <<< "${raw}"` (here-string) | Bash writes `raw` to a temp file first, then `head` reads from that file — no live pipe | Also correct; avoided the race in testing because a here-string is not implemented as a pipe. Slightly heavier (temp-file I/O) than parameter expansion for no behavioral benefit. |
| `printf '%s\n' "${raw}" \| sed -n '1p'` (reads to EOF, no `q`) | `sed` deliberately keeps consuming to EOF instead of exiting after line 1 | Also correct — eliminates the race by never closing the pipe early — but wastes CPU proportional to `raw`'s size for no benefit over the other two. |

**Recommendation: parameter expansion.** It is the only form that removes the *entire* subprocess-
and-pipe machinery this bug class depends on, is the cheapest, and needs no reliance on any
particular `head`/`sed`/coreutils version's internal buffering behavior — which is exactly what
made the original bug intermittent and hard to trust a "fix" against without this kind of
empirical, buffer-size-varying test.

**Applied and verified the fix removes the failure:** patched a scratch copy with the parameter-
expansion form, re-ran the identical 200 KB stub scenario — script now succeeds (exit 0,
`upload_url=...` printed).

**Example (of the existing pattern to mirror):**
```bash
# scripts/check-release-consistency.sh's existing seam (verified by reading the file):
#   --metadata-json <path>   -> skip the live `cargo metadata` call, read this file instead
#   --ci-runs-json <path>    -> skip the live `gh api` call, read this file instead
```

### Anti-Patterns to Avoid
- **A second hard-coded copy of `CRATES`'s order inside the new gate script:** defeats the whole
  point of the gate (a second manually-maintained list can silently drift from the real one).
  Always read `CRATES` via `PUBLISH_CRATES_LIB_ONLY=1 source scripts/publish-crates.sh`.
- **Reordering `CRATES` instead of fixing the manifest:** would work today, but is a strictly
  larger, riskier diff (touches the publish loop's proven-in-production ordering) for the same
  outcome the manifest fix achieves with two deleted words. Confirmed unnecessary by direct testing.
- **A live per-crate registry rehearsal as the gate's mechanism:** explicitly rejected by
  CONTEXT.md's own discretion default ("it cannot pass before siblings are published") — and
  correctly so; this would require network access and would only be exercisable at actual publish
  time, defeating the purpose of a pre-merge gate.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Detecting a versioned-vs-path-only Cargo dependency | Custom TOML parsing of `Cargo.toml` files | `cargo metadata --format-version 1`'s `path`/`req` fields, already the pattern `check-crate-names.sh`/`check-release-consistency.sh` use | `cargo metadata` is Cargo's own canonical, version-tolerant view of the dependency graph; hand-parsing TOML risks missing `{ workspace = true }` inheritance, renamed packages (`package = "paladin-ai-core"`), or future manifest syntax |
| Parsing an HTTP status line out of `gh api -i` output | A custom byte-scanning parser | The existing `sed -nE 's#^HTTP/[0-9.]+ ([0-9]{3}).*#\1#p'` one-liner already in the script (unaffected by the fix — only the *feed* into it changes) | Already correct and already tested; the bug is entirely upstream of this line |
| A safe way to extract "the first line of a large string" in bash | A new coreutils wrapper or a written-from-scratch state machine | Bash's own parameter expansion (`${var%%$'\n'*}`) | Zero subprocess, zero pipe, zero buffer-size sensitivity — the simplest correct tool already in the language being used |

**Key insight:** every fix in this phase is a *subtraction* (delete two `version =` fields; replace
one pipe with an in-process bash expansion; read an existing array through an existing seam) rather
than an addition of new tooling — consistent with CONTEXT.md's explicit scope boundary that "the
fixes are manifest, shell and gate changes" and nothing under `src/`.

## Common Pitfalls

### Pitfall 1: Assuming `--no-verify` on `cargo package`/`cargo publish` skips dependency resolution
**What goes wrong:** `--no-verify` only skips the build-verification step (compiling the packaged
crate in isolation); it does NOT skip resolving versioned dependencies against the registry. This
is exactly why `paladin-battalion` failed in the real `v0.10.0` run even though nothing about the
*build* was broken.
**Why it happens:** the flag's name suggests it disables all extra checks, but Cargo's own
dependency-resolution step for a versioned requirement happens earlier, during packaging.
**How to avoid:** treat "packages/resolves against the live index" and "builds in isolation" as two
separate, independently-failable steps; this phase's fix addresses the first.
**Warning signs:** `error: failed to select a version for the requirement` during packaging, not a
compile error.

### Pitfall 2: Treating a fixed-size "over 64 KiB" test payload as sufficient
**What goes wrong:** this research found the EPIPE race did NOT trigger at ~70 KB but did trigger
reliably at 100 KB+ on this exact box — "just over the nominal pipe-buffer size" is not a reliable
trigger threshold because the actual race depends on `head`'s internal read-buffer size too, which
is a coreutils implementation detail, not a POSIX guarantee.
**Why it happens:** the bug is a race between two independent buffer sizes (kernel pipe buffer,
`head`'s userspace read buffer), not a single documented constant.
**How to avoid:** use a payload comfortably larger than any plausible combination (200 KB+
recommended, verified to trigger reliably 5/5 at 100-500 KB in this environment) rather than a
payload just over the textbook 64 KiB pipe-buffer figure.
**Warning signs:** a regression test that "usually" catches the bug but occasionally passes even
against the unfixed script — a sign the chosen payload size is too close to the actual threshold.

### Pitfall 3: Assuming the existing `publish-dry-run` CI job already gates every PR
**What goes wrong:** `.github/workflows/ci.yml:2000`'s `publish-dry-run` job is scoped to
`push` events on `main` only — it has never run on a pull request, so "Local sweep row 29 was green"
(a *local* `make publish-dry-run` run) says nothing about CI coverage at all, and the new gate
cannot simply piggyback on that job's existing trigger.
**Why it happens:** the job's trigger was presumably scoped that way to avoid running an expensive
full-workspace publish dry-run on every branch push/PR — a reasonable cost tradeoff for that
specific expensive job, but one that silently left publish-order defects completely unchecked
pre-merge.
**How to avoid:** wire the new (cheap, metadata-only) gate into a job/step that actually runs on
`pull_request`, separately from the existing expensive dry-run job's trigger scope.
**Warning signs:** a gate that "passed in CI" turning out to have only run post-merge, when the
whole point was to catch the defect before merge.

### Pitfall 4: Rewriting `MIGRATION.md`'s title or the semver-allowlist's historical prose to say "0.10.1"
**What goes wrong:** `MIGRATION.md`'s "Upgrading from v0.9.0 to v0.10.0" title describes the
*milestone's feature scope*, which is unchanged by this patch; blindly renaming it to "v0.10.1"
would misrepresent a patch-only pipeline fix as a new feature milestone. Similarly, the semver
allowlist's justification prose describing "the v0.10.0 minor bump" is historically accurate
regardless of the patch version and has no literal version field to change at all.
**Why it happens:** SC4's phrasing ("MIGRATION.md/allowlist rows read 0.10.1") over-generalizes
from the manifest/changelog version bump, which genuinely does need to change everywhere, to files
that carry no such literal field.
**How to avoid:** apply amend-at-source (dated addendum, not rewrite) to `MIGRATION.md`'s title;
leave the semver-allowlist's prose untouched entirely — verified above that it contains no version
field of any kind.
**Warning signs:** a task that greps for "0.10.0" in `MIGRATION.md`/the allowlist and mechanically
replaces every hit — this would rewrite historically-accurate prose describing a past decision.
