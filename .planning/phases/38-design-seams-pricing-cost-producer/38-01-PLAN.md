  <name>Checkpoint: what one settlement row covers under the (run_id, superstep, attempt) key</name>
  <decision>Choose the settlement granularity ADR-0053 records: one settlement per superstep attempt aggregating every Paladin node in that superstep (D-15's key unchanged), or one settlement per node attempt with D-15's key extended by node_id.</decision>
  <context>D-15 locks the settlement idempotency key (run_id, superstep, attempt) but not what one settlement covers. `TraceEvent::NodeStarted`/`NodeFinished` (crates/paladin-core/src/platform/container/trace.rs) show that one WarEngine superstep can dispatch several Paladin nodes concurrently, each on attempt 1. Per-node settlement under the locked key would give two nodes the same key, and an idempotent store would silently drop the second node's charge (under-charging — LEDGR-03's exactly-once becomes at-most-once). The milestone research proposed (run_id, superstep_seq, node_attempt), which has the same collision. Phase 39's 007 migration persists whichever rule ADR-0053 records, so this is behind the one-way door D-14 already rates. ADR-0052 (Task 1) places the engine-path halt at the superstep boundary, which is where a superstep-aggregate settlement naturally happens. Undo cost after Phase 39: a ledger data migration plus a port contract change.</context>
  <options>
    <option id="superstep-aggregate">
      <name>Superstep-aggregate settlement, key unchanged (recommended)</name>
      <pros>Keeps D-15 exactly as locked; one settle per superstep attempt sums every node's Cost (parallel vanguard nodes, Aegis retries, fallback hops), so no key can collide; matches ADR-0052's superstep-boundary halt, so the draw, the settle and the halt check all happen at one point; fewer ledger rows.</pros>
      <cons>Per-node spend is not a ledger row — per-node cost stays visible in NodeFinished.cost trace events rather than in the ledger; a superstep that fails midway settles whatever its completed nodes reported.</cons>
    </option>

      <name>Per-node settlement, key extended to (run_id, superstep, node_id, attempt)</name>
      <pros>Ledger rows map one-to-one to node attempts, so per-node spend is queryable from the ledger alone (useful for LEDGR-04 per-model views).</pros>

- **Status:** `Accepted`, `**Date:** 2026-09-25`.
- **Context:** Phase 39 (LEDGR-01..04) writes the `007` migration in both `crates/paladin-storage/migrations/{sqlite,postgres}/` and a `TreasuryLedgerPort` mirroring `RunRepositoryPort`; Phases 41/42 draw against it; the Phase 27 worker is concurrent and redelivers leases, so draws must be race-proof and settlement idempotent; SQLite has no native decimal type, which is one reason the amount is an integer.
- **Decision**, as bold-led paragraphs:
  1. **Balance model (D-14):** an append-only ledger — every reserve, settle and release is an immutable row, never updated or deleted by normal operation. A scope's window balance (committed spend for a tenant or API key in a window) is a `SUM` over that scope's rows attributed to the window, computed inside the same transaction that inserts a new reservation.
  2. **Row kinds and signed contributions (D-15):** `reserve` contributes `+hold`; `settle` references its reservation (when one exists) and contributes `actual − hold` (a settle with no reservation contributes `actual`); `release` contributes `−hold` for a reservation that ended without a charge. Committed spend is therefore exactly the plain `SUM` of contributions. `settle` and `release` rows are attributed to their reservation's window, so a hold placed in one window and settled in the next never splits the window SUM across a boundary. Window timestamps come from the store or server clock, never a worker's local clock (ALLOW-01).
  3. **Amount unit (D-02, D-15):** every amount is an `i64` count of nano-units (1e-9) of the currency, carried with its ISO 4217 code on every row — the same unit as `Cost` (Phase 38 plan 38-02). A SUM over rows with differing currency codes is a refusal, never a conversion (FX is FUT-12). State that the nano-unit is a finer scale than PRICE-02's micro-unit wording and why (at $0.15 per 1M tokens one token is 0.15 micro-units and would round to zero per call; it is 150 nano-units).
  4. **Settlement idempotency key (D-15), per the option selected at the checkpoint above:** with `superstep-aggregate`, the key is `(run_id, superstep, attempt)` and on the engine path the ledger settles once per superstep attempt, aggregating the `Cost` of every Paladin node the superstep dispatched (parallel vanguard nodes, Aegis node retries and fallback hops all roll into that single settlement), so two nodes in one superstep never share a key; with `per-node-extended-key`, the ADR states that D-15's `(run_id, superstep, attempt)` is amended to `(run_id, superstep, node_id, attempt)` by operator decision dated 2026-09-25 at this checkpoint, and that the engine path settles once per node attempt. Either way `attempt` distinguishes a genuine re-execution of the superstep after resume or lease redelivery (real re-spend, charged again) from a duplicate delivery of the same settlement (charged once). On the agent loop `run_id` is the Platform API run id when present, else the `PaladinExecutionService` execution id; `superstep` is the model-call ordinal within the loop; `attempt` is `1` (the service's own buffered retries of one call roll into that call's settlement). Name explicitly that the persistence source of the engine-path attempt counter is an open item Phase 39/42 must resolve, and that the milestone research's `(run_id, superstep_seq, node_attempt)` reading was not adopted because two parallel nodes on attempt 1 would collide.
  5. **Serialization of SUM-then-reserve (LEDGR-02):** the reservation is admitted only if `SUM + hold` fits, and the SUM and the insert are serialized per scope inside one transaction: PostgreSQL rejects `FOR UPDATE` on an aggregate query, so the lock is taken on a per-scope row (or a transaction-scoped advisory lock keyed on the scope) BEFORE the SUM; SQLite takes the write lock up front with `BEGIN IMMEDIATE` (a deferred transaction would let two readers SUM before either writes); the in-memory adapter holds one mutex across SUM and insert. Growth is mitigated by an index covering (tenant, key, recorded timestamp).
  6. **Left to Phase 39 (D-15):** column names, index definitions and all DDL.
- **Considered Options** — bulleted: (a) append-only, derive-on-read (chosen); (b) **running balance in an `allowance_windows` table** — rejected: a second table whose counter can drift from the history that should justify it, a rollover job or lazy-reset logic at every window boundary, and two writes per draw that must stay transactionally consistent; (c) **full DDL in this ADR** — rejected by D-15 (Phase 39 owns the schema, written against its own contract tests).
