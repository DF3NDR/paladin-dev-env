  <context>
Why this gate exists: 39-CONTEXT.md was gathered in `--auto` mode — every gray area took the recommended option and no operator answered. D-01 (scope columns) and D-06 (partial unique settlement index) are rated **one-way**: once `007` is applied to an operator database, reshaping them needs a data migration. D-02 (`model_breakdown` column) is rated **costly**. Phases 41/42 build reservation and halt on this schema.

Proposed design (identical in both dialects apart from types; Postgres lands in 39-03):
- `entry_id` TEXT primary key (UUIDv7); `kind` TEXT with CHECK in ('reserve','settle','release'); `schema_version` TEXT stamped with the ledger's first schema-version string (the `RUN_SCHEMA_VERSION` convention).
- `tenant_id` TEXT NOT NULL, `api_key_id` TEXT NOT NULL on every row (D-01). Until Phase 40, production writers stamp the literal `unattributed` in both (`LedgerScope::unattributed()`); Phase 40 changes only the source of the values.
- `reservation_id` TEXT NULL (a reserve row's own id; a settle/release row's referenced reservation; NULL for an unreserved settle).
- `run_id` TEXT, `superstep` BIGINT, `attempt` BIGINT — required on settle rows (CHECK), optional on reserve rows so Phase 42 can record which superstep a hold was placed for.
- `amount_nanos` BIGINT NOT NULL — the row's **signed contribution** (reserve `+hold`, settle `actual − hold` or `actual` when unreserved, release `−hold`); the window balance is a plain `SUM(amount_nanos)` (ADR-0053 §1–2).
- `charged_nanos` BIGINT NOT NULL DEFAULT 0 — the actual charge on a settle row (0 on reserve/release); the spend view sums this column. D-02 says the breakdown sums to `amount_nanos`; that holds for every unreserved settle (all Phase 39 production rows). For a reserved settle `amount_nanos` is `actual − hold`, so the breakdown is defined to sum to `charged_nanos` instead.
- `currency` TEXT NOT NULL (ISO 4217, `CurrencyCode`).
- `model_breakdown` TEXT (SQLite) / JSONB (Postgres) NOT NULL DEFAULT '{}' — bare model name → nano-units (D-02).
- `attributed_at` — the instant that places a row in a window: the store clock when a reservation or an unreserved settle is written; a settle/release that references a reservation **inherits the reservation's instant** (ADR-0053 §2 "attributed to their reservation's window"). A window's balance is the SUM over rows with `window_start <= attributed_at < window_end`. **Planner deviation from D-12's literal wording:** D-12 names the covering index on `(tenant_id, api_key_id, window_start)`. Storing a per-row `window_start`/`window_end` cannot express membership in Phase 41's rolling windows (a row written at time t belongs to every rolling window that contains t), so the index is `(tenant_id, api_key_id, attributed_at)` — same purpose (serving the balance SUM and window queries), keyed on the attribution instant.
- `recorded_at` — when the row was written (audit), store clock.
- Indexes: `idx_treasury_ledger_settlement` UNIQUE on `(run_id, superstep, attempt) WHERE kind = 'settle'` (D-06); `idx_treasury_ledger_scope_window` on `(tenant_id, api_key_id, attributed_at)` (D-12); `idx_treasury_ledger_reservation` on `(reservation_id) WHERE reservation_id IS NOT NULL` (settle/release look up their reservation); `idx_treasury_ledger_settled_window` on `(attributed_at) WHERE kind = 'settle'` (the CLI's all-tenants window scan).
  </context>
