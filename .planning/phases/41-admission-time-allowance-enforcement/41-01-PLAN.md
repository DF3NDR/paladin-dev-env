<assumption_delta_decision>
The assumption-delta detector fired twice on the phase section: `optional` ("an optional lifetime
cap") and `chosen` ("a configurable warn threshold").

- **Primary noun:** the **ceiling** -- one (scope kind, limit kind, amount, optional period) tuple
  evaluated by one function over one balance read. A per-scope allowance entry yields up to two
  ceilings (window, lifetime); a principal yields up to four (D-03).
- **Decision (`optional`): `promote`.** The lifetime cap is not a second code path beside the window
  allowance: it is the same ceiling evaluated over an unbounded `BalanceQuery` (`since`/`until` both
  `None`, C10), `AllowanceLimitKind::Lifetime` being a detail of one variant. `AllowancePolicy::
  ceilings_for` is the single place both kinds are produced.
- **Decision (`chosen`): `no-change` to identity.** `warn_at` is a configuration parameter (global
  default, per-entry override), not part of the notice identity: the D-16 once-per-window key is
  `(scope_kind, tenant_id, api_key_id, limit_kind, window_start, ceiling_nanos)`, so changing
  `warn_at` mid-window does not re-arm a notice while raising the ceiling does (recorded, D-16).
- **Invariant test (accepted, 41-02 Task 2):** `every_ceiling_kind_round_trips_through_the_one_balance_function`
  -- for each of the four ceiling kinds the recorded `BalanceQuery` carries exactly the expected
  `(tenant_id, api_key_id?, since?, until?)`, so a future fifth limit kind that bypasses `balance`
  goes red.

Why this gate exists: 41-RESEARCH.md section "CONTEXT.md Corrections and Planner Decisions Required" verified fourteen places where the code contradicts or leaves open a CONTEXT decision. D-08 (run_schedules columns) and D-16 (treasury_notices table) are rated one-way; D-01, D-02, D-04, D-12, D-17 costly. The operator chose those decisions; this gate confirms HOW they are built, not whether. Every item below cites the correction that changes it.

Proposed design:
1. **C1 -- admission input port.** `paladin-web` cannot name the facade `Treasurer` (crate cycle). New input port `paladin_ports::input::allowance_admission_port::AllowanceAdmissionPort { admit(subject: &RunAttribution, run_id: Option<&RunId>) -> Result<Admission, AdmissionError>; confirm(&Admission); abandon(&Admission) }`; the facade `Treasurer` (D-06, `src/application/services/treasurer/`) implements it; `RunSubmissionService::with_treasurer` and `AgentApiState.treasurer` take `Arc<dyn AllowanceAdmissionPort>`. The Treasurer takes a `RunAttribution` (identity only, no role), so no role can bypass an allowance (D-09).
2. **D-04 + D-00b + C10 + C11 -- the balance read.** `TreasuryLedgerPort::balance(BalanceQuery { tenant_id, api_key_id: Option<String>, currency: CurrencyCode, since: Option<DateTime<Utc>>, until: Option<DateTime<Utc>> }) -> Result<Cost, TreasuryLedgerError>`; a lifetime ceiling is both bounds `None` (no far-future sentinel, C10). Planner's discretion call (CONTEXT "Claude's Discretion"): the method is **defaulted** (default body returns `TreasuryLedgerError::InvalidRequest`), not required, because a required method forces edits to the `#[cfg(test)]` ledger doubles inside `crates/paladin-battalion/src/engine/mod.rs`, which D-00b forbids this phase to touch. All three in-tree adapters override it behind the contract suite; an adapter that does not override it fails admission closed (500, D-10), never open. Register consequence (C11): a defaulted method breaks no implementor, so the MIGRATION.md 9.2 row is `N` (X-10.4, the `PaladinExecutorPort::execute_scoped` precedent) with no allowlist entry, instead of D-04's anticipated `Y` + allowlist.
3. **C8 + D-14 -- the refusal value.** `AllowanceRefusal { scope_kind, limit_kind, balance: Cost, ceiling: Cost, window: Option<(DateTime<Utc>, DateTime<Utc>)>, evaluated_at: DateTime<Utc> }` -- `evaluated_at` (the store instant the window was computed from) is added so `Retry-After = window_end - evaluated_at` never reads a web-process clock.
4. **C5 + D-16 -- migration 011 shape (one-way).** `treasury_notices.api_key_id TEXT NOT NULL` with the documented sentinel `''` for tenant-scope notices (a NULL in a UNIQUE key never conflicts on SQLite or PostgreSQL < 15, verified); lifetime notices use `window_start` = the Unix epoch; two columns beyond D-16's list, `window_end TEXT/TIMESTAMPTZ NULL` and `warn_at INTEGER NOT NULL`, so the worker can rebuild the `AllowanceWarning` on readback; `UNIQUE (scope_kind, tenant_id, api_key_id, limit_kind, window_start, ceiling_nanos)`; `INSERT ... ON CONFLICT DO NOTHING`; zero rows affected = `AlreadyRecorded`. Plus an additive `012_add_treasury_ledger_tenant_index.sql` (`(tenant_id, attributed_at)`, RESEARCH Pitfall 14) so tenant-wide window sums do not walk every key.
5. **C6 -- trace emission (D-18).** Admission claims the notice row (carrying the admitting `run_id`) BEFORE the run row is inserted; `confirm` runs after insert+enqueue, `abandon` deletes this admission's won rows if insert/enqueue fails.
