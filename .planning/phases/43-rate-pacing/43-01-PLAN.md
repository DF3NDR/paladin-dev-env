its own green gate; Task 2 lands the decorator, the config, the composition and the end-to-end test;
Task 3 registers the surface.

the gate is exponential back-off only. Plan 43-02 reshapes the variant and makes the decorator honour
the provider's delay as a minimum -- a functionality gap filled without an architectural change.

Purpose: if a 429 cannot slow the next call through config -> composition -> decorator -> port ->
adapter -> provider without an architectural change, every later plan is wasted. The tracer is
production code.

Ports -- `cadence_port.rs` (new), registered in `output/mod.rs` with a one-line doc comment.** Module docs: why a port (cross-call pacing state must be shared by every decorator in a process, and by every worker with a shared backend, so it cannot live in a decorator field); read-only `gate` vs state-changing `record_*` (a caller cancelled while waiting leaves no state behind, Pattern 2); reactive-only (D-04: a key is gated only after a 429, never from success headers); the in-flight rule (Pattern 3); every adapter returns RELATIVE waits so no caller ever compares clocks across hosts. Items:
- `pub const CADENCE_LOG_TARGET: &str = "paladin::cadence";` (D-07, shared by `paladin-storage` and `paladin-llm`).
- `pub const CADENCE_DELAY_CEILING: Duration` = 24 hours (hard clamp for any delay reaching a port, research Pitfall 3).
- `CadenceKey` -- `#[derive(Debug, Clone, PartialEq, Eq, Hash, PartialOrd, Ord)]`, private fields `provider: String`, `model: String`; `new(provider: &str, model: &str)`, `provider()`, `model()`.
