<objective>
Make fallback chains pace first and hop last (D-03): a 429 on a hop waits out that hop's gate and
retries the same provider until the cumulative paced wait would exceed
`treasurer.cadence.fallback_pace_budget_secs`; only then does the 429 reach the hop rule. Every hop
is wrapped in the Cadence decorator, and chains built from configuration are paced by default.

This plan carries ROADMAP success criterion 2 -- "A mocked 429 against any FallbackLlmAdapter hop
proves back-off with jitter -- the retry delay is honored as a minimum -- rather than
immediate-retry thrash" -- as executable tests.

**Open Question 4 resolution (per-hop wrapping site):** chains are wrapped at the chain builder,
not the factory. `FallbackLlmAdapter::with_cadence` wraps hand-built chains;
`ModelFallbackMiddleware::paced` wraps middleware-built chains; `AgentRuntimeDeps.cadence`
(defaulting to an in-process wiring) wraps config-built chains in `AgentRuntimeConfig::build_chain`.
`LlmProviderFactory` stays a unit struct (no `unit_struct_changed_kind` break). Finding recorded for
the operator: no server composition root builds a fallback chain today (`agent_runtime.model_fallback`
is consumed only by `AgentRuntimeConfig::build_chain`, a library API), so the server's own ports are
covered by 43-01/43-09's `compose_llm` and chains are covered here. A chain a library user builds
with `FallbackLlmAdapter::new` and never calls `with_cadence` on keeps today's hop-immediately
behaviour by design: without a gate there is nothing to pace against, and the decorator never owns
retries (D-01).

Output: `with_cadence` and the pace-first branch, `ModelFallbackMiddleware::paced`,
`AgentRuntimeDeps.cadence`, the rewritten fallback module docs, the registered surface.
</objective>
