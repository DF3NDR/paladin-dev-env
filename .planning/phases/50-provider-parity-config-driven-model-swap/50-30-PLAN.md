<objective>
Stop losing the bill of a fallback hop the chain moves past. With `hop_on_refusal` on, a billed refusal from one
provider sends the call to the next; the next hop's success (or the chain's final error) is all the caller sees, so the
refused hop's tokens and cost never reach the run's tallies, the ledger or the engine.

Purpose: G-50-5a remainder (a), brought into Phase 50 by the owner on 2026-10-17 ("that hop's billed usage/cost must be
carried forward and settled, not lost"). `LlmResponse` has no slot for a second model's spend and adding a field would
touch every struct literal in the workspace, so the hop bills travel in a per-call collector the execution service
installs, the same task-local pattern plan 50-29 uses for the attempt.
PARITY-06 (each fallback hop sends its own model) is extended: each hop's bill is priced against its own model.

Output: the `HoppedBills` collector, `FallbackLlmAdapter` recording, `PricingLlmAdapter` pricing, and the execution
service settling every call's parts in one row, buffered and streamed.
</objective>

<flagged_assumptions>
- A1-50-30: one settlement row per call (not one per hop) follows ADR-0053 section 4 and keeps the agent loop's key
  shape `(run_id, ordinal, 1)`; a second settle under the same key would be dropped as `AlreadySettled`, so per-hop
  rows are not an option. The breakdown names each model with its own nanos.
- A2-50-30: every priced part comes from the one `PriceTable` behind the decorator, so the parts share a currency. A
  `checked_add` mismatch is therefore impossible in practice; if it happens it is logged at `error!` and the call
  settles nothing, never a partial or fabricated amount.
- A3-50-30: the collector spans all of one call's retries, because each retry's hops are separate billed requests.
- A4-50-30: `hop_on_refusal` stays opt-in and off by default (D-10); this plan changes what is counted, not when the
  chain hops.
