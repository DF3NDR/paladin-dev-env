### Disposition of the review findings the orchestrator asked about

**WR-01 (new `new(api_key, model)` rustdoc says `model` is "the default model requested when a call names none"): documentation defect, not a goal gap. Fix before the tag.** I confirmed the claim is false in the code: `config.model` is read only by `validate()` (non-empty) and `default_timeout_seconds`; no request builder substitutes it when `request.model` is empty (grep for an empty-model fallback in compat engine, deepseek, anthropic, openai finds none; the `model.is_empty()` hits are `validate()` and billing). The same wording is on six constructors (kimi:189, deepseek:193, grok:180, gemini:333, anthropic:231, qwen:280). Why it is not a goal gap: the goal's "no silent behaviour change" clause is about behaviour that moved between v0.10.1 and v0.11.0, and this behaviour did not move (v0.10.1's `model` field doc was "Default model to use" and the field was equally unused as a fallback). The "one `new(..)` shape" clause is about signature uniformity, which is met. Why it still matters: it is new wording on the headline constructor that ships in the tag, a consumer who relies on it gets a vendor 400 on an empty model, and OpenAI's own doc is accurate, so the nine types now disagree in prose. The fix is a doc-only edit (or implementing the fallback with tests, which would be a behaviour change and should not ride a tag without being named in the guide).

**WR-02 (grok-4.7 exception overstates the sibling evidence): evidence-accuracy item, confirmed, does not touch the ruling.** The transcript (`50.1-SEED-PROBE.md`, probe 3 tables at lines 1642-1696 and 2608-2662) shows `temperature=2.00` as: grok-4.3 UNREACHABLE in both runs; grok-4.6 ACCEPTED (200) in run 1, UNREACHABLE in run 2; grok-4.5 REJECTED 500 in run 1, UNREACHABLE in run 2; grok-4.7 UNREACHABLE in both. So "the same row fails for grok-4.3, grok-4.5 and grok-4.6" (`seeded.rs:1877`, `switching-providers.md` footnote [i], 50.1-09-SUMMARY:89) is wrong for grok-4.6 (it once accepted 2.00). The ruling's premise for grok-4.7 itself (identical failure in two independent runs) is true as written. The 1.99 cap on the siblings is conservative (it can only refuse a value the vendor may take), so no wrong acceptance results. Reword the three passages to the transcript.

**WR-03 (`with_base_url` doc promises http/https-only validation; 7 of 9 validators test `starts_with("http")`): documentation/code mismatch, confirmed** (grep: only anthropic and gemini test `http://` or `https://`). Bounded impact (reqwest fails a malformed URL later; redirects are off). Not a success-criterion failure. Either share one `is_http_url` check or soften the builder doc.
