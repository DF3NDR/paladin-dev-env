<planner_decisions>
- **PD-01-1 (orchestrator note 6, research Pattern 1):** `permits_thread` answers only "may this scope see a thread whose latest run is `latest`". The no-run policy differs by caller and stays with the caller: the read gate (53-03/53-04) hides a zero-run thread from non-admin, while `ensure_thread_visible` keeps `None => Ok(())` so a first submit to a fresh `thread_id` still works (thread birth). Calling `permits_thread(None)` inside the service would 404 every first submit by a non-admin, so the service calls it only with `Some(&latest)`.
- **PD-01-2 (orchestrator note 6):** the ordering key is `submitted_at DESC, run_id DESC` (every adapter's `list`); `Run` has no `created_at`. Rustdoc and evidence written here say `submitted_at`.
- **PD-01-3 (D-00d, D-00a TDD):** a lock test passes on arrival because the behavior already exists. "Watched failing first" is shown by a local, uncommitted mutation: replace the guard arm with an unconditional `Ok(())`, run the new HTTP test, copy its failing assertion line into the evidence file, and restore the arm. The mutation never reaches a commit.
- **PD-01-4 (D-09 scope):** a corrupt latest-run row on the submit path keeps today's redacted `500 "run store error"` (it reaches `map_submission_error`'s `Backend` arm, no backend text). D-09 limits the role-dependent `404` mapping to `load_visible_run` and `load_visible_thread`; fork gets it through the controller gate in 53-03. This is recorded as a residual in the evidence file, not changed here.
- **PD-01-5 (fork bodies before 53-03):** on today's tree a foreign fork answers `unknown thread '<id>'` while a never-existing thread answers `unknown waypoint '<wp>' on thread '<id>'` (the service checks the waypoint after the guard). Byte equality of foreign-versus-missing fork bodies is therefore proven at the controller by 53-03's route matrix, not by this plan's test; this plan's fork test asserts the TENANT-04 outcome (status, code, message, nothing dispatched).
</planner_decisions>

<assumption_delta_decision>
- **Signal:** `pluralization` on "another tenant's threads" (assumption-delta scan, 2026-10-31).
- **Noun now primary:** the thread's *owning tenant*, derived from the `submitted_by` of its latest run; `ThreadId` stays the thread's sole identity and is not namespaced by tenant.
- **Decision:** `add-alongside` -- ownership is derived alongside the unchanged `ThreadId`/`Waypoint`/`ThreadSummary` identity model (D-01), because recording a tenant on the thread is a registered public-surface break and the milestone stays `v0.11.1` (D-02).
- **Accepted debt:** the D-04 list walk does one owner lookup per examined thread (bounded by 53-04's cap), and an unused thread id stays distinguishable from a hidden one on submit (40-CONTEXT D-14 known limitation).
- **What would force a later promote:** a dogfood deployment where the per-thread lookup cost matters, or a requirement that unused and hidden thread ids answer alike on submit; either moves to "record a tenant on the thread" in the next minor (CONTEXT Deferred Ideas).
- **Invariant test (optional, taken):** `permits_thread_admits_all_and_only_the_latest_runs_tenant` encodes "a thread belongs to its latest run's tenant".
