<planner_decisions>
- **PD-03-1 (D-05, PD-K):** `fork_thread` also enters `load_visible_thread` (so the controller answers missing and hidden alike before the service runs); `RunSubmissionService::ensure_thread_visible` still re-checks for library callers. Fork therefore needs `state.waypoints` wired; the shipped server always wires it beside `run_submission`.
- **PD-03-2 (handler order):** `get_thread`/`get_thread_state`/`get_thread_history`: waypoint 501 check -> parse id -> gate -> handler body (state and get reuse the Waypoint the gate returns; no second `latest()` call). `resume_thread`: parley 501 check -> parse id -> gate -> `require_admin` -> parse responses -> `resume_with`. `fork_thread`: run-submission 501 check -> parse id -> gate -> parse `from_waypoint_id` and webhook -> `fork`. `delete_thread`: waypoint 501 check -> parse id -> gate -> `require_admin` -> busy check -> `delete_thread`. A request body is parsed only after the gate, so a foreign caller learns nothing from a 400.
- **PD-03-3 (orchestrator note 4, research A4):** waypoint classifier `waypoint_error_for_scope` treats `WaypointError::Serialization` and `SchemaVersionUnsupported` as hideable (a corrupt Waypoint under an id is otherwise an existence signal before the owner is known); `Backend` and `NotFound` are not. Fixed message `THREAD_STORE_ERROR_MESSAGE = "thread store error"`. Run-repository failures reached from thread routes keep `"run store error"` (AC-09).
- **PD-03-4:** after the gate admits the caller, later store errors (history page, delete, `ParleyError` fallthrough) are not existence questions and use `thread_store_error(context, err)`: the fixed `500 "thread store error"` for every role, detail to `log::error!`.
- **PD-03-5 (AC-09 thread half, research Pattern 2):** an Admin's gate performs no run lookup, so a run-store failure cannot turn an Admin `GET` into a 500; the only Admin thread route that loads runs is `DELETE` (busy check), which answers the fixed `500 "run store error"`. The Serialization test asserts exactly that and says why in its rustdoc.
- **PD-03-6:** the list route keeps its current behavior in this plan except for its leak site (replaced by `thread_store_error`); the tenant-filtered walk is plan 53-04.
