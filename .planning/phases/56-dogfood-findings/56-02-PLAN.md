<planner_decisions>
- **PD-02-1 (Claude's discretion, D-10 walker):** a `serde_json::Value` walk. `type KeyPath = Vec<String>`. A map key is one segment; a sequence element is the segment `[i]`. Each container records its own path and then recurses. `render_path` joins segments with `.` for messages only, never for comparison.
- **PD-02-2 (input parser):** `serde_yaml::from_str::<serde_json::Value>` as a root dev-dependency (RESEARCH recommendation). It is independent of the `config` crate, so a key mangled at parse time cannot look identical on both sides.
- **PD-02-3 (where the test lives):** one integration file, `tests/config_example_roundtrip.rs`. It holds table-driven helpers and one `#[test]` per property. The existing per-section example tests in `src/config/*.rs` and `agent_host.rs` stay untouched.
- **PD-02-4 (`EXEMPT` row shape):** a segment pattern with `*` as a one-segment wildcard, plus a reason: `["llm", "*", "api_key"]` (reason: secret, `skip_serializing`, WR-04) and `["treasurer", "allowance", "webhook", "secret"]` (reason: secret, `skip_serializing`, redacted in `Debug`). `KNOWN_GAPS` and `KNOWN_PRICE_GAPS` rows carry a pattern plus a `DF-nn`. Both tables go through one `stale_rows` check.
- **PD-02-5 (drift-guard comparison, RESEARCH Pitfall 5):** live keys compare by full segment path. The full fixture keeps every live entry of the example at the same sequence index and appends extras after it. A commented key line is any line matching `^\s*#\s*(?:-\s+)?([A-Za-z_][A-Za-z0-9_./-]*)\s*:(\s|$)` above the `# Platform API` banner. It is compared as a (top-level section, leaf key) pair: the section is the last live top-level key above the line, and the fixture must hold some path under that section ending in that leaf. `PROSE_COMMENT_LINES` lists prose lines that match the pattern (at least `Live-verified`), one reason each, and goes stale like the other tables.
- **PD-02-6 (Settings::new path, D-08 vs D-12):** the P3 test copies the full fixture to a `tempfile::TempDir` as `config.yml`, switches the current directory under `#[serial]`, restores it on every path (a drop guard), and does not touch `APP_*`. An `APP_*` overlay can only add or override values, and the diff is one-directional, so the overlay cannot hide a dropped key.
</planner_decisions>
