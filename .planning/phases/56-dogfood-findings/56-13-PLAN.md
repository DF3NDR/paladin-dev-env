<objective>
Close DF-19 (S2): `paladin-cli setup-check` and `onboarding` reject a valid Anthropic key, because both validate it by posting a retired, hard-coded claude-3 model id. Anthropic answers 404, and the message names neither the model nor the reply. The fix gives both commands one shared probe that sources its model from the Anthropic adapter's seeded default and says, on failure, which model was probed and what the provider answered (redacted). It checks the OpenAI and DeepSeek probes for the same hard-coding, and the maintainer re-runs the failing command with a real key (DOGF-06, D-05, D-06).

Purpose: the command that is supposed to confirm a working setup reports a working key as broken and exits 1. An Anthropic-only user who runs `onboarding` is told their key is bad.
Output: one private probe module, both commands rewired, regression tests, a docs line, a CHANGELOG entry, the maintainer's re-check and DF-19's disposition.

<planner_decisions>
- **PD-13-1 (where the probe model comes from).** The finding names "the registry's seeded default for the provider".
  - That value is reached publicly as `ANTHROPIC_DEFAULT_MODEL`, and paladin-llm's `anthropic_default_model_is_seeded` pins it to a seeded row. Reading the seeded table directly would mean widening paladin-llm's `pub(crate)` registry API, which is a second crate's public surface (D-00b, D-06).
  - A build without `llm-anthropic` has no adapter constant. For that build, a private `ANTHROPIC_PROBE_MODEL_MIRROR` holds the same id. The test `anthropic_probe_model_is_the_adapters_seeded_default` pins it equal to the constant in every feature build, so the two cannot drift silently.
- **PD-13-2 (one module for all three probes).** The two copies had already drifted: setup-check drops the body and onboarding echoes it raw. That drift is how DF-19 landed in two files. All three validators move into `provider_probe.rs`, and both commands import them. This is the "one shared helper" the finding asks for, and it means the Anthropic probe can never again be fixed in one file and not the other.
- **PD-13-3 (failure text).** The failure text is `<Provider> API validation failed for model '<model>' (<status>): <excerpt>` for Anthropic, and `<Provider> API validation failed (<status>): <excerpt>` for the model-less probes. The `: <excerpt>` part is omitted when the excerpt is empty. The excerpt is always `diagnostic_excerpt(body, api_key)`, which redacts before it bounds, the house rule in `security.instructions.md`.
- **PD-13-4 (no redirects).** reqwest strips `Authorization` on a cross-host redirect but not the custom `x-api-key` header. The shared client therefore uses `redirect(Policy::none())`, and a 3xx is reported as a failure.
- **PD-13-5 (records).** This is a fix of a wrong result that needs no user action, so it gets a `CHANGELOG.md` `[Unreleased]` `### Fixed` bullet and no MIGRATION.md section 11.1 row. No doc or test pins the old message text (checked with `grep -rn "API validation failed" docs/src src`). One docs line in `cli-setup-check.md` says which model the Anthropic check probes and what a failure shows.
- **PD-13-6 (maintainer re-check, four tasks).** Only a real key proves that the model is served for the maintainer's account. The agent proves the request shape and the message; the checkpoint closes the loop with the same command that found DF-19. Task 3 costs the executor no context. Task 4 has to follow it, because the disposition cites the re-check, and it has to be last (D-06). That is why this plan has four tasks.
- **PD-13-7 (out of surface).** Other files still name the retired id: the vision-model list in `crates/paladin-llm/src/anthropic/vision.rs`, `tests/integration/anthropic_provider_test.rs` and `tests/integration/llm_live_api_tests.rs`. They are not on DF-19's path (the CLI key probe) and are left alone. DF-16 (setup-check output order) stays re-homed.
</planner_decisions>
