## 9.1 Behavioral changes (user-visible without code changes)

| ID | Change | Who is affected | Required user action |
|---|---|---|---|
| M-B-01 | **BUG-01 fix.** `EdgeCondition::Custom(name)` no longer evaluates to `true` when no evaluator is registered. Campaign/graph validation now fails with `BattalionError::InvalidGraph` naming each unregistered condition, before any node executes. | Any v0.9 workflow using `EdgeCondition::Custom`. Such workflows were routing *incorrectly* (always following the custom edge); after upgrade they fail loudly at validation. | Register an evaluator for each name via the new registry API (CF-FR-01), or replace the condition with `Contains`/`Regex`/`Always`. |
| M-B-02 | **Graceful shutdown.** On SIGTERM/SIGINT the process now waits up to `shutdown_grace` (default 30 s, env `APP_ENGINE_SHUTDOWN_GRACE_SECS`) for in-flight engine runs to halt before exiting — `paladin-server`'s `shutdown_signal` and `ServiceRunner::wait_for_shutdown` both cancel a shared `ShutdownCoordinator` and wait for registered runs to drain (HITL-04, D-21/D-22). | Operators; container orchestration. | Set `terminationGracePeriodSeconds` ≥ 2 × `shutdown_grace` — `k8s/server/deployment.yaml` and `k8s/deployment.yaml` ship `60` (landed, HITL-FR-15). Set `APP_ENGINE_GRACEFUL_SHUTDOWN=false` to restore the old no-wait behavior for legacy-only deployments (landed, HITL-04). |
| M-B-03 | **No behavioral change.** `tool_error_mode` (RT-FR-24) NAMES a policy the v0.9 loop already implemented, rather than introducing one: a failed Arsenal or handoff tool call was always appended to the accumulated output and the run continued (`paladin_execution_service.rs`'s Arsenal and handoff error-handling arms, unchanged since before this phase). This phase adds `FailRun` as a new opt-in (`PaladinError::ArmamentFailed { tool, reason }`) and sanitizes the fed-back text (redact-then-bound, D-34) before the model ever sees it — the sanitization is the ONLY observable difference for an existing user. | Users of the Arsenal/handoff tool loop. None from the policy itself; a leaked credential previously visible in a tool's raw error text is now redacted before the model sees it. | None required to keep today's behavior — `tool_error_mode` defaults to `FeedToModel`, byte-for-byte matching v0.9 apart from sanitization. Set `tool_error_mode = FailRun` (globally via `AgentRuntimeConfig.tool_errors.mode`, or per tool via `tool_errors.per_tool`) to opt into failing the run on a tool error instead. |
| M-B-04 | **Automatic per-superstep checkpointing.** Any graph executed through the new `WarEngine` (via `WarGraph`/`WarEngine::start`/`WarEngine::resume`) now writes one `Waypoint` — a **full `Battlefield` snapshot**, including whatever a workflow places in shared state (which may include raw LLM prompts and model outputs) — after every superstep, by default (`WaypointDurability::Strict`). The write goes to whichever `WaypointPort` backend the caller wires in: `InMemoryWaypointStore` (ungated, tests/dev) or, once landed, `SqliteWaypointStore`/`PostgresWaypointStore` (ENG-05) for durable deployments. Growth is bounded by `EngineLimits` (`max_supersteps` default 50, `max_node_visits` default 25) and, once configured, by `WaypointRetentionConfig` (`max_age_days`, `max_waypoints_per_thread` — see §9.5). | Any workflow author who adopts the new `WarEngine`/`WarGraph` APIs (ENG-01…ENG-08). | **Legacy `FormationExecutionService`, `PhalanxExecutionService`, `CampaignExecutionService`, and `Commander` execution paths are completely unaffected — they write no Waypoints and their behavior is byte-for-byte unchanged (ENG-FR-20).** A v0.9 workflow gains **no new persistence** unless it is explicitly rebuilt against the new engine. To adopt it: choose a `WaypointPort` backend, review `WaypointDurability` (default `Strict` fails the run on a write error; `BestEffort` downgrades to a logged warning), and configure `WaypointRetentionConfig` if snapshots — which may contain raw prompts/outputs — must not accumulate unbounded. |
| M-B-05 | **Rate pacing is on by default (PACE-02, Phase 43 plan 43-01).** Every agent the server builds from configuration or provisions at runtime now waits out a per-(provider, model) gate after a provider 429: later calls to that provider and model are held for an exponential back-off with full jitter, from 500 ms up to 30 s (a `Retry-After` header is honoured from plan 43-02), instead of being sent straight back into the rate limit. `treasurer.cadence.enabled: false` restores the previous behaviour exactly. The OpenAI adapter also now surfaces a 429 on its first attempt instead of retrying it inside its own loop (D-02), so the pacing layer sees every 429 and each one costs the provider exactly one hit; from plan 43-03 the Anthropic adapter does the same (its network and 5xx retries are unchanged), and from plan 43-04 so do the compat-engine presets (Kimi, Qwen, Grok, Ollama and the OpenAI-compatible adapter), DeepSeek and Gemini, each of which used to retry a 429 inside a private loop; those three now read `Retry-After`, `retry-after-ms` and the `x-ratelimit-*` names into the error too. A shared conformance case now proves, for every adapter fixture, that a 429 reaches the provider exactly once. The OpenAI and Anthropic adapters read the provider's own retry delay and rate-limit headers (`Retry-After`, `retry-after-ms`, OpenAI `x-ratelimit-*`, Anthropic `anthropic-ratelimit-*`) into the error (`LlmError::retry_after()`, `LlmError::rate_limit_hints()`). An account-level quota or spend-cap 429 (OpenAI `error.code`/`error.type` `insufficient_quota`, Anthropic `error.details.error_code` `enforced_spend_limit_reached`) is now reported as `LlmError::UsageLimitExceeded` (permanent: not retried, not paced) instead of `LlmError::RateLimitExceeded`. From plan 43-05 streaming calls (`generate_stream`) are paced exactly like buffered ones: the call waits on the gate before it starts, and a 429 (as the call's own error or as the stream's first item) opens the gate while the stream's items are still delivered unchanged; and callers released by one gate are spread by up to `min(wait / 10, 1 s)` so they do not all fire in the same instant (the spread is only ever added, never below a provider's explicit delay). From plan 43-06 a fallback chain is paced first and hops last: a chain built with `FallbackLlmAdapter::with_cadence`, `ModelFallbackMiddleware::paced` or `AgentRuntimeConfig::build_chain` (which is paced by default) now retries the same provider after its gate on a 429, for up to `treasurer.cadence.fallback_pace_budget_secs` (default 60), before it hops to the next provider; 5xx responses, timeouts and network errors still hop at once, and a chain built with `FallbackLlmAdapter::new` and no `with_cadence` still hops on a 429 immediately. From plan 43-08, when a shared pacing backend (Redis) is configured and becomes unreachable, pacing degrades instead of failing: calls keep being paced by per-process gates whose delays are multiplied by `degraded_multiplier` (default 2.0, so a delay-less first 429 gates for twice the base back-off and a provider's own minimum is only ever raised), exactly one `warn` record is emitted under the `paladin::cadence` log target per outage and one `info` record on recovery, and the shared backend is retried at most once every 5 seconds and used again automatically once it answers; a gate recorded locally during the outage is still honoured after recovery. No LLM call fails because the pacing backend is down. From plan 43-09 the run engine's own port (the one every `POST /v1/runs` run and every `WarGraph` node calls through) is paced as well, and `paladin-server` builds ONE wiring at boot that the resident agents, the runtime provisioner and the run engine all share, so a 429 seen through any of them delays the next call to the same provider and model through the others; `treasurer.cadence.backend: { redis: { url_env: NAME } }` shares that state across a fleet (needs a binary built with `redis-cadence`; one without it refuses to start naming the feature rather than pacing in-process). From plan 43-11 a `WarEngine` built with both `with_node_cache` and the new `with_cadence(port, lock_ttl)` executes a cache-policy node once across concurrent identical cache misses (two workers, or two threads of one worker): the dispatch that takes the Cadence stampede lock executes and stores its result, and the others wait up to `lock_ttl` (polling about every 100 ms) and serve the stored delta as a cache hit; a lock error, an elapsed `lock_ttl` or a cancelled run never fails a node. Engines built without `with_cadence`, and nodes without a cache policy, are unchanged, and `paladin-server` attaches no node cache and so no lock. Later Phase 43 plans extend this row. | Every deployment that calls an LLM provider. A workload that previously rode out brief 429 bursts by immediate retry may now see those calls wait or surface a rate-limit error after `max_wait_secs`. Code that matched `LlmError::RateLimitExceeded` to detect an exhausted OpenAI quota or Anthropic spend cap now receives `LlmError::UsageLimitExceeded` for it. | None required. To opt out, set `treasurer.cadence.enabled: false`; to tune, adjust the `treasurer.cadence` keys (section 9.5). |

**Worked examples** (owed alongside the rows above, per D-08's rule that a pending item is acceptable only in later-epic-owned content):

- M-B-01: **landed (CF-01, Phase 23).** A v0.9 campaign edge like

  ```rust
  // v0.9 — this edge silently fired on EVERY run, regardless of what
  // `analyzer` actually output, because `EdgeCondition::Custom` had no
  // registration mechanism and evaluated as always-true (BUG-01).
  campaign.add_edge(CampaignEdge::new(
      analyzer_id,
      escalate_id,
      EdgeCondition::Custom("is_urgent".to_string()),
  ))?;
  let service = CampaignExecutionService::new(paladin_port);
  ```

  now fails loudly at validation unless an evaluator is registered for
  `"is_urgent"`. The v0.10 fix registers one on the service (the same
  `CampaignEdge`/`EdgeCondition::Custom` construction is unchanged):

  ```rust
  use paladin_battalion::edge_evaluator::{EdgeConditionEvaluator, EdgeContext, EdgeEvaluatorError};

  struct IsUrgent;

  #[async_trait::async_trait]
  impl EdgeConditionEvaluator for IsUrgent {
      async fn evaluate(&self, output: &str, _ctx: &EdgeContext<'_>) -> Result<bool, EdgeEvaluatorError> {
          Ok(output.to_lowercase().contains("urgent"))
      }
  }

  let service = CampaignExecutionService::new(paladin_port)
      .with_evaluator("is_urgent", Arc::new(IsUrgent));
  ```

  The `WarEngine` path registers the same evaluator via
  `WarEngine::with_edge_evaluator("is_urgent", Arc::new(IsUrgent))`.
  A user who does not want an evaluator at all can instead replace the
  condition with `EdgeCondition::Contains("urgent".to_string())`,
  `EdgeCondition::Regex(...)`, or `EdgeCondition::Always` — no registry
  entry needed for any of the three. Skipping both routes produces this
  exact validation error, transcribed verbatim from the shipped code
  (`BattalionError::InvalidGraph`'s `Display`, legacy path; the
  `WarEngine` path's `EngineError::UnregisteredEdgeCondition` names the
  same offending set):

  ```text
  Invalid graph: unregistered custom edge condition(s): is_urgent -- register with CampaignExecutionService::with_evaluator before calling execute
  ```
- M-B-02: **landed (HITL-04, Phase 24).** Before this phase, SIGTERM/SIGINT exited the process
  immediately — any in-flight superstep run was dropped mid-flight with no chance to reach a
  Halted boundary, and neither shipped manifest declared `terminationGracePeriodSeconds`:

  ```yaml
  # v0.9 — k8s/server/deployment.yaml's pod spec (no termination grace declared;
  # the kubelet's own default of 30s applied, with no relationship to any
  # engine-level grace concept because none existed)
  spec:
    template:
      spec:
        containers:
          - name: paladin-server
            # ...
  ```

  After this phase, the process waits up to a configured grace window for
  in-flight runs to drain before exiting, and both shipped manifests declare a
  termination grace derived from — and at least twice — that window:

  ```yaml
  # v0.10 — k8s/server/deployment.yaml's pod spec
  spec:
    template:
      spec:
        # 2x the default APP_ENGINE_SHUTDOWN_GRACE_SECS (30s) so the kubelet's
        # SIGKILL deadline never lands mid-drain.
        terminationGracePeriodSeconds: 60
        containers:
          - name: paladin-server
            # ...
  ```

  Two new env vars (`EngineConfig`, `src/config/engine.rs`) control the process-level wait:

  | Env var | Default | Effect |
  |---|---|---|
  | `APP_ENGINE_SHUTDOWN_GRACE_SECS` | `30` | Seconds `paladin-server`/`ServiceRunner` wait, after SIGTERM/SIGINT, for in-flight superstep runs to finish before giving up on the stragglers. |
  | `APP_ENGINE_GRACEFUL_SHUTDOWN` | `true` | Set `false` to restore the v0.9 no-wait behavior for legacy-only deployments — the process cancels in-flight runs and exits immediately without waiting. |

  An operator upgrading with no config changes gets `shutdown_grace_secs=30`,
  `graceful_shutdown=true` and `terminationGracePeriodSeconds: 60` from the shipped
  manifests — a strictly safer default than v0.9's immediate exit, not a behavior an operator
  must opt into. A run still executing when SIGTERM arrives either finishes inside the grace
  window (Waypoint records completion normally) or is aborted at the deadline (`NodeOutcomeKind::
  Skipped { reason: "shutdown" }`, re-listed in the Halted Waypoint's vanguard for exactly-once
  resume) — no in-flight work silently vanishes either way.
- M-B-03: **landed (RT-07, Phase 26).** No behavioral change — the v0.9 loop already fed a failed
  tool call back into the model's context and continued; this phase names that policy
  (`tool_error_mode`, default `FeedToModel`), adds `FailRun` as a new opt-in
  (`PaladinError::ArmamentFailed { tool, reason }`), and sanitizes the fed-back text. The
  sanitization is the only observable difference:

  ```text
  // v0.9 / v0.10 default (FeedToModel) -- BEFORE this phase, an upstream
  // gateway's raw error text (including a leaked credential) reached the
  // model verbatim:
  🔧 Tool Execution: fetch_report
  Result: FAILED
  Error: upstream gateway rejected the request: Authorization: Bearer sk-live-abcdef0123456789

  // v0.10 -- the identical failure, sanitized (redact-then-bound, D-34)
  // before the model ever sees it:
  🔧 Tool Execution: fetch_report
  Result: FAILED
  Error: upstream gateway rejected the request: Authorization: Bearer [REDACTED]
  You may retry with corrected arguments or proceed without it.
  ```

  Set `tool_error_mode = FailRun` (`AgentRuntimeConfig.tool_errors.mode`, or per tool via
  `tool_errors.per_tool`) to fail the run instead of feeding the error back —
  `PaladinExecutionService::with_tool_error_config`, service-level configuration only
  (`PaladinConfig` is untouched, D-10).

  **Post-plan review fix (26-REVIEW.md CR-01/WR-03/WR-01):** the sanitization above was, at
  first cut, wired into only the `ArsenalError`/handoff `Err` path (`format_error`). A
  code-review fix pass widened it to the `ArmamentResult { success: false, .. }` business-failure
  `Error:` field and the successful `Output:` field too (`format_result`, `ToolResultFormatter`) —
  both previously embedded tool-supplied text raw, and the FAILED-business-result path is
  arguably the more likely one for a tool to surface an upstream response body through, since it
  is the tool author's own designed error-reporting mechanism. The same pass also tightened the
  `key=`/`token=` marker to require a word boundary, so an ordinary word like `monkey=5` embedded
  in a tool's JSON output is no longer misredacted. No further action is required to keep today's
  behavior — this only narrows what gets sanitized (adds sanitization where none existed, and
  removes a false-positive class), it does not change the `tool_error_mode` policy itself.
- M-B-04: no worked example owed — this phase (ENG-08) both introduces the behavior and documents it in full above.

**Note on Phase 25 (Node-Level Fault Tolerance — epic `FT`), D-30: no behavioral change; no row is added above.** Every Aegis capability — per-node retry, per-attempt `run_timeout`/`idle_timeout`, `Route`/`Absorb`/`Custom` error handlers, node result caching — is **opt-in per node** through `WarGraph::set_aegis`/`with_default_aegis` (code, not configuration; §9.5), and a v0.9 graph declares none, so an upgraded deployment's workflows execute identically: one attempt per node, no per-attempt bound, a node failure fails the run with the same `node execution error: {message}` display line as before, and nothing is served from a cache (`node_without_aegis_behaves_exactly_as_before`, `pre_aegis_and_limit_failures_carry_none`, `the_display_line_on_a_failed_waypoint_is_unchanged`). The one run-level knob this phase makes real, `EngineConfig.run_timeout_secs` (§9.5), keeps its `None` default, so no run gains a budget it did not configure. `FallbackLlmAdapter` is a new adapter a caller constructs explicitly — no existing provider adapter's behavior changes, and the shared `map_http_status` mapping (25-05) changes only which *typed* `LlmError` variant a non-2xx status becomes (`ProviderError { status }` instead of `ProcessingError(String)`), never whether an adapter's own retry loop retries it. The legacy `FormationExecutionService`/`PhalanxExecutionService`/`CampaignExecutionService`/`Commander` paths and the legacy Battalion `RetryPolicy`/`ErrorStrategy`/timeout services are untouched (X-03). Two accepted, documented caveats that are *not* behavioral changes for a v0.9 graph but matter once a node opts in: an `idle_timeout` on a node whose `PaladinPort` keeps the default `execute_observed` degrades to a per-attempt wall clock (D-19), and a hanging `EdgeConditionEvaluator` remains outside every timeout (R-23-01, still accepted — per-attempt timeouts wrap node execution, not edge evaluation).

## 9.4 Persistence & schema migrations

- **New table: `waypoints`. Landed this plan (22-06).** Two versioned migration files, one per backend (superseding this section's earlier single-path placeholder from Plan 22-04 — one crate now ships two dialects of the same logical table, hence the per-backend subdirectory split): `crates/paladin-storage/migrations/sqlite/001_create_waypoints_table.sql` (Task 1) and `crates/paladin-storage/migrations/postgres/001_create_waypoints_table.sql` (Task 2; `001_` continues the per-crate numbering convention established by `crates/paladin-memory/migrations/001_create_garrison_tables.sql`). SQLite stores `payload` as `TEXT` holding serialized JSON (D-02, for debuggability and because the `sqlx` `json` feature is already enabled workspace-wide); PostgreSQL stores `payload` as `JSONB`, bound via an explicit `::jsonb` cast on the parameter (sqlx sends bound `String` parameters as text over the wire; the cast is what tells Postgres to store it as JSONB rather than TEXT). Both share the same logical schema: `waypoint_id` (primary key), `thread_id`, `parent_id` (nullable), `superstep`, `status` (its own JSON-serialized column, so `history`/`list_threads` summaries can be built without deserializing the full payload), `payload`, `created_at`, with an index on `(thread_id, created_at DESC)`.
- **Runs automatically, not manually.** Both migrations are embedded at compile time via `sqlx::migrate!` (which required adding `sqlx`'s `macros` feature to the workspace-level `sqlx` dependency — a Task 1 blocking-issue fix, no new crate name, see §9.3) and applied automatically when `SqliteWaypointStore`/`PostgresWaypointStore` is constructed — no manual `sqlx migrate run` step is required of the operator. Idempotent: constructing a store twice against the same database is safe (`CREATE TABLE IF NOT EXISTS`/`CREATE INDEX IF NOT EXISTS` plus `sqlx::migrate::Migrator`'s own applied-version tracking), proven by `constructing_store_twice_against_same_file_is_idempotent` (SQLite) and exercised against a real server by the Postgres Tier 2 suite (`docker/docker-compose.test.yml`'s `postgres-test` service, `make test-integration-docker`).
- **Reversibility:** not reversible without data loss (dropping `waypoints` discards all checkpoint history). No `down` migration is provided, consistent with every existing migration in this workspace (`garrison`, `workflow`, `content`, `user` tables), none of which ship a reverse migration.
- **Storage growth guidance:** unbounded by default — every completed superstep writes one `waypoints` row containing a full `Battlefield` snapshot. Configure `WaypointRetentionConfig` (`max_age_days`, `max_waypoints_per_thread`; see §9.5) to bound growth. Pruning MUST NOT (and, per ENG-FR-18, will not) delete a thread's single latest Waypoint or any Waypoint with status `AwaitingInput`.
- **Memory and storage growth are measured, not asserted (ENG-NFR-01/02, Plan 22-10).** `benches/engine_benchmarks.rs` measures `SqliteWaypointStore::save` latency at three Battlefield payload sizes (1 KiB, 512 KiB, just under 1 MiB) against the ENG-NFR-01 target of under 10 ms p50, and per-superstep engine wall-clock cost at two Vanguard widths; `examples/war_engine_memory_baseline.rs` measures resident-memory growth per superstep for a fixed graph and counts Battlefield clones per superstep (ENG-NFR-02: at most one shared clone per superstep, via the Arc-shared read snapshot, plus one per concurrently executing node view), failing loudly if that bound regresses. Measured figures and the commit they were taken at are recorded in `.planning/phases/22-battlefield-state-superstep-engine/22-10-SUMMARY.md` — treat the per-checkpoint storage-growth guidance above alongside those figures, not in isolation, when sizing a deployment's Waypoint retention policy.
- **Existing state is unaffected.** Existing Citadel JSON/SQLite state files remain readable unchanged — the `waypoints` table is entirely new and additive. `WaypointPort` is deliberately separate from `CitadelPort` (see the rustdoc rationale on `crates/paladin-ports/src/output/waypoint_port.rs`: Waypoints are high-frequency and append-mostly, addressed by thread; Citadel remains for coarse, explicitly-invoked whole-entity snapshots). No Citadel schema or file format is touched by this phase.
- **Persisted `GraphFingerprint` format.** Every Waypoint's payload embeds a `GraphFingerprint` string in the form `{version}:{blake3_hex}` — a versioned tag over the blake3 hex digest of the canonical, deterministically sorted byte stream of node ids (plus Paladin output fields), edge specs, schema field dispatch rules, the declared entry set, `defer_flags`, and `dynamic_targets` (excludes prompts/models, per D-04). This format was decided at Plan 22-01's Task 1 checkpoint (option-b), specifically so a future algorithm change is a detectable new tag rather than a silent invalidation of every stored thread's `resume`. **Bumped `v1:` -> `v2:` in Phase 22.1 (CR-01, D-17):** `v1`'s canonical byte encoding concatenated fields with unescaped ASCII delimiters (`|`, `-`, `:`) that were themselves legal `NodeId`/`FieldName` characters, so two structurally different graphs could be crafted to hash identically (e.g. two nodes `"a"`+`"b"` vs. one node `"a|nf|b"`). `v2` replaces this with a length-prefixed encoding with no delimiter collision. Every `v1:`-tagged fingerprint stored before this bump is recognized as stale (a version-tag mismatch) rather than silently reinterpreted under the new encoding. **Bumped `v4:` → `v5:` in Phase 25 (D-11, 25-03):** each node's own `set_aegis` sidecar entry's `on_error` and `cache` policies (and, separately, the graph-wide `default_aegis`) now enter the hashed byte stream, sorted by node id and length-prefixed, because they change what a run *does*; `retry` and `timeout` are deliberately excluded, exactly like every `EngineLimits` field, so tightening either never makes `resume` fail `GraphMismatch`. A `v4:`-tagged fingerprint is recognized as stale on resume, never reinterpreted.
- **Phase 25 (Node-Level Fault Tolerance, D-30): none — no SQL migration.** The node cache stores Redis keys (`{key_prefix}:{key}`, each a JSON `CachedDelta` carrying its own `schema_version`, expired server-side by `PSETEX`) or process-local in-memory entries, never a table. The Waypoint additions this phase makes — `NodeExecutionRecord.attempts`/`cache_hit`, `WaypointStatus::Failed.node_error`, `FieldSpec.cache` — are additive `#[serde(default)]` fields **inside the existing JSON `payload` column**, not new columns: `BATTLEFIELD_SCHEMA_VERSION` is unchanged (`1.0.0`, pinned by test), a pre-Phase-25 payload deserializes with the defaults, and the three-backend Waypoint contract suite round-trips both shapes. No migration file was added under `crates/paladin-storage/migrations/`.

## 9.5 Configuration & environment

Every new runtime behavior this phase introduces is tunable and **disabled or defaulted to today's behavior out of the box** (X-09), so a v0.9 configuration file boots v0.10 with identical behavior. This claim is proven, not merely stated: the root integration test target `v0_9_config_boot` (`tests/integration/v0_9_config_boot_test.rs`, `cargo test --features web-server --test v0_9_config_boot`, gated on every PR by CI's `e2e-platform-api` job — see §9.6) asserts it at two levels. **Config resolution:** the frozen v0.9.0 fixture loads with `Settings::load_from_file` with no edits, `Settings::agent_runtime`/`trace`/`web_server` all resolve to their own `Default`, and each of the nine platform config structs the v0.9 config file never named as a field (`EngineConfig`, `WaypointStoreConfig`, `RunStoreConfig`, `RunQueueConfig`, `RunWorkerConfig`, `RunStreamConfig`, `AssistantsConfig`, `SchedulesConfig`, `WebhooksConfig`) reports its own inert `::default()` state and validates `Ok`, with `apply_env_overrides()` proven a no-op against every relevant `APP_*` variable cleared under `#[serial]` (`EngineConfig::graceful_shutdown` is the one deliberate exception — it defaults `true`, M-B-02's own recorded decision above, and the test asserts that value, not `false`). **Behavioral:** the composed real routers answer `200` for the six v0.9 `/v1/agents…` paths plus `/health`, `/ready` and `/openapi.json`, and `501` — never `404` — for every route family new in v0.10 (`/v1/runs`, `/v1/threads/*/history`, `/v1/assistants`, `/v1/schedules`); `501`, not `404`, is the documented answer for a disabled platform subsystem everywhere in this file, cross-referenced against §9.6's own response-code tables below. **Fixture note:** the file the test actually loads is the frozen `v0.9.0` `tests/fixtures/config/v0.9.0-config.test.yml`, not `config.example.yml` — a byte-identical frozen `v0.9.0-config.example.yml` is committed alongside it as documentation evidence only, because it does not parse at either the `v0.9.0` tag or HEAD (`LlmProviderConfig::api_key` is a required `String` and its `ollama:` block has never carried one — a pre-existing defect unrelated to this program, recorded in `tests/fixtures/config/README.md`).

- **`http.auth.api_keys[].tenant` and `http.auth.bearer_token.tenant` — landed Phase 40 (40-01), TENANT-01, D-03/D-05. The one deliberate X-09 exception of this phase: both are REQUIRED, not defaulted to today's behavior.**
  - `http.auth.api_keys[].tenant` (`ApiKeyConfig.tenant: String`, `#[serde(default)]` so the file still parses) is **required** — there is no implicit default tenant. A v0.9/v0.10 config whose `http.auth.api_keys` entries carry no `tenant` stops `paladin-server` at boot with `http.auth.api_keys[<name>]: 'tenant' is required — every API key must map to a tenant (Phase 40, TENANT-01)`, naming the key's `name`, never its secret `key` value. A malformed (non-empty but invalid, e.g. containing whitespace) value stops boot with `http.auth.api_keys[<name>]: 'tenant' is not a valid tenant id: <TenantIdError>`. To upgrade: add a `tenant:` line to every `api_keys` entry (a plain identifier — non-empty, no whitespace, printable ASCII, at most 128 bytes). A config with no `api_keys` at all is unaffected (the frozen `v0_9_config_boot` fixture has none, so that proof still passes unchanged).
  - **Extended, Phase 40 (40-03), TENANT-01:** the same boot check (`AuthConfig::validate`, called by `paladin-server`'s `build_auth_config`) now also rejects, in this order per entry: an empty key value — `http.auth.api_keys[#<index>]: 'key' must not be empty` (0-based list position, used because the name is not yet known to be printable); an invalid `name` — `http.auth.api_keys[#<index>]: 'name' is not a valid API key id: <error>` (the same identifier rule as a tenant id); a duplicate `name` — `http.auth.api_keys[<name>]: duplicate 'name' — every API key name must be unique`; and a duplicate `key` value — `http.auth.api_keys[<name>]: duplicate 'key' — the same secret is already configured for '<first name>'`, which names both entries by `name` and NEVER prints the shared secret. A v0.10 config that happened to carry two keys with the same name or the same value therefore stops at boot instead of silently letting the later entry shadow the earlier one; fix the duplicate, do not remove `tenant`. The `paladin-cli` onboarding template needed no change.
  - `http.auth.bearer_token.tenant` (`BearerTokenAuthConfig.tenant: Option<String>`) is **required when `bearer_token.enabled` is true** (D-03) — every verified bearer principal must carry a tenant. A verified bearer token while this is unset does NOT authenticate (401, fail closed, `verified_bearer_token_without_configured_tenant_fails_closed`); `paladin-server` itself refuses to boot with `http.auth.bearer_token: 'tenant' is required when bearer_token.enabled is true — bearer-token principals must map to a tenant (Phase 40, TENANT-01)` when `enabled: true` carries no `tenant`. `bearer_token.enabled: false` (today's default) is entirely unaffected.
  - **Why this is X-09's one deliberate exception:** every other config addition in this document defaults to today's inert behavior; this pair cannot, because TENANT-01/D-05 forbid an implicit default tenant — silently defaulting every key to one shared tenant would pool every caller's runs and spend into a single scope, precisely the cross-tenant leak Phase 40 exists to close. The cost is paid once, at upgrade time, by adding one `tenant:` line per configured key/bearer section.

## 9.6 HTTP API

**New engine-backed endpoints — landed this phase (HITL-05, Plan 24-11):** three thread routes in
`paladin-web`, nested under `/v1` (ADR-0037) and authenticated by the same middleware `/v1/agents/*`
already uses. `ThreadApiState` is a new, separate router state (`AgentApiState` is untouched — a
deliberate zero, §9.2). Every route answers `501 not_implemented` (naming
`APP_WAYPOINT_STORE_BACKEND`) when no waypoint backend is configured — the spec still lists the
paths regardless of runtime wiring.

| Method | Path | Status codes |
|---|---|---|
| `GET` | `/v1/threads/{id}/state` | `200`, `400`, `401`, `404`, `501` |
| `POST` | `/v1/threads/{id}/resume` | `202`, `400`, `401`, `403`, `404`, `409` (two distinct envelope `code`s — `thread_not_awaiting_input`, `graph_not_registered` — sharing this one HTTP status), `501` |
| `GET` | `/v1/threads/{id}/history` | `200`, `400`, `401`, `501` |

`POST .../resume` additionally requires an admin-role credential via
`crate::agent_auth::require_admin`, returning `403` for an authenticated non-admin caller. This
narrows D-24's "authenticated callers, any role" default for the one mutating route only (CR-01,
`24-REVIEW.md`, commit `00b1e552`), because neither `ThreadId` nor `Waypoint` carries an
owner/principal to scope against yet. `GET .../state` and `GET .../history` remain
authenticated-any-role. Every credential configured for the resume route must be treated as
admin-equivalent until PLAT-06 (Phase 27) supplies real per-thread ownership scoping;
`crates/paladin-web/src/thread_controller.rs`'s module rustdoc carries the full rationale.

**Run reads are tenant-scoped -- landed Phase 40 (40-01, 40-02, 40-05), PLAT-07, D-11/D-12/D-13.**
Every run now records the principal that submitted it (the tenant configured for the API key,
and the key's configured name -- §9.2 `Run` row, §9.4 migration `008`), and every run read route
serves only the runs the calling principal may see. The rule is one shared core value
(`RunReadScope`, `paladin-core`): a **user-role** principal sees only runs recorded under its own
tenant (two keys of the same tenant see each other's runs; a key of another tenant does not; a
user-role principal never sees a run with no recorded principal), and an **admin-role** principal
-- including the open-access principal when authentication is disabled -- sees **every** run,
including runs with no recorded principal (schedule-fired, same-process, pre-v0.11 rows). The
tenant comes only from the key's configured mapping (§9.5); no header, query parameter or body
field can name one, and a `tenant_id` query parameter on `GET /v1/runs` is unknown and ignored.
Behaviour by route: `GET /v1/runs` lists only the caller's tenant's runs (admin: all), with the
`thread_id`/`assistant_id`/`status` filters composing with the scope inside the store's own query
(another tenant's `thread_id` is an empty page; the keyset cursor walk stays gap-free);
`GET /v1/runs/{run_id}`, `GET /v1/runs/{run_id}/stream`, `GET /v1/runs/{run_id}/webhook-deliveries`
and `POST /v1/runs/{run_id}/cancel` answer the **missing-run `404`** -- the same status, code and
message as a run that does not exist, never a `403` -- for another tenant's run; cancel checks
visibility BEFORE the assistant `allowed_roles` check, so it neither leaks existence nor permits a
cross-tenant mutation. `/stream`, `/cancel` and `/webhook-deliveries` now also answer `501`
naming `run_store.backend` when the run store is not configured (previously they needed only
their own port), because the visibility check reads the run row. `GET /v1/runs/{run_id}/webhook-deliveries`
gains a documented `404` row in `crates/paladin-web/openapi.json`; the other three routes'
existing `404` descriptions are reworded to "Unknown run, or a run the caller may not see". A

**Allowance refusals answer 429 allowance_exhausted -- landed Phase 41 (41-01), ALLOW-02, D-12/D-13.** `POST /v1/runs` by a principal whose API-key or tenant allowance is exhausted (a balance at or above a configured ceiling) answers `429` with the envelope `code` `allowance_exhausted` -- a different code from the per-IP rate limiter's, so a client can tell quota from pacing by the body code alone -- and `error.details` carrying exactly `scope` (`api_key` or `tenant`), `kind` (`window` or `lifetime`), `balance` and `ceiling` (display strings such as `25.0000 USD`) and `window_start`/`window_end` (RFC 3339, `null` for a lifetime ceiling). **Operator allowance notices -- landed Phase 41 (41-08), ALLOW-04, D-17.** When `treasurer.allowance.webhook { url, secret }` is configured, every warn-threshold notice an admission wins is delivered once to that operator URL through the existing durable webhook queue: a `webhook_deliveries` row with event `allowance_warning`, drained by `WebhookDeliveryService` over the existing no-redirect client with the same bounded retries, `3xx`/`4xx` dead-lettering and send-time SSRF check as a run webhook. The JSON payload has exactly twelve keys -- `event` (always `allowance_warning`), `scope` (`api_key` or `tenant`), `kind` (`window` or `lifetime`), `balance` and `ceiling` (display strings such as `0.8000 USD`), `window_start` and `window_end` (RFC 3339, `null` for a lifetime ceiling), `warn_at`, `run_id` (the admitting run, `null` on the HTTP agent routes), `timestamp` (the store instant the notice was recorded at), `tenant_id` and `api_key_id` (the API key NAME, `null` for a tenant-scope notice, never a key value) -- and never run input, a key value or a secret. It is signed `X-Paladin-Signature: sha256=<hex>` over the exact stored bytes with `treasurer.allowance.webhook.secret` (or `APP_TREASURER_ALLOWANCE_WEBHOOK_SECRET`), held on the delivery service and never written to the row; the request carries `X-Paladin-Event: allowance_warning`. The row names a correlation run id that no run owns and the fixed thread `treasurer-notices`, so `GET /v1/runs/{id}/webhook-deliveries` never lists it, and a caller cannot subscribe a run or schedule webhook to `allowance_warning` (the caller-facing event parser answers `400`). The URL is checked by the SSRF guard at boot -- `paladin-server` refuses to start, naming `treasurer.allowance.webhook.url` and pointing at `webhooks.allow_private`, for a private or loopback target; the cloud metadata address is always rejected -- and again at send time. Omitting `webhook` disables only this leg: the notice row, the trace event and the herald line still occur. An enqueue failure after a won notice is logged at `error` and not retried, and never affects the run. At most one notice per scope, limit kind, window and ceiling, so at most one delivery for each. **Rollout rule (RESEARCH Pitfall 12): enable `treasurer.allowance.webhook` only after every replica runs this build.** A replica from before this change decodes `webhook_deliveries.event` with a closed parser, so its `claim_due` rejects the unknown `allowance_warning` row and fails its whole batch, stalling run-webhook delivery on that replica until it is upgraded. Delivery is at-least-once: a retried attempt after an ambiguous failure can reach the operator twice, and `X-Paladin-Delivery` identifies the row.

**Halted runs report why and where to resume -- landed Phase 42 (42-03), ALLOW-03, D-06/D-19, G7.** `GET /v1/runs/{run_id}` and every row of `GET /v1/runs` gain two always-serialised properties: `halt_reason` (an object, or `null`) and `final_waypoint_id` (the run's final Waypoint id, or `null`). For a run halted by an exhausted allowance `halt_reason` is `{ "reason": "allowance_exhausted", "scope", "kind", "balance", "ceiling", "window_start", "window_end" }` -- the figures of the Phase 41 `429 allowance_exhausted` `details`, built by the same function, with `balance` and `ceiling` rendered from integer nano-units as display strings (`"1.0000 USD"`); it is `{ "reason": "ledger_unavailable" }` when the ledger could not be read and the run halted fail-closed; and `null` for every run that did not halt on spend. `final_waypoint_id` of a halted run is the Halted Waypoint -- the fork point to resume from. `error` stays `null` for a halt: a halt is a resume point, not a failure. The object carries only the halted ceiling's own figures -- never another scope's, a tenant id, or an API key name or value. The caller's `halted` run webhook payload gains the same optional `halt_reason` key (other events are unchanged and the `X-Paladin-Signature` is still computed over the stored payload bytes). `crates/paladin-web/openapi.json` was regenerated through `openapi_matches_committed_baseline` (`make openapi`): two nullable properties on `RunResponse`, nothing removed; the `v0.9.0` golden gate is untouched because `RunResponse` and every `/v1/runs*` path postdate the frozen baseline. **Resuming a halted run (Phase 42, 42-04, D-07):** a halted run is terminal, so resume is a new run forked from its `final_waypoint_id` -- `POST /v1/threads/{thread_id}/fork` with `from_waypoint_id` set to it -- which answers `429 allowance_exhausted` with `Retry-After` while the window is still exhausted and, once admitted, continues from the Halted Waypoint without re-running a completed superstep. A `ledger_unavailable` halt resumes the same way once the ledger reads again; an agent-kind run has no checkpoint and is resumed by a fresh `POST /v1/runs`. No new route, field or status code: the fork route and its `429` already shipped.

**SSE done reports why a run halted -- landed Phase 42 (42-05), PLAT-09, D-14/D-16, G10.** A spend-halted run's `done` event on `GET /v1/runs/{run_id}/stream` now carries `halt_reason` -- the same object `GET /v1/runs/{run_id}` returns, built by the same `HaltReason::wire_json` function -- beside `status`, `waypoint_id`, `usage` and `trace_seq`: `{ "status": "halted", ..., "halt_reason": { "reason": "allowance_exhausted", "scope", "kind", "balance", "ceiling", "window_start", "window_end" } }`. A ledger-unavailable halt is a `done` with `"halt_reason": { "reason": "ledger_unavailable" }` on both the live and the degraded path, never an `error` event (`error` stays reserved for `failed`). A halt with no Treasurer reason (a caller cancel or a token halt) keeps the old payload byte for byte, with no `halt_reason` key. The live, degraded and replay paths agree on `status` and `halt_reason` for the same run, and a replayed stream takes its terminal `status` and `halt_reason` from the run row when the row is terminal and skips a persisted `RunFinished` while the row is not (a worker draining on shutdown leaves its run `running`), so a stored trace for a caller-cancelled run, which recorded `halted`, now replays as `cancelled`. `waypoint_id` follows each path's existing rule. Additive: a client ignoring unknown keys is unaffected; the seven frozen event names are unchanged.

**SSE done reports cancelled; a drain is not terminal -- landed Phase 42 (42-06), PLAT-09, D-14/D-15.** A caller-cancelled run's `done` event on `GET /v1/runs/{run_id}/stream` now carries `status: "cancelled"` (it said `halted` before), equal to the `cancelled` status `GET /v1/runs/{run_id}` reports, and carries no `halt_reason` key. This holds on both routes a cancel can take: through the instance that dispatches the run (the in-process token, now reported to the engine by a per-run probe) and through another instance (the durable flag, observed at the next superstep boundary by the debounced probe). A worker shutdown that drains a run mid-flight emits no `done` and no `error`: the run row stays `running` and its queue message is redelivered, so a subscriber sees the stream end without a terminal event and reconnects to follow the redelivered run. A spend halt that lands during shutdown is still a `done` with `status: "halted"` and its `halt_reason`. A client that matched `done.status == "halted"` to detect a cancel must also match `cancelled`; a client that treated stream end without `done` as an error should treat it as "reconnect". The seven frozen event names are unchanged.

**Agent routes stop on the allowance -- landed Phase 42 (42-08), ALLOW-05, D-10/D-12/D-13.** The three HTTP agent routes that start spend -- `POST /v1/agents/{id}/execute`, `POST /v1/agents/{id}/execute/stream` and `POST /v1/agents/{id}/jobs` -- now bound an agent's loop by the caller's remaining allowance. Admission derives a per-run token budget from the tightest remaining ceiling at the agent model's dearest `treasurer.pricing` price (every token billed at the dearest axis, so a prompt-heavy agent stops earlier than its true spend would require), and the agent loop ends after the model response that crosses it. A call that ends this way answers `200` with `stop_reason: "allowance_halted"` and a `halt_reason` object -- the same object `GET /v1/runs/{run_id}` returns, built by the same `HaltReason::wire_json` -- with the partial output kept and the truncation notice appended. The figures report the binding ceiling with `balance` equal to the ceiling, a deliberately conservative bound because the loop does not know the true post-spend balance. `POST /v1/agents/{id}/jobs` records the same `stop_reason` and `halt_reason` on its job result, and the buffered fallback of `execute/stream` (an agent with no streaming backend, whose `done` event is the serialized `ExecuteResponse`) carries them in its `done` data. A **true streamed** `execute/stream` call is one provider call that the server never cuts: it is admission-only, and its overshoot is that whole call. Its terminal `done` stays `{ "done": true, "usage": ... }` byte for byte unless the final chunk's reported `total_tokens` is strictly greater than the derived figure, in which case it additionally carries an informational `halt_reason` object (the same shape) that reports the crossing -- not a halt the server performed (the operator's option-b decision at the Phase 42 design gate, ADR-0057 group e). Every other `stop_reason` response is byte-identical to before: the `halt_reason` key is absent unless the call was halted. **`422 model_unpriced`:** a principal with a configured allowance ceiling calling an agent whose model has no `treasurer.pricing` row is refused before the agent runs, on all three routes, with `code` `model_unpriced`, `details.model` naming the model and no `Retry-After` header (a configuration incoherence, not pacing; spend that cannot be metered cannot be bounded). A derived budget of zero is refused `429 allowance_exhausted` with the binding ceiling's real figures, and a principal with no ceiling is unaffected on every route. **The operator `agent_runtime.token_budget` now takes effect on the HTTP agent routes:** every per-agent service, config-defined or runtime-provisioned, installs the one `TokenBudget`, enforcing the tighter of the operator figure (when `enabled`) and the allowance-derived one (a tie goes to the allowance); before this change the operator figure was inert on these routes. A deployment with the operator budget disabled and no allowance is unchanged. `crates/paladin-web/openapi.json` is regenerated (`make openapi`): `ExecuteResponse` gains an optional `halt_reason` object and the three operations document a `422` response; the frozen v0.9 golden gate carries a fourth sanctioned, narrowly-scoped exception (`strip_known_v0_11_halt_reason`) that removes exactly those two additions from both documents before comparing, and a test fails if it widens.

**Agent-kind runs stop on the allowance -- landed Phase 42 (42-09), ALLOW-03, ALLOW-05, D-08/D-09/D-10/D-12/D-13.** A run of an agent-kind assistant (`Runnable::Agent`) is bounded exactly as the HTTP agent routes are. `POST /v1/runs` for an agent-kind assistant by a principal with a configured ceiling is admitted with the agent's model (taken from the resolved assistant, never from the request): a model with no `treasurer.pricing` row answers `422 model_unpriced` (`details.model`, no `Retry-After`) and an allowance too small to buy one token of that model answers `429 allowance_exhausted`, both before any run row is written; workflow assistants keep the model-less admission and are unchanged. The worker then re-derives the budget **at dispatch** from the ledger (never from a figure persisted at submit time, so an allowance spent while the run was queued is honoured) and the run ends after the model response that crosses it: the run is recorded `halted` (it was `completed` before, with no limit), `error` stays `null`, `halt_reason` is the `allowance_exhausted` object, the partial output is kept on the row with the truncation notice appended, the live and replayed SSE `done` carries `status: "halted"` and the `halt_reason`, and the subscribed `halted` webhook carries it too. A zero or exhausted figure at dispatch records the same halt, and an unreadable ledger records `halt_reason` `ledger_unavailable` (fail closed), in both cases without calling the model. A model that lost its price row between admission and dispatch records `failed` with an error naming the model, also without calling the model. A schedule-fired agent-kind run refused as unpriced is counted and logged like the schedule's other non-allowance submission failures, never as an allowance skip. **Agent-kind runs have no checkpoint (D-08):** the agent loop writes no Waypoint, so a halted agent-kind run has `final_waypoint_id: null`, cannot be forked from a checkpoint, and is resumed by submitting a fresh `POST /v1/runs`, which re-executes from the start; the engine path's continue-from-checkpoint is unchanged (recorded as a known window in `.planning/WINDOWS.md`). **The operator `agent_runtime.token_budget` does not apply to these runs:** the shared run-engine service, which also executes every engine node, installs the `TokenBudget` in Treasurer-only mode with the operator figure forced off, so only a call whose scope carries a derived figure is ever cut and an engine node is never capped (an operator budget there would hand a successful partial result to a Battlefield, ADR-0052). `crates/paladin-web/openapi.json` is regenerated (`make openapi`): `POST /runs` documents the `422`; `POST /runs` is not in the frozen v0.9 document, so the golden gate needs no new exception.

**Mid-run allowance notices -- landed Phase 42 (42-11), ALLOW-03, D-17/D-18.** A run that crosses `warn_at` while it is running now warns at its first superstep boundary past the threshold, instead of waiting for the next admission: the same once-per-window notice claim as admission, emitting exactly one `allowance_warning` trace event on that run's own stream and queueing one operator `allowance_warning` delivery; a lost claim (another run or an admission already owns the window's notice) emits nothing. A spend halt now sends the operator one `allowance_halted` delivery per scope, limit, window and ceiling: the payload carries the same twelve keys as `allowance_warning` with `event` set to `allowance_halted`, `run_id` the halted run and `warn_at` the ceiling's configured threshold, so a receiver that already handles the warning needs only a new `event` value; twenty runs halting in one window produce one delivery. A `ledger_unavailable` halt claims no notice and sends nothing (it is logged at `error`). The boundary guard remembers, per run, each notice claim it already tried, so a long run past its threshold writes at most one claim per ceiling and window rather than one per boundary; the store remains the source of truth and a claim never changes the guard's halt or continue decision. No configuration changes and no new route: the notices ride the Phase 41 `treasurer.allowance.webhook` target and signing secret, and a deployment with no operator webhook still records the durable rows and the trace warning. `crates/paladin-web/openapi.json` is unchanged. **Rollout caveat:** enable this on every replica before relying on it -- a replica running a build from before 42-10 cannot parse the `allowance_halted` event it would find in the shared delivery queue. No public Rust item is added (`Treasurer::spend_guard` keeps its signature; the emitter-carrying constructor is crate-private), so there is no §9.2 row.

## 9.8 Upgrade checklist

One ordered, copy-pasteable checklist for an operator upgrading a v0.9.0 deployment to v0.10.0.
Every step below names a concrete command or file present in the shipped tree; none invents a
subcommand that does not exist.

1. **Back up state.** Snapshot every state directory and database this deployment uses: the
   waypoint store (`SqliteWaypointStore`/`PostgresWaypointStore`'s backing file or database,
   §9.4), the run store (`RunStoreConfig`'s SQLite file or PostgreSQL database, §9.5), the
   Garrison SQLite database if used, and any Citadel state files — Citadel's own file format is
   unaffected by this program (§9.4's repeated "existing state is unaffected" notes). There is no
   destructive migration to reverse a bad upgrade against; a restored backup plus the v0.9.0
   binary is the rollback path.
2. **Apply migrations — by starting the new binary, not a separate command.** Every migration
   this program added (`waypoints`, `garrison_entries.is_summary`, `vault_records`, `runs`,
   `assistants`/`assistant_versions`, `run_schedules`, `webhook_deliveries`, `run_traces` — the
   full list is §9.4) runs automatically at adapter construction via `sqlx::migrate!`; there is no
   `sqlx migrate run` step for an operator to invoke by hand. Start the new `paladin-server`
   binary once against the restored backup and confirm it comes up cleanly. **PostgreSQL note:**
   the same automatic-migration mechanism applies to `PostgresWaypointStore`/
   `PostgresRunRepository`/etc.; no separate manual migration step is needed there either.
3. **Update config — nothing is required.** Every new v0.10 config surface defaults to today's
   behavior, proven by the `v0_9_config_boot` integration test (§9.5): a v0.9 configuration file
   boots this binary with every new subsystem inert. No `config.yml` edit is required to preserve
   v0.9 behavior; add a section only when actually adopting a new capability.
   **Phase 40 note (TENANT-01, the one exception — see §9.5):** a deployment that configures
   `http.auth.api_keys` must add a `tenant:` line to EVERY entry, and a deployment with
   `http.auth.bearer_token.enabled: true` must also set `http.auth.bearer_token.tenant`;
   `paladin-server` refuses to boot otherwise, naming the key's `name`, never its value. Key names
   and key values must also be unique. After this upgrade a run is visible only to principals of
   the tenant that submitted it (another tenant's run answers `404` on every `/runs/{run_id}*`
   route, §9.6), so any operator tooling that reads other tenants' runs over HTTP needs an
   `admin`-role key. A deployment with no `api_keys` and bearer disabled is unaffected.
4. **Raise `terminationGracePeriodSeconds`.** Set it to at least `60` — twice the default
   `APP_ENGINE_SHUTDOWN_GRACE_SECS` of 30s, or at least twice whatever value you configure that env
   var to — in every Deployment manifest before rolling out this upgrade (M-B-02, §9.1). The
   shipped manifests (`k8s/deployment.yaml`, `k8s/server/deployment.yaml`,
   `k8s/server/worker-deployment.yaml`) already carry `terminationGracePeriodSeconds: 60`; an
   operator running a forked or hand-written manifest must make the same change there.
5. **Register a custom evaluator for every `EdgeCondition::Custom` name in use.** M-B-01's fix
   (§9.1) makes an unregistered custom edge condition a validation failure, not a silent
   always-true. Register one via `CampaignExecutionService::with_evaluator("name",
   Arc::new(evaluator))` on the legacy execution path, or `WarEngine::with_edge_evaluator("name",
   Arc::new(evaluator))` on the `WarEngine` path, before calling `execute`/`start` — M-B-01's
   worked example above shows the exact registration call and the validation error text this step
   avoids.
6. **Deploy.** Roll out the new binary and manifests with the grace period and evaluator
   registrations from steps 4-5 already in place.
7. **Verify.** Run `paladin-cli setup-check --verbose` for an environment/toolchain/provider/
   service connectivity check; if the deployment uses the Maneuver flow DSL, run `paladin-cli
   maneuver validate` against its flow configuration; and run `paladin-cli eval run <glob>`
   against a representative scenario glob for a behavioral post-deploy check. `GraphCommands`
   exposes exactly one subcommand, `export` (`paladin-cli graph export --format mermaid|dot`), for
   inspecting a graph's structure — there is no separate command for a runtime probe.
